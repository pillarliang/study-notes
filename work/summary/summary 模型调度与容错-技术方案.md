# Model hub 模型调度与容错方案

## 一、概述

Plaud Model Hub 向业务侧暴露一个稳定的逻辑模型名（如 `summary-gemini`），把请求自动分发到多个底层 Endpoint（GSU、PayGo、跨厂商等），并在调用失败时按"重试 → Failover → 跨模型降级"自动救援。所有策略由 YAML 驱动，业务代码零改动。

要解决的三类约束：

- **配额上限**：单 Endpoint RPM 固定，触顶即 429
- **成本结构**：GSU 预付费便宜但容量受限，PayGo 按量计费贵但弹性，需要 GSU 优先、PayGo 兜溢出
- **可用性 SLA**：单点抖动不能直接打回业务

## 二、架构与流量分发

业务面向逻辑模型编程，调度层把流量按权重/优先级分发到物理 Endpoint：

```
        ┌──────────────────────────────────────────┐
        │            业务层（无需改动）               │
        │   client.invoke("summary-gemini", ...)   │
        └──────────────────┬───────────────────────┘
                           │
        ┌──────────────────▼───────────────────────┐
        │          Plaud Model Hub 调度层           │
        │   路由策略 + 健康管理 + Failover + Fallback │
        └──────────────┬─────────────┬─────────────┘
                       │             │
                  ┌────▼────┐   ┌────▼────┐
                  │ Vertex  │   │ Vertex  │
                  │  GSU    │   │  PayGo  │
                  │ (80%)   │   │  (20%)  │
                  └─────────┘   └─────────┘
                   预付费配额      按量计费
```

**路由策略**（按 logical model 独立配置）：

| 策略   | 行为                    | 适用                       |
| ---- | --------------------- | ------------------------ |
| 加权随机 | 按 weight 随机，长期收敛于设定比例 | 成本/容量加权（GSU:PayGo = 8:2） |

### 配置示例

```yaml
models:
  summary-gemini:
    routing_policy: WEIGHTED_RANDOM
    endpoints:
      - id: vertex-gsu-us
        provider: vertex_ai
        model: gemini-2.5-pro
        region: us-central1
        weight: 80                # 优先消耗 GSU 预付费配额
      - id: vertex-paygo-us
        provider: vertex_ai
        model: gemini-2.5-pro
        region: us-central1
        weight: 20                # 溢出走 PayGo 按量计费

  summary-gpt:
    endpoints:
      - id: openai-gpt
        provider: openai
        model: gpt-5.5

policies:
  summary-gemini:
    fallback_model:               # 列表顺序即降级顺序
      - summary-gpt               # 一级降级：跨厂商
      - summary-claude            # 二级降级
```

## 三、故障处理与恢复机制

故障处理在两条独立的轨道上同时运行，互相喂数据形成闭环：

- **单次救援**（针对当前请求）：重试 → Failover → Fallback，让这一次调用尽量成功
- **健康管理**（针对未来请求）：根据滑动窗口统计调整路由权重与可用性，避免反复撞

### 3.1 单次救援链

按递进顺序串联，前一级失败才进入下一级：

| 阶段         | 触发                  | 动作                                                             | 失败后                        |
| ---------- | ------------------- | -------------------------------------------------------------- | -------------------------- |
| ① 退避重试     | 当前 Endpoint 返回 429  | 优先按服务端 `Retry-After` 退避（缺省时指数退避 1s/2s/4s + 抖动），同 Endpoint 重试一次 | 进入 ②                       |
| ② Failover | 重试仍失败，或返回 5xx/超时    | 把当前 Endpoint 加入本次请求的排除集，从同模型其他 Endpoint 选一个再试                  | 进入 ③                       |
| ③ Fallback | 同模型所有 Endpoint 均不可用 | 按 `fallback_model` 列表顺序切换到备选模型                                 | 备选模型独立再走一遍 ①②；列表全部失败才向业务抛错 |

> Fallback 切到的备选模型享受完整的前两级救援——切到 GPT 不会丢失重试与 Failover 能力，CTO 不需要关心兜底链上的某个备选模型自身是否单点。

### 3.2 Endpoint 健康管理

三种机制按错误类型分工，互不重叠：

| 机制        | 应对错误            | 触发条件                     | 对路由的影响                          | 恢复条件（无需人工）                                         |
| --------- | --------------- | ------------------------ | ------------------------------- | -------------------------------------------------- |
| **自适应权重** | 429 频发          | 滑动窗口内 429 比例上升           | 该 Endpoint 权重渐进下降，但保留 ≥10% 探测流量 | 滑动窗口（默认 120s）内旧记录过期、错误率回落 → 权重自然回升                 |
| **熔断器**   | 5xx / 超时 / 连接异常 | 60s 内失败率 > 50% 且调用 ≥ 5 次 | OPEN，Router 完全跳过该 Endpoint      | 30s 后进入 HALF_OPEN 探测，连续成功 3 次回 CLOSED；探测失败则继续 OPEN |

> 单次 429 的退避重试由 §3.1 救援链 ① 处理（解析服务端 `Retry-After` 喂给 Engine 决定 sleep 时长），属于救援链层，不在健康管理范畴。

**为什么需要自适应权重**：朴素的"二值切换"（429 一来直接摘除 Endpoint、过期再放回）会让流量在主备之间瞬间倾倒，备份很容易被洪峰击垮造成连锁 429。自适应权重按错误率渐进降权，让备份有时间适应；下限探测流量保证主 Endpoint 配额恢复后能第一时间感知。

```
GSU 错误率   GSU 权重           流量分配
 0%          80（原始）          GSU 80% │ PayGo 20%
 50%         20（×0.25）         GSU 50% │ PayGo 50%
 80%         8（下限保护）       GSU 29% │ PayGo 71%
 恢复        80（自然回升）      GSU 80% │ PayGo 20%
```

### 3.3 Model 整体熔断

当某个 model 的**全部 Endpoint 同时不可用**（被限流或熔断）时，调度层捕获 `NoAvailableEndpointError`，按 `fallback_model` 列表跨模型降级。判定基于实时路由信号，无独立状态机；任一 Endpoint 重新可用即自动解除。

> 自适应权重的下限保护故意保留少量探测流量，避免轻度拥塞被误判为整模型熔断——只要还有探测流量在跑，model 就不算熔断。

### 3.4 一次完整失败的处理路径

```
请求进入
  │
  ├─ 路由层选 Endpoint：排除熔断中 Endpoint，应用自适应权重
  │
  ├─ 调用 → 成功？
  │     ├─ 是 → 回写滑动窗口 → 返回
  │     └─ 否 ↓
  │
  ├─ 429    → 按 Retry-After 退避重试 → 仍失败 → Failover
  ├─ 5xx    → Failover（不在原 Endpoint 重试）
  │
  ├─ 同模型 Endpoint 全部失败
  │     └─ Fallback 至备选模型 → 备选模型再走完整救援
  │
  └─ 不论成败：错误统计回写自适应权重/熔断器，影响下一次路由
```

## 五、综合效果

以"GSU 80% / PayGo 20% + GPT-5.5 兜底"为例：

| 场景 | 单 Endpoint | Plaud Model Hub |
|---|---|---|
| 正常运行 | 单点配额 | 80:20 分担，优先消耗预付费 |
| GSU 触达配额 | 业务报错 | 自适应权重渐进切流，PayGo 平滑接管 |
| GSU + PayGo 同时不可用 | 全部超时 | 自动 Fallback 至 GPT-5.5；GPT-5.5 内部继续走完整救援链 |
| GSU 配额恢复 | 需人工切流 | 滑动窗口过期、权重自然回升，自动回归 |
| 切换/扩展模型 | 改代码、重新部署 | 改 YAML，业务无感 |
