## 1 记忆解决什么问题

LLM 本身无状态：context window 是它唯一的工作记忆，session 结束即全部清零。记忆系统要解决的就是**跨 session 的信息传递**——让下一次对话能带着"用户是谁、项目背景是什么、哪些做法已被验证"开工，而不是每次从零开始。

不是所有持久化都算记忆，边界要划清楚：

- **自动记忆 vs 人工维护的文档**。CLAUDE.md、AGENTS.md、项目内文档也承载跨 session 信息，但它们由人控制和审阅；自动记忆由 agent 自行写入，不依赖人工编辑。分界线是**人工控制的有无**。由此有一条设计推论：用户明确表达的要求应该进人工监控范围（文档），而不是只沉在自动记忆里——人看不见的地方不适合放人拍板的规则。
- **会话内持久化不算记忆**。plan 用于对齐实现方案，task/todo 用于跟踪当前进度，它们只服务当前 session。只在本次对话内有用的信息不进记忆（Claude Code 的 system prompt 对这条边界有专门说明）。
- **参数内记忆（parametric memory）不在讨论范围**。把知识写进模型权重（微调、持续学习）是另一条路线，现有 harness 都不走：离线整合（dream）再深入，也只是把记忆重组成更好的文本，无法像人类睡眠那样把经验内化成直觉。本文的"记忆"全部是参数外的——存在 context 或外部存储里的文本与结构化数据。

在此之上，整个领域的设计被三条公理支配：

**公理一：错误记忆有放大效应。** 一条记错的、有偏的、把用户偶然选择当成偏好的记忆，会污染之后的每一个 session——一次犯错可能带来后续上百次负面影响。推论：**写入门槛必须高**，"不记什么"比"记什么"更重要。这解释了为什么成熟方案都把大量篇幅花在负面清单和写入门控上（见 §3「记什么：写入门控」）。

**公理二：记忆是历史快照，不是实时状态。** 写下时为真不等于现在为真：文件会改名、函数会删除、决策会推翻。推论：**召回之后必须验证**，"不信什么"是读管线的核心（读端纪律见 §5.5「读：验证纪律」，存储层解法见 §7「场景线三：时序知识图谱」）。

**公理三：读写都有延迟和成本。** 交互式 agent 对响应延迟敏感，深度的记忆整理（去重、融合、解冲突）又必然耗时。推论：**重整理必须移出主链路**，放到异步、离线的时机去做（见 §4「何时写：三种写入时机」）。这与人需要睡眠来巩固长期记忆是同一个约束的两种表现。

## 2 统一模型与决策结构

任何记忆方案都可以拆成两条管线来分析：

- **写管线** = 生成 + 维护。生成是从对话中筛出值得记的内容；维护是更新、融合、消除冲突、淘汰过期条目。
- **读管线** = 召回 + 使用。召回是把相关记忆找出来；使用包括按记忆调整行为，以及对记忆内容做验证。

这个拆法与学界的归纳一致：记忆机制综述（Zhang et al. 2024，见文末参考文献）把 memory operations 分为 writing、management、reading 三类——写管线覆盖前两类，读管线对应第三类。

难点不在存储本身，而在三处：**生成时的筛选、维护时的融合、召回时的精度**。做过笔记的人都有体会——不停地记并不是好方式，大部分笔记未来价值很低，还会干扰高价值内容的查找。记忆系统面临完全相同的问题。

在两条管线之上，「记什么、存哪里、何时写、怎么读」四个设计问题并不平权。场景是唯一的根变量，但它对四个问题的作用方式分两种，四个问题据此分成两类：

**一类是选型问题——存哪里、怎么读：场景在三个互斥范式里挑一个。** 场景的形态特征（记忆量多大、条目同不同质、召回精度要求多高、要不要关系与时间维度）决定「存哪里」；存与读强耦合、一体两面——存储组织本身就是为某种召回方式设计的（索引文件给 LLM 导航用，embedding 给相似度计算用，图的边给遍历用），选定存法，读法随之确定，不能自由组合。这类问题的特点是三选一、互斥，一个场景只有一个对的答案。

**另一类是通用轴问题——记什么、何时写：没有可挑的范式，所有场景共用同一套框架，场景只负责实例化。** 
何时写：可选的写入时机全集只有三种（会话内实时、会话尾部抽取、离线批量整合，§4），各场景按"延迟预算 × 质量要求"决定实际启用哪几种、把重整理放在哪个时机；
记什么：筛选标准通用——任何场景下都是同样三条：写入门槛默认从严（公理一）、写前自问"未来的 agent 会不会因为这条记忆表现得更好"、答不上来就什么都不写（即 no-op 门控，no-op = 空操作；空操作是合法且被优先采纳的输出，详见 §3.3「负面清单与写入门控」）、用事实/经历/做法三分法查覆盖（§3）。
但只有标准列不出具体清单，"到底记哪些、不记哪些"还要代入两个场景事实才能得出：

- 一是**这个场景里哪些信息在记忆之外另有权威来源可查**——coding 有代码和 git，所以"git 可查的不记"；对话场景的用户偏好无处可查，恰恰要记；
- 二是**这个场景的未来任务需要什么信息**——coding 要构建命令与仓库坑点，销售对话要客户痛点。同一条"用户住在上海"，对话助手场景答得上"未来会更好"所以记，coding 场景答不上所以不记——标准同一份，清单随场景变。

这套两类划分立在一条原理上：**错误只能发生在需要做决定的环节；没有决定可做的环节，不存在"做错"。** 一个设计问题的答案由两部分构成——所有场景共用的公共部分，和每个场景自己拍板的决定部分；公共部分人人一样、无从出错，错误全部集中在决定部分。两类问题的决定环节位置不同，错误形式随之不同：

- 选型问题（存哪里 ⇄ 怎么读）的决定环节是**挑方案**：三种范式是同一问题的三个**互斥**答案——选了文件+索引，就排除了向量库和图谱，不能并用为主存储。互斥的三选一才叫挑方案，挑选可能出错：coding 场景挑了向量库，方案本身就是错的，补救只能推倒换范式。
- 通用轴问题（记什么、何时写）**没有互斥方案可挑，但这不等于没有选择——要分两层看**。体系层只有一套：筛选标准就那三条、写入时机全集就那三种，不存在"另一个学派"可改投，"挑错体系"无从发生。体系内部两个问题又不同：何时写有三个**可叠加、互不排斥的开关**——Claude Code 三个齐备、Mem0 只开每轮尾部抽取、共识做法是并用（§4.2「取舍：快慢双通道」），能同时全开就说明它们不是竞争方案，各开不开由场景事实（延迟预算、写入量、质量要求）推导；记什么连开关都没有——三条标准全部同时生效，场景要给的只是标准里**变量的取值**（"哪些信息别处可查"，coding 取值是代码和 git，对话场景取值是几乎没有）。所以这类问题的全部决定就是把场景事实填进唯一一套框架，唯一的错误形式是填错；修复也不用推倒什么，改配置、重填值即可。

空位填错的两个例子：

- 记什么填错：对话产品照抄 Claude Code 的负面清单，把用户偏好排除在记忆之外。错不在筛选标准本身，而在"哪些信息别处有权威来源可查"这个空位填了 coding 场景的答案——对话场景里用户偏好没有任何别处可查，本该是最核心的记忆内容。
- 何时写填错：海量用户的对话产品启用"每条新事实写入时都调一次 LLM 做融合"。三种写入时机没有哪种本身是错的，错在这个组合没有代入自己场景的写入量——千万用户源源不断产生事实条目，每条多一次 LLM 调用，写入成本无法承受。Mem0 生产版砍掉写入时融合，就是在纠正这个错误（见 §6.1「存与写：抽取 → 入库」）。

这个区分的实际用途是指明排错方向：记忆内容出了问题（记了垃圾、漏了关键偏好），不要去寻找"另一套更好的标准"——不存在第二套，正确动作是回头核对填进去的场景事实；存取效果出了问题，才需要考虑换范式。

附一个自查证据，回应"凭什么说记什么在通用轴上、不在选型链上"：固定场景、切换存储来验证——同一个对话产品，底层无论用向量库还是文件存，"记用户偏好、不记寒暄"这个答案都不变。记什么跟着场景走、不跟着存储走，所以它不在「存 ⇄ 读」那条选型链上，而是和何时写并列成通用轴。

## 3 记什么：写入门控（通用纪律）

**该不该记一条信息，连问两个问题判断：第一问"不记的话，将来还能不能从别处查到最新版？"——查得到就不记；第二问对查不到的信息把关，"未来的 agent 会不会因为这条记忆表现得更好？"——答不上来也不记（即 no-op 门控）。寒暄、一次性询问在别处同样查不到，卡住它们的正是第二问。这两问所有场景共用；但每个场景"能查的别处"不同（coding 有代码和 git，对话场景几乎没有），所以按同一套问题排除出来的负面清单，各场景各有一份。**

先划清这一章「通用」的边界：通用的是**原理和判断准则**——写入门槛必须高（公理一）、"未来的 agent 会不会因此表现更好"这个门控问题、三分法这个分析框架，放到哪条场景线都成立。但把准则套到具体场景，产出的**清单条目**会不同。

清单条目为什么随场景变，要从负面清单的本质说起。负面清单即「不记什么」的禁止项列表——逐条列出哪些类别的信息不允许写入记忆（Claude Code 的完整清单见 §3.3「负面清单与写入门控」），用列禁止项而非列允许项的形式，是因为公理一要求宁可漏记、不可错记，明文封死高风险类别最直接。这份清单不是随手拍的，本质是一条生成规则的展开：**「有更权威、更新鲜来源可查的信息，不进记忆」**。

> 权威指那个来源就是事实本身、不是转述："项目用 React 18"的第一手来源是 package.json，它不是记录了这个事实、它就是这个事实；新鲜指来源随现实自动更新，而记忆是复印件、永远停在写下那一刻（公理二）——项目升级到 19，package.json 自动就是 19，记忆里那条还写着 18。查来源永远拿到当前正确版本，查记忆可能拿到过期版本还被当真，所以这类信息存进记忆只有害处：白占索引、干扰高价值记忆的查找，还埋下召回出错的雷。
>
> 操作化成一个判断题：**"如果不记，将来需要时能不能从别处查到当前正确的版本？"**能 → 不记，现场查（"谁改的文件"查 git blame，"目录结构"直接 ls）；不能 → 记忆就是这条信息的唯一载体，不记就永远丢了（"用户偏好 pnpm"没有任何文件和命令能查出来）——这类才该记。

而"更权威来源"有哪些由场景决定：coding workspace 里代码、git、CLAUDE.md 这批权威源俱全，大量信息被规则排除；对话场景里用户的偏好没有任何别处可查，"用户偏好 X"恰恰是要记的核心、负面清单反而集中在寒暄和一次性询问上。所以读 §3.3「负面清单与写入门控」的 Claude Code 清单时要明白：那是这条生成规则在 coding 场景的实例化——换场景条目要重新推导，但规则是同一条。

### 3.1 内容三分法：审视设计用的检查工具

本章会出现两套分类，职责不同，先说破以免混淆：本节的三分法来自学界，是**给人用的检查工具**——没有任何系统直接实现它，它的用途是拿来对照自己的设计、看三类内容是否各有去处；§3.2「类型系统：生产实现真正用的分类」才是各家系统里实际运行的分类，按写入时要做的操作决策设计，两套分类长得完全不同。两者不是"理论与实现"的推导关系，而是同一块内容空间的两种切法，靠 §3.2 开头的映射表对上。

学界（CoALA 论文，LangChain 官方文档沿用）借人类记忆的分类给出三分法：


| 类型               | 存的是什么 | agent 中的对应物      |
| ---------------- | ----- | ---------------- |
| semantic（语义记忆）   | 事实    | 用户是谁、项目背景、外部资源位置 |
| episodic（情景记忆）   | 经历    | 过去的任务是怎么做成的、完整过程 |
| procedural（程序记忆） | 做法    | 可复用的工作流、技能、验证清单  |


这个分类的价值在于提醒设计者：三类内容的写入时机、存储形态、过期速度都不同，不该塞进同一个袋子。

- 事实——条目化即可；
- 经历——需要保留过程（Codex 的 rollout summary、LangGraph DeepAgents 用 checkpoint 线程回放）；
- 做法——要沉淀成可执行的模板（Codex 的 skills/ 目录；这一思路的源头是 Voyager 的 skill library，把习得的能力存成可复用代码）。

### 3.2 类型系统：生产实现真正用的分类

各家系统给每条记忆打的类型标签，切法与 §3.1「内容三分法」不同，因为设计目标不同：类型系统围绕**写入时要做的操作决策**设计——这条记忆存到哪（私有还是团队）、什么时候存、将来怎么用——而不是围绕内容性质设计。任何系统存下的内容仍然都能用三分法去归类，所以两套分类可以互相映射：


| CoALA 三分法      | Claude Code 落点                                      | Codex 落点                       |
| -------------- | --------------------------------------------------- | ------------------------------ |
| semantic（事实）   | user / project / reference                          | MEMORY.md 手册条目、环境与工作流证据        |
| episodic（经历）   | 类型系统里没有——由 session log 与 transcripts 兜底，Dream 整合时翻阅 | rollout_summaries/（每场对话一份提炼摘要） |
| procedural（做法） | feedback（行为规则）                                      | skills/（可执行的流程模板）              |


这张映射表就是三分法作为检查工具的用法：**拿它照一遍实现，看覆盖与缺口**。Claude Code 的四类集中在事实与规则，"经历"不设类型、靠日志兜底；Codex 三类都有显式落点。自建方案时同理——若三类中有一类完全没有去处，要么是刻意取舍，要么是漏了。

生产实现的共识是**类型化**——每条记忆声明类型，类型决定它的 scope、写入时机和用法。

**Claude Code 分四类**：user（用户角色/偏好/知识水平，始终私有）、feedback（用户对工作方式的指导，默认私有、全项目约定才进团队 scope）、project（进行中的工作/目标/事故，倾向团队 scope）、reference（外部系统资源指针，通常团队 scope）。每类都写明 when_to_save 和 how_to_use。其中三个设计值得细看。

**其一，feedback 同时记录纠正与确认。**

- 纠正指用户否定 agent 的某个做法、要求停止或改变，比如"别在每次回复末尾写总结，我自己会看 diff"；
- 确认指用户认可 agent 的某个不显然的做法，表示以后照此办理，比如 agent 拿不准拆小 PR 还是打包成一个、选了打包后用户说"对，这次合成一个是对的"。

只记录纠正的记忆库里全是"禁区"，没有一条"已验证的做法"——agent 确实不再犯旧错，但用户已经认可的做法也被它当成不确定项反复权衡，行为越来越保守。所以确认要和纠正一样存。

难点在两类信号的可见度不对称：纠正是显式的，用户会打断、会说 "no not that" / "stop doing X"；确认往往很轻，可能只是一句 "yes exactly"，甚至只是对一个不寻常的选择没有提出异议。官方给的确认型例子：

> user: yeah the single bundled PR was the right call here, splitting this one would've just been churn
> assistant: [saves private feedback memory: for refactors in this area, user prefers one bundled PR over many small ones. Confirmed after I chose this approach — a validated judgment call, not a correction]

用户只是随口肯定了"这次打包成一个 PR 是对的"，agent 把它存成一条"已验证的判断"，同类重构下次就不必再纠结拆分粒度。prompt 原文（feedback 类型的 description 与 when_to_save）：

> Record from failure AND success: if you only save corrections, you will avoid past mistakes but drift away from approaches the user has already validated, and may grow overly cautious.
>
> Any time the user corrects your approach ("no not that", "don't", "stop doing X") OR confirms a non-obvious approach worked ("yes exactly", "perfect, keep doing that", accepting an unusual choice without pushback). Corrections are easy to notice; confirmations are quieter — watch for them.

**其二，feedback 与 project 的正文强制三段结构：规则本身 → Why → How to apply。** 只有结论的规则，一到边界情况就失效。看官方例子：

> user: don't mock the database in these tests — we got burned last quarter when mocked tests passed but the prod migration failed
> assistant: [saves team feedback memory: integration tests must hit a real database, not mocks. Reason: prior incident where mock/prod divergence masked a broken migration]

假设只存了结论"测试必须连真实数据库"，将来遇到一个根本连不上数据库的纯逻辑单元测试，agent 只剩两个坏选项：机械死守规则，或凭空给自己豁免。补上 Why 之后边界就能判断了——这条规则的动机是"mock 掩盖过一次损坏的 prod migration"，那么不涉及数据库行为差异的纯逻辑测试，大概率不在规则的本意范围内。How to apply 一行则回答规则在什么时机、什么范围生效。prompt 原文：

> Lead with the rule itself, then a **Why:** line (the reason the user gave — often a past incident or strong preference) and a **How to apply:** line (when/where this guidance kicks in). Knowing *why* lets you judge edge cases instead of blindly following the rule.

project 类的 Why 还有第二个作用：project 记忆过期快，动机能帮未来判断这条记忆是否仍然成立。prompt 原文的说法是 "Project memories decay fast, so the why helps future-you judge whether the memory is still load-bearing."

**其三，project 类保存时把相对日期转成绝对日期。** 相对日期的参照系是"说话那一刻"，而参照系不会随记忆一起保存："周四起合并冻结"在写下的当周意思明确，两周后被召回时，"周四"指向哪一天已经无从判断。所以换算必须发生在写入时，而不是留到召回时去猜。prompt 原文与官方例子：

> Always convert relative dates in user messages to absolute dates when saving (e.g., "Thursday" → "2026-03-05"), so the memory remains interpretable after time passes.
>
> user: we're freezing all non-critical merges after Thursday — mobile team is cutting a release branch
> assistant: [saves team project memory: merge freeze begins 2026-03-05 for mobile release cut. Flag any non-critical PR work scheduled after that date]

**Codex 不分类型分信号强度**，高价值记忆归入四个 bucket：稳定的用户操作偏好、高杠杆的流程知识（来之不易的捷径、失败防护、难发现的仓库事实）、可靠的任务地图与决策触发器（真相在哪、什么信号该转向）、用户环境与工作流的持久证据。核心原则是**为节省未来用户的时间优化**，不只是节省 agent 的时间——一条好记忆能省掉用户未来的重复说明、纠正和打断。推断偏好时以用户消息为主要证据，assistant 的总结只是次要证据。

两条路线的取舍：类型化把"存到哪、何时存、怎么写"编成可执行规则，写入决策程序化、私有与团队的边界清晰，代价是类型没覆盖到的信息容易没有去处；信号分桶以"价值密度"为唯一准绳，天然过滤低价值内容，代价是全靠模型的判断力，约束只能靠更长的 prompt 去补。两者并不互斥——类型决定归属，信号强度决定去留，可以叠加。分工上也各有对口场景：像 Claude Code 那样边对话边记的方式适合类型化，因为写入时要当场决定这条记忆归哪类、放私有还是团队，类型规则给了现成答案；像 Codex 那样事后成批回看对话历史、离线提炼记忆的方式（见 §4.1「三种写入时机」的离线批量整合）适合信号分桶，因为回看时的核心判断只有一个——这条信息价值够不够大、值不值得留。

### 3.3 负面清单与写入门控

公理一（错误记忆放大效应）在实现里的直接体现，就是每家都花重笔墨定义"不记什么"。

**Claude Code 的负面清单**（这份清单是各家中最完整的）：

- 能从当前项目状态推导的：代码模式、约定、架构、文件路径、项目结构；
- git 可查的：历史、近期变更、谁改了什么——`git log` / `git blame` 是权威；
- 调试方案和修复套路——修复已在代码里，commit message 里有上下文；
- 已写进 CLAUDE.md 的内容；
- 临时任务态：进行中的工作、当前对话上下文；
- 敏感数据：API key、凭据，绝不进团队记忆。

关键的一条：**这些排除项在用户明确要求保存时依然适用**。用户让保存一份 PR 列表，正确做法是追问"里面有什么出人意料、不显而易见的"——那才是值得留的部分。

**Codex 的 no-op 门控**把门槛做成了一个显式问题：写入前自问"未来的 agent 是否有理由因为这条记忆表现得更好？"若答案为否——一次性查询、无要点的状态更新、该重新查询的临时事实、常识、没被采纳的头脑风暴——则返回全空字段，不做任何文件更改。**空操作是允许且被优先采纳的**。

> [!warning] 易错点：探索性讨论不是记忆
> 头脑风暴、试探性设计讨论、assistant 的提议，默认都不进记忆——除非有明确证据表明结论被采纳、被实现或被反复强化。把"聊过"当"定了"存下来，正是公理一所警告的污染源。

## 4 何时写：三种写入时机（通用纪律）

「何时写」不是随意挑时机，而是被公理三（读写都有延迟和成本）卡着的：深度整理——融合、解冲突、淘汰——必然耗时，而交互式 agent 的实时回复路径经不起这种等待。由此定下组织原则：**整理越重，越要挪离用户实时等待的主链路**。追加、单点修改这类轻活可以留在交互中；融合、解冲突这类重活必须放到用户不在等的离线时机。

写入时机满打满算只有三种，这份全集对所有范式都相同；按「离主链路的距离」从近到远排列，距离越远，能干的整理越重，质量稳定性也依次递增。

### 4.1 三种写入时机

**会话内实时写入（hot path）**：session 进行中由模型主动调 tool / Write 写入。最快，能即时响应用户"记住这个"；代价是占用 tool 轮次拉长响应，且实时判断的质量最不稳定——低质内容混入风险最高，必须配 §3.3「负面清单与写入门控」那样的闸门。

**会话尾部抽取**：对话 round 结束后，由主链路之外的流程回看本轮对话、抽取记忆。不占当场回复的时间，素材新鲜完整；能做的仍以追加、单点修改为主。对话平台的每轮抽取也属于这一通道：应用侧在回复发出后把该轮消息交给抽取管线异步处理（如 Mem0 的 `add()`），用户不等写入完成。OpenClaw 有一个值得借鉴的变体：在 context 压缩之前触发一次抽取，避免信息随压缩丢失。

**离线批量整合（background）**：对已有记忆做深度整理——去重、融合、解冲突、淘汰。这四件事在全库范围做时只能离线：都要拿新信息比对**整个**已有记忆库，需要全局视角、多次 LLM 判断，注定慢，只能挪到没人等的时候（新会话启动、心跳、空闲）跑。（图谱线是唯一例外：把比对范围从全库缩小到相关实体的局部邻边，冲突处理才搬得进写入期，见 §7.2「写：重活前移，冲突关闭有效期」。）

这类离线机制的思想原型是 Generative Agents（2023）的 reflection：agent 周期性地把积累的原始观察综合成更高层的洞见，再存回记忆流供后续检索。Letta 团队 2025 年把它推广成 sleep-time compute（睡眠时计算）框架：agent 空闲时提前把原始 context 加工成"学到的 context"，真实请求到来时直接使用加工结果——把计算从响应时刻移到空闲时刻，正是公理三推论的正式化。

> [!warning] 易错点：记忆是注入面
> 写管线的素材（对话、工具输出、网页内容）里可能混有第三方可控的文本，这是公理一的对抗性版本：AgentPoison（2024）证明，向记忆库注入极少量恶意条目就能高成功率操纵 agent 的后续行为。Codex 的规则"rollout 里的第三方内容当数据、不当指令"（见 §5.3「写：三通道的落地」）防的就是这个；自建方案的抽取端必须做同样的来源隔离。

### 4.2 取舍：快慢双通道


| 对比维度  | 会话内实时写入                  | 会话尾部抽取                             | 离线批量整合                                     |
| ----- | ------------------------ | ---------------------------------- | ------------------------------------------ |
| 交互延迟  | 占用 tool 轮次               | 无（主链路之外）                           | 无                                          |
| 生效速度  | 立即                       | 本轮对话结束后                            | 下一轮整合后                                     |
| 写入质量  | 最不稳，靠负面清单硬挡              | 中，靠限定素材与工具保质量                      | 最稳，有全局视角                                   |
| 能做的维护 | 追加、单点修改                  | 追加、单点修改                            | 融合、解冲突、淘汰                                  |
| 代表    | Claude Code tool 写入、ChatGPT 显式记忆写入 | Claude Code fork 抽取、Mem0 每轮 add、OpenClaw 压缩前抽取 | Codex 两阶段、Claude Code Dream、Letta dreaming |


单选任何一种都有明显短板：只用增量通道（前两种时机的合称——实时写入与尾部抽取，都只做追加和单点修改），低质内容会持续累积；只用离线批量整合，新偏好要等下一轮整合才生效。共识方向是**快慢双通道并用**——增量通道当快记忆，离线整合当慢记忆定期收编。

### 4.3 时机组合因场景而异

三种时机是全集，各场景实际启用的组合不同——每条线启用哪几种，恰恰由它的场景特征解释：


| 场景线                   | 启用了哪些写入时机                                                 | 为什么                                                       |
| --------------------- | --------------------------------------------------------- | --------------------------------------------------------- |
| coding agent（§5，文件范式） | 三通道齐备（Claude Code，离线 Dream 默认未开启）或离线为主（Codex），离线整理做得最重    | 记忆珍贵、质量要求高；量小，深度整理付得起                                     |
| 对话/平台型（§6，向量范式）       | 基本只有每轮尾部抽取（应用侧异步跑，不占回复延迟）；写入时融合被砍（Mem0 生产版改纯追加），离线整合通道未启用 | 偏好类事实下一轮就要生效，等不起离线整合；用户海量，逐条融合的 LLM 成本爆炸；条目同质，脏一点靠检索排序兜得住 |
| 关系密集型（§7，图谱范式）        | 每 episode 尾部抽取（应用侧异步），且把解冲突等重活前移进这一通道、摄入时做完               | 查询期要亚秒、不调 LLM，只能写入时把维护做完                                  |
|                       |                                                           |                                                           |


所以「怎么写」通用的是时机全集与取舍规律，不通用的是各场景实际启用的组合——具体选择与落地细节，在各自场景线里讲。

## 5 场景线一｜coding agent：文件 + 索引

场景特征：单个项目 workspace，记忆量小（几十到几百条）、彼此异质（规范、偏好、决策、事故各不相同）、召回要求接近确定性（漏一条已纠正的偏好就是重犯旧错）；交互式使用，对延迟敏感。这组特征把这条线推向「文件 + 索引」范式，也是 coding agent 的共识默认。

### 5.1 为什么不用向量 RAG

拆成三条看，每条都对着场景特征：

- **量不大，装得下。** 向量库的存在理由是语料塞不进 context、必须先用相似度粗筛出候选；而单个项目的记忆通常只有几十到几百条，能整个装进 context，或一次 grep 扫完。语料小到装得下时，"先建索引再近似检索"是在为不存在的问题付复杂度。
- **彼此异质，相似度失配。** 向量召回假设"语义相似 ≈ 相关"，这在同质语料上成立，在异质的记忆上不成立——一条记忆该不该生效，取决于任务处在什么状态，而不是它和任务描述的文字像不像（机制展开见 §5.4「读：导航式召回」）。
- **更珍贵，召回要求更高。** 检索文档漏掉一篇还能凑合作答，漏召回一条用户已纠正过的偏好，agent 就会把同一个错再犯一遍。这要求接近确定性的召回，而向量 top-k 只按相似度分数截断，不保证相关条目一定入选。既然量小到付得起全量加载，就没有理由退而接受无保证的召回。

向量召回不是没用，而是适用边界被 RAG 热潮夸大了——它该在的位置是语料大、内容同质、允许模糊召回的场景（即 §6「场景线二：对话与平台型」），这三条 coding agent 记忆场景一条都不满足，它自然退场。

### 5.2 存：索引常驻，条目按需

结构：一个**索引文件常驻 context**，多个**条目文件按需读取**。这就是 progressive disclosure（渐进式披露）——常驻层只花极少 token，深层内容按相关性加载。这一范式的思想源头是 MemGPT（2023）：把 context window 当主存、外部存储当外存，由 agent 自己决定什么信息何时搬进搬出——progressive disclosure 就是这个分层思想落在文件系统上的形态。

- Claude Code：`MEMORY.md` 索引（每条一行指针，200 行 / 25KB 上限）+ 每条记忆独立 md 文件（frontmatter 含 name / description / type）。索引里绝不写记忆正文。私有与团队 scope 各一套目录和索引，团队目录在每次会话开始时同步。组织原则是按主题语义聚合、不按时间顺序堆积——正是 OpenClaw 日记式（按天追加）组织的反面：按天堆积等于把融合难题原样推迟给检索端。
- Codex：三层结构。`memory_summary.md`（常驻 system prompt，要求密集、高导航性）→ `MEMORY.md`（手册，供关键词 grep）→ `rollout_summaries/` 与 `skills/`（深层，仅在被明确指向时打开）。
- Letta 新版 Agent SDK 的 MemFS：git 跟踪的文件系统记忆——专用记忆框架的开创者也转向了文件范式，收敛信号很强。
- LangGraph deepagents：把 `/memories/` 路径路由到持久 Store，agent 用文件 tool（write_file / edit_file）直接读写。

### 5.3 写：三通道的落地

时机选用：这条线是三种写入时机用得最全的——Claude Code 三通道齐备，Codex 以离线整合为主；因为记忆珍贵、质量要求高，量又小到付得起深度整理。

**实时通道与用户显式控制。** 这条通道承接用户对记忆的直接命令。Claude Code 给了用户三个显式开关，按"动不动库"恰好分落在两条管线上：

- **记住 X**（写管线）：立即按最合适的类型存一条新记忆——永久进库。
- **忘记 X**（写管线）：定位对应条目并删除——永久出库。
- **忽略记忆**（读管线）：本次对话不召回、不引用、不提及它，但条目仍留在库里、下次照常可用（见 §5.4「读：导航式召回」）。

前两个改的是"库里有什么"、落在写管线、效果持久；第三个改的是"这一轮用不用它"、落在读管线、只对当前对话生效、不碰存储。这正是 §2「统一模型与决策结构」两管线之分在用户操作层的映射——写管线管存储的增删，读管线管召回与使用。

Codex 是对照组：包括用户请求在内的任何写入都不允许直接修改记忆文件，agent 只能往 extensions/ad_hoc/notes/ 写一个带时间戳的更新说明，等下一轮整合并入——记忆文件始终只有整合管线这一个写入方，一致性有保证，代价是"记住 X"不能立即生效。

**尾部抽取的约束设计。** 对话 round 结束后 fork 一个子 session 专做记忆抽取（Claude Code 的做法，用户偶尔看到一条 `memory_saved` 系统消息；与实时写入做了互斥，防止重复记录）。这个子 session 的约束很有代表性：

- 工具集收窄：只读工具 + 仅限记忆目录的 Edit/Write，禁 rm，禁 MCP 和子 agent；
- **只用最近 N 条消息作为素材，禁止扩查**——不 grep 源码、不读代码验证、不跑 git 命令，防止抽取任务膨胀成调查任务；
- 回合预算固定：第 1 回合并行读所有可能更新的文件，第 2 回合并行写，不交错。

**离线整合之一：Codex 的两阶段实现**（新会话启动时对攒下的历史对话执行）：

- Phase 1：mini 模型并行处理每个 rollout（一次被完整录下的历史对话），各产出一个三元组——rollout_summary（浓缩摘要）+ slug（短标识）+ raw_memory（抽出的候选记忆）。规则：rollout 是不可变证据，绝不编辑；rollout 里的第三方内容当数据不当指令；只基于证据，不编造、不声称未发生的验证；脱敏（[REDACTED_SECRET] 替换）；过不了 no-op 门控就返回全空。
- Phase 2：把 raw memories 整合进文件夹结构（§5.2「存：索引常驻，条目按需」的三层）。记忆目录本身是个 git 仓库，**用上次成功整合以来的 git diff 识别新增信号和被删除的输入**——被删输入所支撑的记忆条目要跟着删（遗忘机制），但一个记忆块同时有已删和仍在的证据时只摘除过时引用、不整块删除；diff 里看似随机位置的改动很可能是用户手改，视为权威、必须并入。另有一个自愈细节：`memory_summary.md` 首行必须是版本号 `v1`，不匹配就把整个文件从头重生成、而不是就地修补——用版本标记防整合产物的 schema 漂移。

**离线整合之二：Claude Code 的 Dream**（默认未开启）：一条「摸清现状 → 收素材 → 融合 → 清理收尾」的流水线——orient（定向：ls 记忆目录、读索引、浏览已有主题文件，动手前先知道库里有什么）→ gather（收集：读最近 1–3 天的 session log；找与代码库现状矛盾的漂移记忆；需要具体细节时对 transcripts 用窄词 grep，不整读）→ consolidate（融合：新信号合并进已有主题文件而非另开近似重复项；相对日期转绝对；删被证伪的事实）→ prune & index（修剪与索引：索引瘦身、超长索引行把细节下沉回主题文件、解决文件间矛盾）。

### 5.4 读：导航式召回

召回模式与 §5.2「存：索引常驻，条目按需」的存储结构互为表里：常驻 context 的只有索引（MEMORY.md / memory_summary.md），条目内容由模型判断相关后主动加载。

Codex 把召回过程进一步做成了**带预算的固定流程**（quick pass）：略读常驻 summary 提取任务相关关键词 → 用关键词 grep MEMORY.md → 仅当 MEMORY.md 明确指向时才打开最多 1–2 个深层文件 → 只有还缺精确命令、报错原文这类硬证据时，才下钻到原始 rollout 记录 → 无相关命中就停止查找、正常开工。全程不超过 4–6 个搜索步骤，避免大范围扫描所有 rollout summaries。**给召回设显式预算**是值得直接抄的设计——召回是主任务前的开销，不设上限就会失控。

触发时机（Claude Code 的规则）：记忆看起来相关、或用户提及既往工作时访问；用户明确说"回忆/检查/记住"时必须访问；用户说忽略记忆时，则既不应用、不引用、也不提及记忆内容。

**召回靠什么判断相关，是这条线选导航式、拒绝相似度检索的根。** 一个隐含前提要先破掉：向量召回默认"文字像 = 相关"，但记忆的相关性不由文字相似度决定，而由任务所处的状态决定。举一条记忆"这个项目跑测试必须用 pnpm、不能用 npm"，当前任务是"修复登录页按钮样式错位"——两段文字语义几乎不沾边，相似度接近零，向量召回必然把它排在 top-k 之外漏掉；可它高度相关，因为 agent 改完样式要跑测试验证，此刻不知道这条就会敲 `npm test`、把用户纠正过的错再犯一遍。这条记忆真正的生效条件是"本次任务会执行测试命令"——一个关于任务状态的**结构性条件**，不是关于文字意思的条件。

结构性条件本质是对任务当前状态某个维度的判定，可归为四类：**在哪**（文件路径、代码语言、所属项目）、**在做什么**（即将调用的工具、用户的任务意图）、**做到哪一步**（会话启动、即将 commit、context 即将压缩等生命周期节点）、**对着什么做**（git 分支、部署环境）。
召回系统要回答的唯一问题是"此刻该把哪几条记忆放进 context"，所以总要有一个判断者来对每条记忆做这个决定。向量检索的判断者是相似度计算，已被上文否定；剩下两条路，区别就在换了谁当判断者——程序代码，或 LLM 自己：

- 条件机器可直接判定的，用**确定性触发**——把生效条件写成程序能机械求值的规则，判定由 harness 的代码完成、不经过模型：Cursor rules 在规则文件头声明 glob（如 `**/*.sql`），agent 碰到路径匹配的文件时，harness 把规则正文注入 context；Claude Code hooks 按工具名配 matcher（如 `Bash`），该工具即将被调用时 hook 触发、把输出注入 context。判定是/否二值，条件为真就百分之百注入——向量召回按相似度分数取 top-k，相关条目可能因排不进前 k 名被漏掉，这里没有分数、召回有保证。这条路属人工配置侧——条件和内容都由人写在配置文件里，不是 agent 自动写入的记忆；
- 条件需要理解语义的，交给 **LLM 读索引自己推理**（即导航式本身）——LLM 能建"改样式 → 要验证 → 要跑命令 → pnpm 这条适用"这样的多步因果链，这是只比对表面语义的 embedding 推不出来的。

导航式召回的取舍：模型沿索引主动多轮查找，精度高、过程可解释、能顺着线索继续深入；代价是消耗 tool 轮次，所以必须配预算封顶（上面的 quick pass）。与之对照的另两条召回路线——检索式见 §6.2「读：检索式召回」，图式见 §7.3「读：三路混合与存储层免验证」。

### 5.5 读：验证纪律（不信什么）

公理二说记忆只保证"写下时为真"：文件会改名、函数会删除、决策会推翻。最彻底的对策是把每条召回的记忆都现场核实一遍，但验证本身要花动作——查文件、grep、git log 都是 tool 调用，条条全验会拖垮响应。省不掉又验不起，所以验证纪律实际由三个问题构成：**哪些记忆必须验、验证动作是什么、验出冲突怎么办。**

**哪些必须验：漂移风险 × 验证成本定档。** 漂移风险指记忆指涉的东西有多容易变——点名具体函数、文件、flag 的记忆风险最高，这类记忆只声称"它在写下时存在"，此后随时可能被改名、删除，甚至从未合并；概括仓库状态的记忆（架构描述、活动日志）同样冻结在写下的时点；用户的稳定偏好则风险低。验证成本指现场核实要花几步——确认文件存在、grep 一个函数名是一步的事，核实一段架构描述要读很多代码。Codex 把两个变量做成决策矩阵：


| 漂移风险 | 验证成本 | 决策                             |
| ---- | ---- | ------------------------------ |
| 高    | 低    | 回答前先验证                         |
| 高    | 高    | 可以从记忆作答，但必须声明来自记忆、可能过时，并提议现场刷新 |
| 低    | 高    | 直接从记忆作答                        |


矩阵之上再压两条硬规则：其一，用户即将根据这条记忆**采取行动**（而非只是询问历史）时，无论落在哪一格都必须先验证——行动会把错误落成现实，后果不再可控；其二是底线，**不得把未验证的记忆事实当作"已确认的现状"呈现**——允许从记忆作答，但必须像矩阵第二行那样声明来源和时效。

**验证动作对准记忆的指涉物。** 点名文件 → 先查文件还在不在；点名函数或 flag → 先 grep 代码；概括近期或当前状态 → 用 `git log` 和读当前代码重新回答，而不是复述快照。

**验出冲突，以当前观察为准。** 召回的记忆与现场看到的不一致时，相信眼前的代码，并顺手更新或删除那条过时记忆——读管线在这里反哺写管线的维护（§2「统一模型与决策结构」）。

**纪律不能只靠模型自觉，harness 要兜底。** Claude Code 给超过 1 天的记忆在注入时自动附加提醒："这是某时刻的观察、不是实时状态，请对照当前代码核实"——把"记忆是快照"这个事实在每次召回时显式摆到模型面前。

> [!warning] 易错点："记忆说 X 存在" ≠ "X 现在存在"
> 这是读管线最容易犯的错。记忆的权威性只覆盖到它写下的那一刻。因此在根据一条记忆采取行动之前，必须先验证它点名的东西如今还在：点名文件就先确认文件存在，点名函数或 flag 就先 grep 代码。这一步不是可做可不做的优化，而是每次必须执行的纪律——跳过验证的错误是无声的：模型把过期记忆当现状说出去时，自己没有任何信号能察觉，只能靠事前强制流程防住。

## 6 场景线二｜对话与平台型：抽取式事实库 + 向量检索

**这一范式恰好站在 §5.1「为什么不用向量 RAG」那三个否定条件的反面。** coding agent 不选向量，是因为记忆量小、彼此异质、召回要求接近确定性；而对话型产品（个人助手、客服系统）三条全反过来：用户成千上万、每人积累一堆"偏好深色主题""对花生过敏""住在上海"式的条目，总量大到塞不进 context、必须先粗筛；条目又高度同质——同质意味着"语义相似 ≈ 相关"这个假设重新成立，余弦相似度重新是够用的相关性代理。三个条件一翻转，向量检索就从 coding 场景里的劣势变成这里对路的选择。

### 6.1 存与写：抽取 → 入库

机制的前两步就是这条线的存与写：

- **抽取**：原始对话冗长、口语化、夹着大量无记忆价值的寒暄，不能直接入库。先用 LLM 把它压成离散的事实条目（"用户是素食主义者"），干两件事：滤掉噪声，并把口语表述归一化成彼此可比、适合 embedding 的原子事实。"抽取式"三个字即由此而来。写入时机上，这条线基本只用「每轮尾部抽取」这一个通道：每轮对话结束后，应用侧把该轮消息交给独立的抽取管线处理（Mem0 的 `add()` 即此形态，支持异步执行）。回复先发给用户、抽取在旁路跑，写入不占响应延迟——这里常说的「实时」指时效（当轮就抽、下一轮即可检索到），不是把写入挤进回复链路。真正占 tool 轮次的模型现场写入，这条线只留给用户明确说"记住这个"的低频场景（ChatGPT 的显式记忆写入）。（时机取舍见 §4.3「时机组合因场景而异」）
- **入库**：每条事实转成 embedding 向量存进向量库，按 user_id / agent_id 等维度做租户隔离，各人的记忆互不串扰。

写端最核心的决策是「新事实和已有记忆的关系怎么处理」，Mem0 从论文版到生产版给了两个相反答案：

> [!note] 深入：写入时融合 vs 纯追加——脏活放写入端还是读取端
> 新事实进来时、如何处理它与已有记忆的关系，是这类系统的核心决策。Mem0 论文版与生产版给了两个相反的答案。
>
> **论文版——写入时融合。** 每抽到一条候选事实，先向量检索捞出库里语义相近的旧记忆，再由 LLM 判断二者关系、四选一执行：
>
> - **ADD**：全新信息、库里没有 → 存入；
> - **UPDATE**：旧记忆的补充或修正（旧「住上海」遇到新「住北京」）→ 改写那条；
> - **DELETE**：新信息让旧的彻底作废 → 删除旧条目；
> - **NOOP**：库里已有、无新增（又说了一次「我吃素」）→ 什么都不做。
>
> 好处是库始终干净：「住哪」永远只留最新一条，不会新旧并存打架。代价是**每进一条事实就多调一次 LLM**（一次检索 + 一次判断），海量对话下写入路径凭空多出成千上万次调用，又慢又贵；且融合判断本身会误合、误删，是新引入的出错点。
>
> **生产版——纯追加。** 砍掉融合，新事实直接转向量存入，不比对、不判断。「住上海」「住北京」两条同时躺在库里，写入极快极省，但库变脏——冗余与矛盾没人在写入时收拾，全推给**查询端的排序**：取 top-k 时靠相似度加新近度，让更新、更相关的那条盖过旧的。矛盾没被真正解决，只是指望排序时新的能顶上来。
>
> 本质是「脏活放写入端还是读取端」的经典权衡：融合在写入时一次做完（贵、库干净），纯追加甩给读取时的排序（省、库脏）。Mem0 生产版的判定是——在其量级上，「库保持干净」这点收益抵不过写入时融合的延迟与复杂度。这不是融合没价值，而是它的性价比在大规模下翻了负，也正是 §2「统一模型与决策结构」所说"维护时的融合是最难、也最先被工程放弃的一环"的活证据。

### 6.2 读：检索式召回

查询转成向量，算相似度取 top-k，把最相关的几条拼进 context。召回全程不调 LLM，靠向量近邻搜索，条目规模再大也是亚线性——这正是它扛得住海量用户的原因。

取舍：不占 tool 轮次、对条目规模不敏感；代价是精度受 embedding 上限约束，召回错了模型也无从察觉——与 §5.4「读：导航式召回」里"LLM 能推多步因果链"恰成对照。这条路线的理论原型是 Generative Agents（2023）的三因子检索打分——相关性、新近度、重要性加权求和——和 MemoryBank（2023）按 Ebbinghaus 遗忘曲线做的时间衰减；OpenClaw 的衰减与召回加权是它们的工程化。

### 6.3 代表实现

- **Mem0**：代表实现。`infer=True` 时 LLM 从对话抽取关键事实、决策、偏好；用 user_id / agent_id / run_id 做 scope 隔离；写端取舍见上面的融合 vs 纯追加 callout。
- **ChatGPT memory**：消费级代表。两条腿——saved memories（用户或模型显式存下的事实条目）+ 引用历史对话（隐式检索过往 session）；用户能在设置界面逐条查看、编辑、删除，把记忆控制权交还用户是消费级产品的信任设计。
- **OpenClaw 默认方案**：每日日记（SQLite 索引）+ 关键词/向量混合检索 + 时间衰减 + 被召回过的片段加权。原文列为负面案例：挖掘整合阶段（light / REM / deep 三段）甚至不调用 LLM，只做文本切分和相似度计算——"大的阶段设计还算常见，但具体实现方式完全不是 LLM 时代的工作"（详评见 §8.3「逐方案评价」）。

## 7 场景线三｜关系密集型：时序知识图谱

**它补上 §6「场景线二」平铺事实库解决不了的两件事：事实之间的关系，和事实的时效。** 平铺库把每条事实存成孤立条目，条目间的关联丢失——问"某人的经理负责的项目现在进展如何"，相似度检索只能捞回文字像的零散条目，拼不出这条跨越多个实体的关系链。而事实还会随时间失效："在 Acme 就职"跳槽后就不再为真，平铺库要么删掉（丢了历史）、要么留着（和新事实自相矛盾）。知识图谱把这两块一起补上。典型场景：CRM、客服、合规审计——事实互相关联、需要回答"何时为真"。

### 7.1 存：三层结构与双时态

结构以 Zep 的 Graphiti 为代表，分三层：

- **episodes**：原始摄入数据，不可变的证据层——每次进来的对话或文档原样留档，后续所有抽取都能回溯到它，相当于"事实的出处"。
- **entities（节点）与 facts（边）**：从 episodes 抽出实体当节点、实体间的关系当边，每条边是一个三元组（主-谓-宾，如"Alice—就职于—Acme"）。关系被显式建成边、成了一等公民，才能沿边跳转做多跳推理。
- **双时态窗口**：每条 fact 挂两条独立的时间轴——一条记它在**现实世界**成立/失效的时间（valid_at / invalid_at），一条记**系统**何时得知/推翻它的时间。前者支撑"某个历史时点什么为真"的查询，后者留下"系统当时以为什么为真"的审计痕迹。这两条轴一起，才是"时序"二字的完整含义。

> [!note] 深入：双时态用一条时间线看懂——现实何时为真 vs 系统何时知道
> 「双时态」难在两种时间听着像一回事、其实正交：一条记事实在**现实**里成立/失效（valid_at / invalid_at），一条记**系统**何时建档/推翻它（created_at / expired_at）。现实发生的时刻和系统得知的时刻几乎从不重合，这就是它存在的理由。
>
> 以「Alice 在哪就职」为例。现实真相：2020-01-01 入职 Acme，2024-06-01 转投 Globex。但系统直到 2024-07-15 的一次对话才听说跳槽，这一刻它新建 Globex 那条、并把 Acme 那条标记为不再当前。库里两条边、四对时间戳：
>
>
> | fact             | valid_at（现实成立） | invalid_at（现实失效） | created_at（系统建档） | expired_at（系统推翻） |
> | ---------------- | -------------- | ---------------- | ---------------- | ---------------- |
> | Alice—就职于—Acme   | 2020-01-01     | **2024-06-01**   | 2020 年摄入         | **2024-07-15**   |
> | Alice—就职于—Globex | 2024-06-01     | （尚未失效）           | **2024-07-15**   | （尚未推翻）           |
>
>
> 关键在 Acme 那条：现实里 6-01 就失效，系统却到 7-15 才推翻它——这道 6-01 与 7-15 的缝隙，正是双时态要精确刻画的东西。
>
> 两条轴支撑三类查询：①「Alice 现在在哪」走世界时间、取当前有效 → Globex；②「Alice 2023 年在哪」走世界时间、取历史时点 → Acme；③「2024-07-01 系统以为她在哪」走系统时间 → Acme，且这答案是对的——问的不是现实，而是系统当时的认知。
>
> 第三类是纯审计维度，也是第二条轴的全部价值：agent 若在 7-10 基于「Alice 在 Acme」做了个事后看错的决策，只有系统时间能回放出"那天全库都还这么以为"，从而分清是判断错、还是信息滞后。这条审计能力也解释了下面"关闭有效期而非删除"为何必要——删除会把"系统曾经相信过什么"一起抹掉。

### 7.2 写：重活前移，冲突关闭有效期

时机选用：按三种写入时机对号，这条线走的是**会话尾部抽取**——应用侧每收到一个 episode 就交给摄入管线异步处理，不占回复链路，与 Mem0 的每轮 add 同通道。特殊之处不在时机而在活的重量：别家在这个通道只做追加和单点修改，这条线把通常归离线通道的重活也前移进来——实体抽取、关系判定、冲突处理都在摄入 episode 的那一刻做完。付得起的原因是比对范围只有相关实体的局部邻边、不是全库（§4.1「三种写入时机」的例外条款）；被迫这么做的原因见 §4.3「时机组合因场景而异」：查询期要亚秒、不调 LLM，维护只能在写入时做完。

冲突处理是这套结构的点睛之笔：新信息和旧事实矛盾时，**不删除旧事实，而是给它盖上 invalid_at、关闭有效期**。于是"就职于 Acme"既不消失也不和新的"就职于 Globex"打架——查"现在"返回后者，查"去年"仍能返回前者。这是公理二（记忆是快照）在存储层的另一种解法：§5.5「读：验证纪律」的文件范式靠读端每次验证来对抗过期，图谱范式则把时效直接刻进数据，让查询天然只返回当前为真的事实。

### 7.3 读：三路混合与存储层免验证

检索走三路混合：embedding 语义 + BM25 关键词 + 图遍历（按图距离重排），能做关系推理和时点过滤。关键在**查询期完全不调 LLM**：昂贵的实体抽取、关系判定都发生在写入期，查询期只剩确定性的图遍历加向量近邻，所以能亚秒返回——代价花在建设期而不是查询期。

验证责任放在哪一端，是图谱范式与文件范式的真实分岔：文件范式把验证做成读端纪律（§5.5「读：验证纪律」那套规则），灵活、不依赖存储层能力，但每次使用都要付出验证动作；Graphiti 把"不信什么"做进存储层——矛盾发生时自动关闭旧事实的有效期，查询天然只返回当前为真的事实，读端免验证，代价是把正确性全部押在写入端实体抽取的可靠性上。加上图数据库与实体建模的工程成本，这是三种范式里引入门槛最高的。

### 7.4 同类与认知科学对应物

OpenClaw 的 memory-wiki（默认关闭）也属此类，显式维护实体和概念对象。

图当索引的思路有认知科学对应物：HippoRAG（2024）按海马体索引理论建模——海马体不存内容、只存内容之间的关联，内容本身存在新皮层；对应过来，知识图谱扮演海马体（只存实体与关联），原文片段扮演新皮层（存内容），检索沿关联跳转找到内容。

## 8 横向对比与方案地图

### 8.1 范式对比与选型


| 对比维度  | 文件 + 索引                       | 事实库 + 向量检索          | 时序知识图谱         |
| ----- | ----------------------------- | ------------------- | -------------- |
| 适合的内容 | 少量、异质、高价值                     | 大量、同质的事实条目          | 关系密集的事实        |
| 召回方式  | 模型沿索引主动导航                     | 相似度排序，被动注入          | 语义 + 关键词 + 图遍历 |
| 时间维度  | 正文里写绝对日期                      | 时间衰减降权              | 存储层双时态窗口       |
| 冲突处理  | 离线整合时改写或删除                    | 基本不处理，检索排序兜底        | 自动关闭旧事实有效期     |
| 引入成本  | 最低（纯文本文件）                     | 中（向量库）              | 高（图数据库 + 实体抽取） |
| 代表    | Claude Code、Codex、Letta MemFS | Mem0、ChatGPT memory | Zep/Graphiti   |


选型结论（就是 §2「统一模型与决策结构」那条"场景是根变量"的具体化）：

- 内容量小、非同质、质量要求高 → 文件 + 索引（coding agent 场景直接选它）。
- 用户量大、事实条目同质、需要多租户隔离 → 抽取式事实库 + 向量检索。
- 事实之间关系密集、需要回答"何时为真" → 时序知识图谱。

### 8.3 逐方案评价

各维度内部的路线对比已沉在对应章节：类型化对信号分桶见 §3.2「类型系统：生产实现真正用的分类」，写入时机的取舍见 §4.2「取舍：快慢双通道」，三种存储范式见 §8.1「范式对比与选型」，三条召回路线分别见各场景线的读端小节（§5.4 / §6.2 / §7.3）。本节只看整机——每个方案作为整体，优势在哪、局限在哪、什么场景选它。

#### Claude Code

- 优势：三种写入机制齐备，快慢兼顾，是目前最完整的实现；负面清单与验证纪律各家最全，prompt 人工调教痕迹重、信息密度高，值得逐条揣摩"这条限制为什么要加"。
- 局限：实时写入通道仍可能混入低质记忆，只能靠清单硬挡；Dream 默认未开启，长期整合效果未经大规模验证；记忆存在 $HOME 而非项目目录，换机器需要迁移。
- 选它：交互式 coding agent 场景的默认参考实现，自建方案先抄它的 baseline 再改。

#### Codex / OpenAI Agents SDK

- 优势：离线批量整合 + 严格 no-op 门控，写入质量最稳；git diff 遗忘机制是各家中唯一系统化的遗忘设计；三层渐进披露配上召回预算，读端成本可控。
- 局限：学习慢——新偏好要等下一轮整合才生效；用户说"记住这个"也只能先落到 ad hoc notes 等待整合，即时性差；实现细节量过大，prompt 超长而信息密度不高。
- 选它：会话量大、能接受滞后学习、把写入质量放在第一位的场景。

#### Letta（MemGPT → MemFS）

- 优势："agent 自己管理 context"的理论框架最完整；记忆作为独立服务可编程、可自托管、可跨应用共享。
- 局限：早期 core memory blocks 范式已被自家新版放弃、转向 MemFS，处在迁移期；作为外部服务引入，集成成本高于 harness 内置方案。
- 选它：需要把记忆做成独立服务、多个应用共享同一份 agent 状态时。

#### Mem0

- 优势：最轻量，API 简单，user_id / agent_id / run_id 多租户隔离现成，几行代码嵌进既有应用。
- 局限：写入纯追加、没有融合与冲突消除，记忆质量全靠检索排序兜底；事实条目粒度，承载不了流程性知识（procedural）。
- 选它：对话型产品记用户偏好和事实，条目量大且同质的场景。

#### Zep / Graphiti

- 优势：唯一把"何时为真"做进存储层的方案——冲突自动关闭旧事实有效期，读端免去验证负担；三路混合检索亚秒返回，不占交互延迟。
- 局限：依赖图数据库和抽取质量，对模型结构化输出的可靠性要求高；实体建模成本高，用在 coding agent 场景属于杀鸡用牛刀。
- 选它：事实关系密集、需要时点查询的业务（CRM、客服、合规审计）。

#### LangGraph / deepagents

- 优势：抽象干净（Store + namespace + 文件路由），hot path 还是 background 自由选择，组装自由度最高。
- 局限：只给机制不给策略——负面清单、写入门控、验证纪律全部要自己设计，等于把 §3、§4 的通用纪律和各场景线的落地功课全留给使用者。
- 选它：自建 agent 且想完全掌控记忆策略时，当积木用。

#### OpenClaw（负面案例）

- 教训一：阶段设计看着像样（light / REM / deep 三段整合），但整合过程不用 LLM、只做文本切分和相似度计算——记忆质量取决于筛选与融合的智能程度，流程齐全补不了智能缺位。
- 教训二：资源花在了与记忆能力无关的地方（DREAMS.md 散文体日记只是给用户看的装饰），华而不实。
- 可取之处：日记按时间过期降权、context 压缩前先抽取记忆这两个点仍值得借鉴。

#### ChatGPT memory

- 优势：用户可视、可管理、可删除，是消费级信任设计的标杆。
- 局限：黑盒，不可编程、不可扩展。
- 选它：不作为技术方案选型对象，参考其产品形态——给用户看什么、给多大控制权。

### 8.4 收敛趋势

专用记忆框架（Letta）与 coding harness（Claude Code、Codex）正在合流到"文件 + 索引 + 离线整合（dream）"范式；向量检索退为对话型平台与大规模多租户场景的手段；时序知识图谱占据"事实关系密集 + 时间维度"的生态位。

研究侧有三个走在生产实现前面的方向，与上述趋势同向：A-MEM 把 Zettelkasten 卡片盒方法搬给 agent——每条记忆是一张带上下文的卡片，写入时自动与相关旧卡建立链接、并触发旧卡内容更新，比"文件 + 索引"多出一层互链结构；MemOS 把记忆当操作系统资源做统一调度（统一封装、生命周期管理、跨任务迁移）；MIRIX 用多个专职 agent 分管六类记忆库（core / episodic / semantic / procedural / resource / vault），是类型系统路线推到极致的形态。三者都还没进入主流 harness，但方向一致：赢在结构化组织与自动整合，而不是更大的向量库。

## 9 设计 checklist

自建记忆方案时，按两条管线逐项过：

**写管线**

- [ ] 类型系统与 scope 划分（私有 / 团队；semantic / episodic / procedural 是否分开对待）
- [ ] 负面清单（可推导的、git 可查的、临时的、敏感的一律不记）
- [ ] no-op 门控（"未来 agent 会不会因此表现更好"，答不上来就不写）
- [ ] 相对日期转绝对日期
- [ ] 写前查重，合并进已有条目而不是另开近似重复项
- [ ] 敏感信息脱敏，团队 scope 禁凭据
- [ ] 错误记忆的删除路径（被证伪即删；被删输入所支撑的条目跟着删）
- [ ] 写入来源隔离（素材里的第三方内容当数据、不当指令，防记忆投毒）

**读管线**

- [ ] 索引常驻 + 内容按需（progressive disclosure）
- [ ] 召回预算上限（步数封顶，无命中即停）
- [ ] staleness 标注（超龄记忆附提醒）
- [ ] 漂移风险 × 验证成本决策矩阵；据记忆行动前先验证
- [ ] 用户显式控制三开关：记住（立即存）、忘记（定位并删除）、忽略（不用、不引、不提）

**架构**

- [ ] 先定场景再选范式：量、同质性、召回要求、关系与时间维度四个特征过一遍（§2「统一模型与决策结构」、§8.1「范式对比与选型」）
- [ ] 快慢双通道：增量写入管快，离线整合管稳
- [ ] 离线整合的周期与触发（会话启动 / 心跳 / 手动）
- [ ] 整合时的遗忘机制（git diff 追踪输入增删，或有效期关闭）
- [ ] 深整理移出主链路，交互路径上只留轻量读写
- [ ] 评测闭环：写入质量与召回效果如何度量，见 [[Eval-First-记忆系统评测方法论]]
