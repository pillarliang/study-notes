# Agent Harness 模块剖面图

> 同样一套 harness，[[23-Agent-架构图详解-七节点与三层]] 沿「时间顺序」走七步循环，本笔记沿「空间分工」把它切成九个模块。每个模块固定回答三件事：**它是什么角色 / 它在循环里的相对位置 / 它对外暴露什么接口**。
>
> 对照源图：`harness.drawio · Page-16`。

---

## 0. 全局定位

### 0.1 harness 是什么

> **harness 是一个围绕大模型构建的运行时系统。它持有状态、把用户目标转换成多轮模型请求、允许模型调用工具、接收工具结果、再决定下一步。**

模型自己是无状态的，只会"输入一段文本，输出一段文本"。要让模型在真实世界里持续工作，就需要一层壳子负责：

- 维护对话历史与项目上下文
- 把模型输出里的工具请求落实成本地副作用
- 把本地副作用的结果再翻译回模型能看懂的形式
- 跨进程持久化整段会话
- 把过程广播给 UI 与外部观察者
- 防止上下文窗口爆栈

把这六件事拆开来，就是九个模块。

### 0.3 两条骨架

读图前先钉住两条骨架，后续模块都挂在它们上。

#### 骨架一 · 三种节奏

harness 内部的事不是匀速进行的，按发生频率分档：

| 节奏 | 发生时机 | 典型模块 |
| --- | --- | --- |
| **一次性 / 触发式** | 执行体重建、配置变更 | 1. 会话装配层 |
| **跨执行体** | 打开 / 压缩 / 分支切换 | 2. Session Manager |
| **每轮一次** | 每发一次 prompt 跑一遍 | 3. Context Manager、4. Model Adapter |
| **每个工具调用一次** | 模型每请求一次工具 | 6. Sandbox 工具执行边界 |
| **持续广播 / 消费** | 整段会话期间 | 7. stream event、8. Subscriber |
| **prompt 结束后一次** | 主循环退出之后 | 9. 压缩检查与三道防线 |

把模块挂错节奏档位，是阅读 harness 最常见的误解来源。

#### 骨架二 · 主循环边界

page-16 用绿色注释框圈出了主循环回路：

```text
读取 AgentMessage[] → 形成本轮上下文
  → 模型适配层（请求/响应规整）
  → 助手消息
  → 决策：包含工具调用？
     ├── 否 → 直接回复文本（退出循环）
     └── 是 → 工具执行边界（查找/校验/钩子/执行）
         → 工具结果 → 回写 AgentMessage[] → 继续下一轮
```

**不在主循环里**的事同样关键，但与循环异步：

- 用户输入接收（在会话容器、提问入口里）
- 事件订阅消费（外围消费者，主循环只负责广播）
- 会话调度切换（更上层的会话调度层）
- 会话树持久化（订阅者职责，主循环不知道磁盘）

## 1. 模块 · 会话装配层

### 1.1 角色

**一次性把 system prompt 拼好，供后续整段对话共用。**

整段会话期间 system prompt 通常不变，因此装配只在「执行体被重建」或「skill / 工具集发生变化」时跑，不进入主循环。

### 三种触发条件

| 触发 | 含义 |
| --- | --- |
| 整个执行体重建，首次装配 | 新开会话、恢复会话、分支切换 |
| 工具集变更 | 用户启停某些工具时重算工具清单 |
| 扩展运行时新增 skill 路径 | 扩展在跑过程中向资源目录注册新 skill |

### 装配三步

```text
扫描资源目录            ┌─→ 加载 skill 索引（只解析 frontmatter）
项目目录 / 用户配置目录  ┤
扩展提供                └─→ 加载项目长期规则（AGENTS.md / CLAUDE.md，读全文）
                                          │
                                          ▼
                                  拼装 system prompt 文本
                                          │
                                          ▼
                              写入「system prompt 快照」（执行体内）
```

两条加载路径的差异：

| 维度 | skill 索引 | 项目长期规则 |
| --- | --- | --- |
| 来源 | 资源目录递归扫 | 项目根固定文件名 |
| 读取深度 | 只读 frontmatter | 读全文 |
| 嵌入位置 | system prompt 的 `<available_skills>` 块 | system prompt 的 `<project_context>` 块 |
| 后续如何被用 | 模型看到目录后按需 read 正文 | 直接随每轮上下文一起送进模型 |

> **为什么 skill 只读 frontmatter**：skill 数量可能上百，正文加起来塞不进窗口。frontmatter 像目录页，让模型按需要 read 正文，本身只占少量 token。

### 与主循环的关系

装配层不在主循环内。产出物——**system prompt 快照**——存到执行体的内存里，由 Context Manager 每轮取用。整段会话不重复装配，除非触发条件再次满足。

## 2. 模块 · Session Manager

### 2.1 角色

**JsonL 持久化与会话树的总管。负责把磁盘上的事实序列变成 `Agent.state.messages: AgentMessage[]`，再把它写回磁盘。**

Session Manager 是主循环之外的组件，但产物 `AgentMessage[]`（即 `Agent.state.messages`，下文简称 `AgentMessage[]`）是主循环的命根子。

> `AgentMessage` 是 Kernel 层定义的**超集类型**，role 不止 user / assistant / toolResult 三种，还允许 Runtime 注册自定义类型（bashExecution、branchSummary、compactionSummary 等）。它在送给模型前会经 `convertToLlm` 塌缩成 pi-ai 层的 `Message` —— 详见 [[23-Agent-架构图详解-七节点与三层]] 「边界一」。

### 2.2 四个 buildSessionContext 触发时机

page-16 把 Session Manager 的入口画成一条横向流水线，列出 4 个会触发「重建 AgentMessage[] 」的事件：

```text
┌─新建/恢复会话─┐    ┌──压缩完成──┐      ┌──分支切换──┐
│ 销毁旧执行体  │    │ 执行体保留 │      │ 销毁旧执行体│
│ 新建执行体    │   │           │       │ 新建执行体  │
└───────┬──────┘   └─────┬─────┘    └──────┬─────┘
        │                │                 │
        ▼                ▼                 ▼
   ┌────────────────────────────────────────────────┐
   │  重建 AgentMessage[]：沿父指针回溯会话树 → 消息序列         │
   └──────────────────────┬─────────────────────────┘
                          ▼
                ┌──────────────────────┐
                │  JsonL → AgentMessage[]  │
                └──────────────────────┘
```

四个触发口的差异：

| 触发口 | 执行体处理 | 触发动机 |
| --- | --- | --- |
| 新建会话 | 新建执行体 | 进程冷启或开新对话 |
| 恢复会话 | 销毁旧的，新建一个 | 切到历史会话 |
| 压缩完成 | **保留当前执行体** | 摘要刚生成，需要把数组替换为「摘要 + 最近若干消息」 |
| 分支切换 | 销毁旧的，新建一个 | 用户切到会话树的另一个分支 |

> **「压缩完成」是唯一不销毁执行体的触发口**。其余三种都意味着「换一个执行体」，因此装配层会被重跑。

### 2.3 会话树为什么是树

JsonL 不是单纯的追加列表，而是带父指针的森林。任何一条助手消息都可以作为父节点派生出新分支——分支切换其实就是换一条父指针链。重建 AgentMessage[] 的核心动作是**沿父指针从叶子节点回溯到根**，把这条链上的消息按顺序展开。

### 2.4 与会话装配层的协同

会话装配层负责 system prompt，Session Manager 负责 AgentMessage[] 。**两个原料都备齐，Context Manager 才能产出 context。**

新执行体的启动顺序固定是：

1. 装配层先跑一遍 → system prompt 快照就位
2. Session Manager 沿父指针回溯会话树 → AgentMessage[] 就位
3. Context Manager 把两者合并 → 主循环可以开跑

## 3. 模块 · Context Manager

### 3.1 角色

**每轮调模型前，把「system prompt 快照」与「 AgentMessage[] 」合并成一份 context，递交给模型适配层。**

Context Manager 是主循环里第一个被触发的组件，负责回答一个问题：**这次调模型，要送哪些消息进去？**

### 3.2 内部结构

```text
┌─────────── Context Manager ───────────┐
│                                       │
│  ① system prompt 快照（执行体内）       │
│         │                              │
│         ├──────► context（每轮组装产物） │
│         │                              │
│  ② Agent.state.messages: AgentMessage[]│
│     in-memory transcript               │
│                                       │
└───────────────────────────────────────┘
```

两个原料的差别：

| 原料 | 谁写入 | 何时变 |
| --- | --- | --- |
| system prompt 快照 | 会话装配层 | 装配触发时变 |
| AgentMessage[] | 用户输入 / 助手回复 / 工具结果 / JsonL 重建 | 每轮多次变 |

### 3.3 输入与输出

**输入边**有三条路径会改写 AgentMessage[]：

1. **用户输入** —— 来自会话容器、提问入口
2. **工具结果消息** —— 来自工具执行边界的回写
3. **JsonL → AgentMessage[]** —— 来自 Session Manager 的重建

**输出边**只有一条：递交给模型适配层。

### 3.4 关键约束

> 用户每次提问不重建 AgentMessage[]，用户消息直接走「消息完结事件双写」追加到数组里。

正常对话中 AgentMessage[] 是**增量追加**，不是每轮重新构造。只有「新建会话 / 恢复会话 / 压缩完成 / 分支切换」这四个时机才会让 Session Manager 出面把 JsonL 翻成新数组。

## 4. 模块 · Model Adapter

### 4.1 角色

**主循环唯一与远端模型打交道的位置。把内部 context 翻译成模型 API 能听懂的格式，再把流式响应翻译回内部事件。**

### 4.2 内部结构

```text
context
   │
   ▼
┌──────────────── Model Adapter ────────────────┐
│                                               │
│  请求归一化 ──► Provider request              │
│                       │                       │
│                       ▼                       │
│                ┌─Model Provider─┐             │
│                │ OpenAI         │             │
│                │ Gemini         │             │
│                │ Anthropic      │             │
│                └────────────────┘             │
│                       │                       │
│                       ▼                       │
│                响应归一化 ───► AssistantMessage │
└───────────────────────────────────────────────┘
                       │
                       ▼
                  广播到 stream event
```

### 为什么必须有这一层

不同供应商在六件事上写法都不同：

| 维度 | 差异举例 |
| --- | --- |
| 工具格式 | OpenAI 用 `tools` + `function`，Anthropic 用 `tools` + `input_schema` |
| 流式协议 | SSE / NDJSON / 自定义协议 |
| 错误结构 | 有的塞 HTTP 状态码，有的塞 payload 字段 |
| thinking 块表达 | Anthropic 用 `thinking` 块，OpenAI 用 reasoning effort |
| StopReason 命名 | `stop` vs `end_turn` vs `length` vs `max_tokens` |
| Usage 计算 | 是否区分 cache hit、是否区分 reasoning tokens |

Adapter 的任务就是把这六件事统一成 harness 内部的标准形态。代价是每加一家供应商写一份适配器；收益是上层全程不感知供应商差异——**换模型只换字符串**。

### 输出双口径

Adapter 的输出同时走两条路：

1. **结构化输出**：完整的 AssistantMessage，递给「包含工具调用」决策菱形
2. **流式输出**：广播到 stream event 节点，被订阅者消费

两条不是顺序关系，而是并发的——UI 可以边流式渲染边等最终判定。

### 一条铁律

> **错误编码进 stream event，不抛异常。**

无论模型 API 返回什么错误，Adapter 都把它转成一个 `error` 类型的事件塞进流里。上游因此永远能用同一种方式消费流，不需要写 try/catch。

## 5. 模块 · AssistantMessage · content[]

### 5.1 角色

**模型一次输出的结构化容器。决定主循环下一步是「退出」还是「调工具」。**

AssistantMessage 自身是数据结构，但它在 page-16 上被单独标出来，因为它是主循环里**唯一的分叉点**所依赖的载体。

### 5.2 内部结构

```text
AssistantMessage
└── content[]   ← 数组，按顺序排列两类块，可同时存在
    ├── TextContent       ← 文本回复
    └── ToolCallContent   ← 工具调用请求
```

关键规则：

- `content[]` 数组按顺序排列两类块，**可同时存在**
- 文本只用于回复，**只有工具调用块才进入 Sandbox**

### 触发的分叉

主循环靠一个菱形节点读取 AssistantMessage：

```text
                   ┌─ NO ──► 返回文本回复 ──► 等待下次提问 ──► 压缩检查
   含工具调用？───┤
                   └─ YES ─► 工具执行边界
```

判定逻辑只问一件事：content 数组里有没有任何一块是工具调用类型？这一行决定了 agent 和 chatbot 的本质差异——agent 能根据模型自己的判断决定**继续干活还是停下**，而不是固定问一句答一句。

### NO 分支三连节点

走 NO 分支后，page-16 画了三个连续节点：

```text
返回文本回复 ──► 等待下次提问 ──► 压缩检查
```

| 节点 | 含义 |
| --- | --- |
| 返回文本回复 | 把 TextContent 广播给订阅者（UI 渲染、JsonL 落盘等） |
| 等待下次提问 | 主循环暂停，等下一次用户提问 |
| 压缩检查 | 在等待之前**先做一次压缩判定**（详见模块 9） |

注意压缩检查是夹在「文本回复完」和「等用户输入」之间的，不是循环内的逐轮检查。

## 6. 模块 · Sandbox 工具执行边界

### 6.1 角色

**所有模型请求的工具调用必须在这个边界内完成。它是 harness 唯一允许产生本地副作用的位置。**

Sandbox 不是物理沙箱，而是**逻辑边界**——通过六道关卡保证每次工具调用都被守门、校验、可拦截、可观测。

### 六步流水线

```text
┌────────── Sandbox 工具执行边界 ───────────┐
│                                          │
│  ① 按名称查工具                            │
│              │                            │
│              ▼                            │
│  ② 用 schema 校验入参                      │
│              │                            │
│              ▼                            │
│  ③ 前置钩子                                │
│              │                            │
│              ▼                            │
│  ④ 调用工具本体                            │
│              │                            │
│              ▼                            │
│  ⑤ 后置钩子                                │
│              │                            │
│              ▼                            │
│  ⑥ 封装为工具结果消息                       │
│                                          │
└──────────────────────────────────────────┘
                  │
                  ▼
        回写 AgentMessage[]（广播事件 + 进入下一轮）
```

每一步的职责与归属：

| 步骤 | 归属 | 职责 | 失败处理 |
| --- | --- | --- | --- |
| ① 按名称查工具 | Kernel | 在 ToolRegistry 查表 | 找不到 → 直接造一个错误结果 |
| ② 用 schema 校验入参 | Kernel | 类型与字段校验 | 不合法 → 直接造一个错误结果 |
| ③ 前置钩子 | Runtime | 拦截 / 改写 / 二次确认 | 可返回 allow / block / rewrite / confirm |
| ④ 调用工具本体 | 本地副作用 | 真正动手 | 抛错也包装成错误结果 |
| ⑤ 后置钩子 | Runtime | 截断 / 脱敏 / 强制终止 | 可设置 terminate=true 强制结束 |
| ⑥ 封装为工具结果消息 | Kernel | 拼成消息回写 | —— |

### 三个不变量

工具边界贯穿三条铁律，page-16 没有显式标注，但它们是边界设计的根本动机：

1. **失败必转结果，进程绝不崩**：工具不存在、参数非法、执行报错——一律包成 `isError: true` 的工具结果消息
2. **回写顺序严格按模型原始顺序**：一次返回 N 个工具调用，结果按 1..N 顺序回写，跑得快的不能插队
3. **回写完才能进下一轮**：AgentMessage[] 拿到工具结果后，主循环才回到 Context Manager 重新组装

### 一个常见误解

`Tool` 类型不带执行能力。pi-ai 层的 Tool 只描述工具给模型看，**不负责执行**；只有 Kernel 层的 `AgentTool` 才带 `execute` 方法。执行是 Kernel 域的职责，pi-ai 不碰本地副作用。

## 7. 模块 · stream event

### 7.1 角色

**广播主循环内部的关键时刻，让外部消费方与内部消费方都能旁听。**

stream event 不参与决策，但所有「能看到 agent 在干什么」的能力都建立在它之上。

### 三类事件分组

page-16 把 stream event 节点内部分成三档：

| 事件层级 | 何时广播 | 典型用途 |
| --- | --- | --- |
| **模型流式输出** | 模型流式回包的每个 delta | UI 打字机效果 |
| **工具执行期间** | Sandbox 六步流水线的关键节点 | 显示「正在 read 文件」之类的中间态 |
| **整轮 / 整段 / 压缩** | 一轮结束、整段对话结束、压缩前后 | JsonL 落盘、压缩订阅者唤醒 |

### 广播来源

page-16 上有两条线汇入 stream event：

1. **Model Adapter → stream event**：流式事件源头之一
2. **工具调用 → stream event**：副作用过程中的状态广播

两条线最终在 stream event 节点汇合，再向下游订阅者广播。

### 累积快照设计

模型流式输出的每个 delta 都携带 `partial: AssistantMessage` 累积快照——UI 可以直接渲染这个快照而不用自己拼增量。这是一个 UI 友好的设计：消费者不需要维护增量合并逻辑。

## 8. 模块 · Subscriber

### 8.1 角色

**stream event 的消费方。决定事件流被「拿来做什么」。**

订阅者本身不影响主循环，但许多关键能力（UI 渲染、磁盘持久化、自动压缩）都挂在订阅者上。

### 两类订阅者

```text
stream event ───┬──► 外部消费方（UI）
                │
                └──► 内部消费方（压缩）
```

| 类型 | 职责 | 与主循环的关系 |
| --- | --- | --- |
| **外部消费方** | UI 渲染、日志、远程 RPC 推送 | 完全异步，掉一个事件不影响循环 |
| **内部消费方** | 监听整段对话结束事件，判定是否要压缩 | 可能反向触发会话装配层与 Session Manager |

### 一个常被忽视的设计原则

> **消息是事实来源，事件只是投影。**

事件流可以丢、可以重发、可以延迟；但 AgentMessage[] 与 JsonL 是真理。订阅者全部基于「事件流」工作，意味着它们的失败永远不会污染会话事实。这也是为什么持久化的是消息而不是事件——事件流可以从消息重放出来，消息却没法从事件流反推。

## 9. 模块 · 压缩检查与三道防线

### 9.1 角色

**让上下文窗口不爆栈的兜底系统。**

压缩检查只是这套兜底系统的一道菱形决策，但它背后挂着三道防线，page-16 用三块带颜色的注释块单独画出来。

### 9.2 压缩检查的触发条件

```text
                ┌── 信号 1（主动预防）──┐
                │ 模型回包带 token 账单 │
                │ 累计 > 窗口 − 预留    │
压缩检查 ◄──────┤                       │
                │ 信号 2（被动兜底）     │
                │ 模型返回上下文溢出     │
                └────────────────────────┘
```

Pi 默认预留 16384 token。两种信号任一触发都立即进入压缩。

### 9.3 关键 · 检测位置不是「每轮 turn 后」

```text
┌─整轮 prompt 跑完─┐
│ 主循环退出       │ ──► 压缩检查
│ (agent_end)      │     用最后一条助手消息做检查
└──────────────────┘
```

为什么不每个 turn 都查？

> 主循环中途有连续依赖（说 → 调工具 → 说 → 调工具）。打断会乱节奏，必须等模型自己说完才查。

一次 prompt 可能产生多条助手消息（每个 turn 一条），中途的助手消息只是被覆盖式记下，**只用最后一条做一次检查**。

### 9.4 三道防线对比

| 防线 | 位置 | 时机 | 机制 |
| --- | --- | --- | --- |
| **① 工具结果强制截断** | 工具自己 | 工具返回前 | 50KB / 2000 行硬上限，附 `[Truncated: ...]` 提示 |
| **② prompt 内累积检查** | —— | —— | **故意缺位**（主循环连续依赖不能打断） |
| **③ overflow 自动重试** | 会话容器 | prompt 结束后 | 删错误助手 + 压缩 + 重试 |

#### 防线 ① · 工具截断

每次工具结果上限：**50KB 或 2000 行**，先到先截，附 `[Truncated: ...]` 提示让模型知道。
覆盖范围：

- 读文件：大文件 head 截断
- grep：单行最多 500 字符
- bash：输出尾部截断

所以单次工具结果不会爆窗口。

#### 防线 ② · 故意不存在

主循环中途不做 token 累积检查，因为连续依赖（说 → 调工具 → 说 → 调工具）不能被打断。

后果：「工具调用风暴」是真实的崩溃路径——同一个 prompt 里调一连串工具，每个都没超上限，但累加起来撑爆窗口。靠防线 ③ 兜底。

#### 防线 ③ · overflow 自动重试

触发场景：一次 prompt 内多个工具结果累积撑爆窗口。

处理流程：

```text
模型返回上下文溢出错误 → 异常结束
        │
        ▼
会话容器识别为 overflow 类型
        │
        ▼
删掉那条错误助手消息（不进下次上下文）
        │
        ▼
触发压缩
        │
        ▼
★ 自动重试同一个 prompt
```

限制：**只允许 1 次自动重试**。第二次还 overflow → 放弃，提示用户切大窗口模型。

副作用：因为防线 ② 不存在，工具调用风暴最终靠防线 ③ 兜底，用户能感受到 1 次重试延迟。

## 10. 全景串联

### 10.1 模块汇总速查

| 模块 | 节奏档位 | 输入 | 产物 | 与主循环的位置 |
| --- | --- | --- | --- | --- |
| 1. 会话装配层 | 一次性 / 触发式 | 资源目录 + AGENTS.md | system prompt 快照 | 循环外 |
| 2. Session Manager | 跨执行体 | JsonL 会话树 | AgentMessage[] | 循环外 |
| 3. Context Manager | 每轮一次 | 快照 + AgentMessage[] | 本轮 context | 循环内首站 |
| 4. Model Adapter | 每轮一次 | context | AssistantMessage + 流式事件 | 循环内 |
| 5. AssistantMessage | 每轮一次 | 模型响应 | 分叉决策载体 | 循环内分叉点 |
| 6. Sandbox 工具执行边界 | 每个工具调用一次 | 工具调用块 | 工具结果消息 | 循环内分支 |
| 7. stream event | 持续广播 | 主循环关键时刻 | 三档事件 | 循环边 |
| 8. Subscriber | 持续消费 | 事件流 | UI / 压缩反应 | 循环外 |
| 9. 压缩检查与三道防线 | prompt 结束后 | token 账单 / 溢出错误 | 触发压缩 / 重试 | 循环外兜底 |

### 10.2 四种走法验证理解

| 走法 | 路径 | 检验点 |
| --- | --- | --- |
| 冷启动 | 装配层 → Session Manager → Context Manager → 主循环 | 装配在前，重建 AgentMessage[] 在后 |
| 正常一轮对话 | Context Manager → Model Adapter → AssistantMessage → 退出 / Sandbox → 回写 → 下一轮 | 主循环边界清晰 |
| 工具调用风暴 | Context Manager → Model Adapter → Sandbox × N → overflow → 防线 ③ 重试 | 防线 ② 缺位的代价 |
| 用户主动压缩 | 用户触发 → 压缩订阅者 → Session Manager → 重建 AgentMessage[]（执行体保留） | 唯一不重建执行体的触发口 |

### 10.3 harness 设计的几条普遍原则

把九个模块的设计动机抽掉具体细节，剩下五条贯穿全图的原则：

1. **节奏分离**：一次性、每轮、每工具、持续——每件事只在它该跑的节奏档位跑，错档就出 bug。
2. **错误转结果**：任何子组件失败都包装成可序列化的消息，不抛异常。整个主循环因此永远能跑下去。
3. **消息是事实，事件是投影**：持久化消息、广播事件、订阅者基于事件工作。事件丢了能从消息重放，反之不行。
4. **副作用收敛到唯一边界**：所有外部影响（读写文件、调远端、跑命令）必须经过 Sandbox 六步流水线，便于守门、观测、回放。
5. **模型边界归一化**：Model Adapter 把供应商差异吸收掉，上层全程不感知用的是哪家模型。

### 10.4 看别的 harness 实现时该问的清单

把这张图作为模板，看 Claude Code、Codex、LangGraph 等任意 harness 时按下面问题对照即可定位：

| 问题 | 对应模块 |
| --- | --- |
| system prompt 怎么拼？skill / 项目规则从哪来？ | 1. 会话装配层 |
| 会话持久化形态是什么？是数组还是树？ | 2. Session Manager |
| AgentMessage[] 是每轮重建还是增量追加？ | 3. Context Manager |
| 加新模型供应商需要改几个文件？ | 4. Model Adapter |
| 模型一次输出能不能同时包含文本和工具调用？ | 5. AssistantMessage |
| 工具执行有几道钩子？失败怎么处理？ | 6. Sandbox |
| 事件流分几档？UI 拿到的是增量还是累积快照？ | 7. stream event |
| 压缩什么时候触发？由谁触发？ | 8. Subscriber + 9. 压缩检查 |
| 上下文窗口爆栈有几道防线？ | 9. 三道防线 |

九个问题问完，对一个 harness 实现的理解就到位了。读图就是在脑子里把这九块拼起来——每一块在哪个节奏档位、对外暴露什么接口、与上下游怎么咬合。所有 agent harness 本质都在解同一个问题——**怎么让一个无状态的模型在有状态的世界里持续工作**——只是切层方式略有不同。
