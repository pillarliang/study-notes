# pi 的设计艺术 · 决策精要

> [!summary] 本文定位
> 本文提炼《pi 的设计艺术：构建生产级 Coding Agent 的架构决策》中的**设计判断**，不再逐章复制源码机制。具体运行过程由 02–05 负责；功能用法由 `official-doc/` 负责。

书稿编号沿用原结构：第 1–32 章之间额外插入“第 26b 章 SDK”，所以 26b 不是漏号，27 之后也不顺延。

---

## 1. 全书只回答一个问题

> **怎样让最内层协议足够稳定，同时允许产品层持续增加 provider、工具、会话、UI 和扩展能力？**

Pi 的答案不是“整个系统都做小”，而是把变化频率不同的责任分开：

```text
pi-ai
  统一模型、认证、消息与流式协议
        ↓
pi-agent-core 的 loop-engine 主链
  agentLoop + Agent + tool pipeline + AgentEvent
        ↓
pi-coding-agent
  session、compaction、资源、具体工具、Extension、产品策略
        ↓
Interactive / Print / JSON / RPC / SDK
  不同宿主复用同一运行对象
```

“轻量”指内层职责克制，不代表 provider、产品工具和 TUI 的总代码量很小。

## 2. 八条设计纪律

### 2.1 按独立使用者分层，而不是按文件类型分层

一个能力只有在使用者和发布节奏真正独立时，才值得成为单独 package。包边界同时成为依赖边界：内层不导入产品层，TUI 也不反向进入 agent core。

**收益**：可单独测试、可渐进采用、多个宿主共享内核。

**代价**：装配代码更多，跨层调试路径更长。

### 2.2 把稳定协议留在内层，把产品策略推到外层

内层稳定的是：统一事件、消息契约、tool 接口、turn 控制流和状态归约。容易因产品而变的 retry、compaction、prompt、UI、权限体验与资源发现留在 `pi-coding-agent` 或宿主。

判断一个能力是否进入 core，可问：

1. 所有宿主是否必须以同一种方式实现？
2. 不统一是否会破坏消息或事件契约？
3. 是否存在多种同样合理的产品策略？

只有前两问为“是”、第三问为“否”时，才更像内核职责。

### 2.3 控制流与长期状态分离

`agentLoop` 推进一次 run；`Agent` 保存跨 run 的内存状态；`AgentSession` 连接产品策略；`SessionManager` 保存长期事实。

这种分离让循环容易测试，也让 session、retry 和 compaction 可以独立演化。代价是调用方必须正确完成装配，不能指望 loop 自动替产品做决定。

### 2.4 依赖显式传入，不依赖进程级隐式状态

cwd、models、tools、resource loader、session manager 与 stream function 尽量由调用方显式提供。这样同一进程才能同时承载多个工作目录、多个 session 或测试替身。

这不是单纯的“纯函数洁癖”，而是 SDK 嵌入、RPC、多会话和子 agent 组合的共同前提。

### 2.5 provider 与 API 协议是两个维度

同一家 provider 可以暴露多种 API；同一种兼容 API 也可以被多家 provider 复用。Pi 因而把模型身份、认证、目录与 streaming 装配在 provider 上，把 wire protocol 差异放在 API 实现中。

上层只面对统一的 `Model`、`Context`、`Message` 与事件流。代价是 compat 配置会持续增长，而且可用性仍需运行时验证。

### 2.6 只有具有增量价值的过程才值得事件流

文本、thinking 与 tool call 会逐步到达，UI 和控制流需要观察过程，所以模型调用使用流式事件。最终结果型能力若没有有意义的中间态，Promise 反而更简单。

因此“全部 API 都流式化”不是目标；**让消费者在需要的粒度上观察状态变化**才是目标。

### 2.7 约束是给模型的保护栏

结构化 `read`、`edit`、`grep` 和 `find` 比万能 bash 更容易验证，也更容易给出可恢复错误。工具 schema、精确编辑、输出截断与三阶段管道都服务同一个目的：把模型可能犯错的空间缩小到可处理范围。

代价是工具数量增多、模型需要选择工具，且无法覆盖所有 shell 场景，所以 bash 仍作为后备能力存在。

### 2.8 能用资源或 Extension 表达的能力，不进入 loop 分支

- Skill 用 Markdown 描述工作方法，只影响模型行为；
- Extension 用同进程代码注册工具、命令、事件处理和 UI；
- Pi package 负责分发资源；
- provider 负责模型协议与认证；
- SDK/RPC 负责宿主集成。

能力外置减少 core 分支，但也把治理、安全和兼容责任交给产品作者。Extension 同进程运行，不是安全隔离。

## 3. 关键取舍及其代价

### 极简 loop-engine

得到可测试、可嵌入、可替换的循环；代价是产品层必须自己承担 session、恢复与安全体验。

### 多 provider 统一层

得到模型切换与跨宿主复用；代价是 provider compat、认证和消息转换成为长期维护面。

### JSONL 会话树

得到 append-only、可读、易分支和易恢复；代价是文件会增长，加载通常要重建索引，跨进程并发写需要额外治理。

### 同进程 Extension

得到低开销和深度集成；代价是 Extension 继承主进程权限，加载信任不能替代运行隔离。

### 专用工具优先

得到低错误率、可预测输出和结构化恢复；代价是工具选择负担与更多接口维护。

### 多宿主共享 `AgentSession`

得到 Interactive、RPC 和 SDK 行为一致；代价是 `AgentSession` 成为产品复杂度的汇聚点。

## 6. 适用边界

Pi 的架构更适合：

- 需要深度定制 agent 行为；
- 同时支持多个 provider；
- 需要 CLI、RPC、SDK 等多种宿主；
- 团队愿意理解 TypeScript 类型与分层装配；
- 项目周期足以回收架构投入。

它不一定适合：

- 只需快速上线的简单 chatbot；
- 原生复杂多 agent 编排是核心诉求；
- 团队不使用 Node/TypeScript；
- 极低延迟比可替换性更重要；
- 希望框架默认提供完整 sandbox、审批、审计和企业治理。
