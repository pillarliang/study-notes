# Pi 笔记写作规范

> 目标：让没有读过源码的人只靠正文理解 Pi 的实际运行机制，并能回到指定源码基线核验结论。

---

## 1. 只保留服务于当前问题的内容

1. **一节只回答一个问题。** 标题说明问题，第一段直接给结论；出现第二个独立问题时另起小节。
2. **每段必须有明确目的。** 删除一句话后，如果不影响本段结论、运行过程或必要边界，这句话就应删除。
3. **限制条件紧邻被修正的结论。** 必须说明它在防止什么误解；不要为了显得严谨而突然引入另一套机制。
4. **不要混入无关比较对象。** 例如解释 `beforeToolCall` 时，不要为了声明“它不是 sandbox”而展开 sandbox；只有主题本身要比较二者时才另节说明。
5. **一个结论只完整解释一次。** 其他位置用一句引用或 wikilink 指回原节，不在总览、正文、warning 和结尾重复。
6. **罕见边界不占主线。** 不改变核心心智模型的字段清单、实现细节和低频分支，移到源码入口或独立笔记。
7. **正文优先回答 why、what、who、when。** how 只保留到足以解释职责、时机和可观察结果；数组怎样复制、对象是否同一引用、内部容器怎样更新等实现手法，不得抢占机制主线。
8. **实现细节必须通过准入测试。** 只有当它会改变读者对公开行为的预测、避免高频误判，或是后文推理不可缺少的前提时才进入正文；否则只留源码位置。
9. **相邻章节必须形成问题链。** 新一节开头说明它承接上一节的哪个结论、继续回答什么问题；如果一节可以任意移动而不影响推演，应补足关系、调整顺序，或降为独立补充。

---

## 2. 用最短路径建立理解

机制章节按以下顺序写：

```text
承接上一节提出的问题
  → 结论（why / what）
  → 一个最小但完整的运行实例
  → 谁在什么时机拿到什么数据（who / when）
  → 发生什么、结果交给谁
  → 只保留影响可观察行为的必要 how
  → 源码对应
```

- **术语首次出现时就地定义。** 标题、图和代码中的首次出现也算；定义前不要只堆缩写、状态标签或源码名。
- **概念先于源码标识符。** 先讲目的和动作，再给函数名、类型名、路径和行号。删除反引号中的名称后，正文仍应可读。
- **例子最小但必须真实。** 一个例子只证明当前结论，不顺带解释其他主题。
- **运行时对象使用完整结构。** 不用 `read(...)`、`toolResult(...)` 等伪函数记法冒充真实数据。若只展示字段值，明确写成“下面只是 `arguments` 字段的值”。
- **官方英文术语保持一致。** `tool call`、`loop turn`、`agent run`、`context`、`steering`、`follow-up`、`terminate` 等保留原文，并在当前语境中定义。

---

## 3. 新术语与 API 必须完成引入闭环

“术语首次出现时就地定义”不仅是措辞要求，还是正文的依赖顺序：**任一句话都只能依赖前文已经建立的概念。** 结论本身正确，但读者必须跳到后文才能知道其中某个词的含义，仍属于解释失败。

### 3.1 首次出现按读者看到的位置计算

- 标题、摘要、目录、流程图、代码示例、表格、callout 和结论中的出现都算首次出现，不能因为后文有专节解释就省略前面的定义。
- 总览需要提前使用后文术语时，按以下顺序处理：优先改成普通中文；无法替换时在原处加一句最小定义；术语较多时先增加“阅读前先区分”小节。
- wikilink 和源码路径用于展开与核验，不能代替当前段落理解主线所需的定义。
- 不在同一句结论中并列一个已解释对象和一个未解释对象，例如先写“`prompt()` 与 `waitForIdle()` 都会等待”，再到后文解释 `waitForIdle()`。

### 3.2 先说明它是哪一类东西

首次引入代码标识符时，先指出它属于哪一类，避免把事件、状态、方法和内部字段混在一起：

- **方法**：谁提供、谁在什么情况下调用、调用后做什么；
- **事件**：谁发出、何时发出、接收者能据此判断什么；
- **状态**：哪个对象处于该状态、进入和离开的条件是什么；
- **回调**：谁注册、谁调用、返回或完成会影响什么；
- **类型或数据结构**：它描述什么运行时数据，数据由谁产生、交给谁；
- **内部字段**：只有影响公开行为时才进入正文，并先解释它代表的运行事实。

仅翻译名称不算定义。例如“`waitForIdle()` 就是等待空闲”仍然缺少：它属于哪个对象、等待当前还是未来运行、对象已空闲时会怎样，以及等待完成后调用者可以确认什么。

### 3.3 异步 API 还要解释完成语义

首次介绍返回 Promise 的方法或会被 `await` 的回调时，至少说明：

1. 开始等待的条件；
2. Promise 在哪个可观察时点完成；
3. 已经满足条件时是否立即完成；
4. 等待的是调用时的当前工作，还是也包含未来启动的工作；
5. 它与相邻 API 的关系，避免读者误以为必须重复等待。

### 3.4 定义后立刻给一个可预测结果

定义的验收标准不是“读者大概知道中文意思”，而是读者能预测一个最小场景：

```text
调用或事件发生前是什么状态
  → 谁触发什么动作
  → 哪个时点算完成
  → 完成后下一行代码或下一个组件能做什么
```

如果还不能预测，就继续补充输入、时机或结果；如果需要展开另一套机制才能解释，应改用普通中文并把该 API 移到真正需要它的小节。

## 4. 机制说明必须闭合

以下清单只用于已经通过“实现细节准入测试”的核心机制。低频分支、内部字段和不改变公开行为判断的影响需要核验，但不要求在正文逐项展开；**核验过不等于必须写出来。**

介绍一个 stage、callback、状态或消息转换时，正文应能回答：

1. 为什么需要它，什么条件会触发；
2. 触发时已经发生了什么；
3. 输入是什么，由谁产生；
4. 当前步骤执行什么；
5. 输出是什么，下一个读取者是谁；
6. 哪些分支会跳过；
7. 对文件、进程、网络和消息数组有什么可观察影响。

补充规则：

- `prepared`、`immediate`、`kind` 等状态首次出现时，展示判别字段、实际数据和后续去向。
- 参数或消息转换至少给一组具体 before/after，并指出改变与保留的字段。
- exception、error result、policy block、cancellation、skip 和 `terminate` 不得混称为“失败”或“停止”；要说明是否执行 tool、是否进入后处理、产生哪些事件和消息，以及是否继续本批或下一次 LLM 请求。
- 描述顺序时，明确被排序的对象、完成判断、观察者和批次范围。事件顺序与消息顺序不同时，用同一组快慢调用列出两条序列。
- callback 先讲它解决的决策问题和返回结果，再讲函数名与参数；参数要解释成信息，不能照抄签名。

---

## 5. 不混淆框架保证与外部能力

- **框架保证**只包括该模块能控制的调用时机、验证、状态转换和消息处理。
- **自定义 callback** 是应用程序注入的任意代码。框架尚未调用 tool 的 `execute`，不等于 callback 没有访问文件、网络或进程；这项边界只在前文可能造成相反理解时说明一次。
- **policy 与 sandbox 分开。** policy 决定是否允许继续调用；sandbox 由运行环境限制代码实际能访问的资源。只有主题需要比较时才同时介绍。
- **假设示例不能冒充默认行为。** 写成“应用程序可以配置”，不能写成 Pi CLI、SDK 或框架自动提供。
- **对象可变性必须核验。** callback 收到的是副本还是原对象、修改后是否重验、返回 `undefined` 时修改是否保留，都以源码为准。
- **类型、实现和运行时对象分开。** `type`/`interface` 只规定形状；具体实现执行工作；运行时变量保存当前选中的实现。

---

## 6. 精确性、语言与证据

- 源码笔记开头声明仓库和 commit hash；默认行为、控制流和行号都以该 commit 为准。
- 源码名、路径和行号只用于查证，放在解释之后；行号写入前逐条核验。
- 只记录当前基线上的最终行为，不保留探索、bugfix、废弃方案或无关版本演进。
- 边界方向写具体：端点是否包含、索引属于哪一侧、事件与消息谁先发生。
- 使用自然、简洁的书面中文，不用“你、我、我们”，不用比喻或“上层、宿主、通道”等空泛词承担定义。
- 图只有在比文字更短时才使用；流程用箭头，层级用缩进。超过五节不强制画全局图。
- callout 只保留会造成实际误判的高频边界；交叉引用写成 `[[笔记名]] §章节「标题」`，并只链接直接相关内容。

---

## 7. 完稿自查

完稿检查至少分三遍，不能只检查事实和源码行号：

1. **标识符遍**：从标题开始记录每个英文术语、反引号标识符、事件名和状态名的第一次出现，检查该处是否已经定义；
2. **读者遍**：暂时不看源码，逐段确认读者只凭前文能否回答“这是什么、谁触发、何时完成、结果给谁”；
3. **回归遍**：新增摘要、流程图或前置段落后重新从头检查，因为新增内容可能把某个术语的“首次出现”提前。

机械搜索可以找出标识符首次出现的位置，但不能判断解释是否完整；最终仍要用下面的问题逐项验收：

1. 每节能否用一句话说出唯一目的？
2. 是否有无关背景、突然出现的免责声明、比较对象或重复结论？有则删除。
3. 从标题开始逐行检查时，每个英文术语、反引号标识符和状态名是否都只依赖此前已经定义的概念？摘要、图和代码中的首次出现是否也完成了定义？
4. 新方法是否说明所属对象、调用者、调用时机和效果？新事件是否说明发送者、时点和含义？新状态是否说明主体及进入、离开条件？
5. 异步方法或 callback 是否说明 Promise 的完成时点、已满足条件时的行为、等待范围及与相邻 API 的关系？
6. 例子是否最小、真实且结构完整？读者能否据此预测下一步可观察结果？
7. stage、callback、状态分支和转换是否说明输入、动作、输出与跳过路径？
8. 框架保证、可选 policy、任意 callback 和 sandbox 是否被混写？
9. 错误、取消、顺序和 `terminate` 是否说明实际控制流后果？
10. 源码基线、默认行为和行号是否已经核验？
11. 是否存在以 `slice()`、对象引用、内部 `Set`、字段清单或罕见 fallback 为主体的段落？若不影响公开行为判断，删除或移到源码入口。
12. 从头顺读时，每节是否都由上一节自然提出？是否出现“事实正确但不知道为什么此处要讲”或“必须先读后文才能读懂当前句”的割裂段落？
13. 只看目录时，章节是否构成读者问题与因果链，而不是类、方法、私有字段或事件名清单？内部标识符若不是理解对象，只作为证据出现。

本规范需要调整时直接编辑此文件，不另建重复规范。
