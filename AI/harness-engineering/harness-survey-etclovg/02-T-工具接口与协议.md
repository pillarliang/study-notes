# Tool 层：工具接口与协议（Tool Interface & Protocol）

> ETCLOVG 七层中的第二层。定义 agent 如何**发现、描述、调用**自身能力。回到 [[00-Survey总览-ETCLOVG七层框架]] 查七层全景。

相关已有笔记：

- MCP 协议入门：[[MCP_学习笔记]]
- Pi 的 tool 用法实践：[[09-Skills-按需技能]]


## 1. 这一层为什么难——一个根本性的张力

### 1.1 核心矛盾

工具层不是"接口设计问题"，而是一个**决策质量问题**伪装成接口设计问题。原因在于 LLM 的工作方式：模型在每一步都要看到所有可用工具的描述（schema、用途、参数），然后选一个。

由此产生一个无法回避的二元张力：


| 目标         | 工程动机        | 副作用             |
| ---------- | ----------- | --------------- |
| **扩大能力覆盖** | agent 能做更多事 | tool menu 变长    |
| **保护决策质量** | 选对工具、参数对    | tool menu 必须保持小 |


**为什么 menu 大会伤害决策？** 三个机制叠加：

1. **Prompt entropy 上升**——每个工具的 description 都进了上下文。100 个工具 × 平均 200 token = 20K token 用在"还没开始干活"上
2. **Planning branching 爆炸**——在每个决策点 LLM 都要评估"这 100 个里哪个对"，错选率随 menu 大小近似线性上升
3. **Token overhead 推高成本和延迟**——每轮对话都要重复加载这堆 schema

生产部署的工程经验反复证实：**过大的 tool menu 会降低可靠性、增加 token 开销、放大 planning error**。这不是优化问题，是结构性约束。

### 1.2 这一层切成四个子方向

综述把 Tool 层的研究空间分成四块。它们不是平行罗列，而是**沿一条因果链**展开——前一块定义"调用怎么发生"，后一块解决"调用规模化后崩在哪"：

```mermaid
flowchart LR
    PROTO[协议与接口标准<br/>调用机制如何标准化] --> DISC[描述/发现/选择<br/>哪个工具该被选中]
    DISC --> TRAIN[训练与集成<br/>模型如何学会用工具]
    TRAIN --> SCALE[可扩展与会话管理<br/>长时间运行下不崩]
```

## 2. Protocol & Interface Standards（协议与接口标准）

### 2.1 关键 reframe：按"集成边界"分类，而不是按厂商

#### 传统分类法的失效

工程师初看这块经常困惑：MCP、A2A、function calling、OpenAPI、AGENTS.md……它们到底是竞争关系还是互补关系？是不是新的取代旧的？

按厂商或时间线分类（"OpenAI 的 function calling 出现在 X 年，Anthropic 的 MCP 出现在 Y 年"）会得出"它们在争夺同一块地"的错误结论。

#### 原理：每个标准跨越一条不同的"集成边界"

正确的分类轴是**这个标准在系统的哪两个组件之间架桥**——这就是 *integration boundary*。

四种边界：


| 边界                              | 含义                     | 类比               |
| ------------------------------- | ---------------------- | ---------------- |
| **Model ↔ Function**            | 把模型自然语言输出结构化成可执行函数调用   | 编译器前端：自然语言 → AST |
| **Agent ↔ External Capability** | agent 运行时与工具/资源解耦，按需发现 | 操作系统的系统调用接口      |
| **Agent ↔ Agent**               | 跨进程的 agent 委派与协作       | 微服务之间的 RPC       |
| **Agent ↔ Repo / Environment**  | 把工具用法和约束写进版本控制         | README 之于人类开发者   |


#### 推论：常被对立的标准其实职责不重叠

按这个轴看，MCP vs A2A、function calling vs OpenAPI 这些"看似在打架"的对比都站不住——**它们各占一条边界**，互补而非竞争。

#### 可视化：协议的拓扑位置

```
┌─────────────── agent ────────────────┐
│                                      │
│   LLM ──function calling── runtime   │
│                               │      │
└───────────────────────────────┼──────┘
                                │
                ┌───────┬───────┼──────────┐
                │       │       │          │
               MCP   OpenAPI   A2A    AGENTS.md
                │       │       │          │
                ▼       ▼       ▼          ▼
              工具    REST     其他      项目
                     服务    agent      仓库
```

这张图揭示一个容易被忽视的事实：**协议分内外两层，而 runtime 是唯一同时贴着两层的组件**。

- **内层（横线，agent 内部）**：function calling 连接 LLM 与 runtime——LLM 生成决策，runtime 执行
- **外层（竖线，agent 跨边界）**：MCP/OpenAPI 接外部工具、A2A 接其他 agent、AGENTS.md 接项目仓库

关键推论：**外层四个标准全部从 runtime 引出，而不是从 LLM 引出**。LLM 永远不直接说 MCP / OpenAPI / A2A——它只吐出抽象的 function call，由 runtime 翻译成具体请求（MCP 的 JSON-RPC、OpenAPI 的 HTTP、A2A 的消息、对 AGENTS.md 的文件读取）。所以图里竖线必须挂在 runtime 上，而不是从框底正中垂下：runtime 是决策与外部世界之间唯一的执行枢纽。

一句话固化分工——LLM 是"决定调什么"的脑，runtime 是"真正伸手去调"的手，外层标准是手伸向不同外部实体的几根手指，手指只能长在手上。

所以"agent 系统的协议标准"既包含**内部组件协议**（function calling），也包含**跨边界协议**（其他四个）。综述用 *integration boundary* 而不是 "agent interface" 这种以 agent 为中心的措辞，正是因为 agent 在某些边界上不是端点，而是**横跨两端**——更精确地说，横跨两端的是 runtime。

### 2.2 标准对照表

> ● 一等支持　◐ 部分或惯例支持　○ 不在范围


| 边界                 | 标准                   | Wire 格式  | Typed | Runtime discovery | Long-running |
| ------------------ | -------------------- | -------- | ----- | ----------------- | ------------ |
| Model ↔ Function   | Function calling     | JSON     | ●     | ○                 | ○            |
| Agent ↔ Capability | **MCP**              | JSON-RPC | ●     | ●                 | ◐            |
| Agent ↔ Capability | OpenAPI              | HTTP     | ●     | ◐                 | ○            |
| Agent ↔ Agent      | **A2A**              | JSON-RPC | ●     | ●                 | ●            |
| Agent ↔ Agent      | ACP / ANP            | HTTP     | ●     | ●                 | ●            |
| Agent ↔ Repo/Env   | AGENTS.md / AGENT.md | Markdown | ○     | ◐                 | ○            |


读表的关键：四个维度反映的是不同边界的需求差异。比如 **Long-running** 列里只有 Agent↔Agent 类标准一等支持——因为 agent 之间委派的任务可能跑几分钟到几小时，而 Model↔Function 单次调用通常是毫秒级，根本不需要这个能力。

### 2.3 各标准的定位详解

#### 1. Function calling（Model ↔ Function 边界）

**它要跨的鸿沟**：LLM 天生只会吐出一串文本，而运行时要执行的是"函数名 + 具名参数"的结构化调用。一句"帮张三发封问候邮件"里，哪段是函数名、哪段是收件人、哪段是标题，运行时无从切分。Function calling 就是架在这道鸿沟上的桥。

**机制：一份事先约定的契约，调用按它走三步**。契约就是工具的 JSON schema——声明函数名、以及每个参数的名字和类型。有了它，一次完整调用固定为三步（以 `send_email` 为例）：

```jsonc
// ① 工具声明：runtime 在请求前把 schema 注入 prompt
{ "name": "send_email",
  "parameters": { "to": "string", "subject": "string", "body": "string" } }

// ② 模型产出 call：贴着 schema 的结构，不再是自然语言
{ "name": "send_email",
  "arguments": { "to": "zhangsan@x.com", "subject": "问候", "body": "最近可好" } }

// ③ runtime 执行后回填 result：同样结构化，喂回模型继续推理
{ "status": "sent", "message_id": "m_8a21" }
```

**为什么这层 schema 约束不可省**：对比就清楚。没有它，模型可能输出"给张三发邮件标题是问候"——这串文本里参数边界是糊的，runtime 没法可靠切出 `to` / `subject` / `body`。有了它，参数边界被契约钉死，模型输出被强制成机器可直接解析的字段。本质是把"解析自然语言"这个最不可靠的环节，提前用一纸约定消化掉。

**局限：只解决"怎么调"，不解决"有什么可调"**。所有工具的 schema 必须在请求前一次性铺进 prompt；function calling 自身没有 discovery 机制，模型无法在运行中反问"现在还有哪些工具可用"。这恰好是下一层 MCP 要补的环节。

#### 2. MCP（Agent ↔ External Capability 边界）

**Model Context Protocol** 已成为 coding/enterprise agent 最可见的工具集成基础。

**核心架构**：host-client-server 三方

- **host**：agent 进程
- **client**：host 内的连接管理器
- **server**：独立进程，暴露 tools / resources / prompts 三类能力

**为什么这套架构有价值**：

1. **Schema 层互操作**——server 用 JSON-RPC 暴露类型化接口，任何 MCP 兼容的 host 都能用
2. **生态流动性**——agent builder 可以复用别人写好的 server catalog（GitHub、文件系统、数据库……），不必为每次部署写自定义连接器。这是比"标准化数据格式"更深层的价值

**边界**：Agent ↔ External Capability。MCP 不管 agent 之间怎么通信（那是 A2A 的事），也不管模型输出怎么变 JSON（那是 function calling 的事）。

详见 [[MCP_学习笔记]]。

#### 3. A2A（Agent ↔ Agent 边界）

**A2A 的目标和 MCP 完全不同**：不是把工具暴露给一个 agent process，而是**让多个不透明的 agent process 互通**。

**关键能力**：

- **Discovery**：通过 Agent Card 找到对方提供什么服务
- **同步与流式交互**：短任务直接 request/response，长任务通过 streaming
- **Long-running task 协作**：A 委托 B 一个跑 30 分钟的任务，期间 B 可以汇报进度、A 可以查询状态

**为什么必须长任务一等支持**：agent 委派的工作往往是"调研 X 后产出报告""完成代码 review"这种数分钟到数小时级别的任务。如果协议假设"调用必须在几秒内返回"，整个协作模式都无法成立。

#### 4. MCP vs A2A：互补而非竞争

按边界看清楚就一目了然：

- MCP 走 **tool/context access**——agent 拿能力
- A2A 走 **inter-agent delegation/collaboration**——agent 拿另一个 agent

一个真实 agent 系统通常同时用两者：通过 MCP 访问 GitHub/数据库，通过 A2A 委托另一个专业 agent 做代码 review。

#### 5. OpenAPI（Agent ↔ External Capability 的另一选择）

**和 MCP 占同一边界，但风格不同**：

- 走 HTTP（不是 JSON-RPC over stdio/SSE）
- 提供语言无关的机器可读 API 契约
- 许多 agent framework 当作 tool generation 和 validation 的来源——读 OpenAPI spec 自动生成 function calling schema

**典型用法**：已有 REST API 的系统不必单独写 MCP server，直接把 OpenAPI spec 喂给 agent framework 即可。

#### AGENTS.md / AGENT.md（Agent ↔ Repo/Env 边界）

**完全不同维度的标准**：不是 wire protocol，而是 repo 根目录的 Markdown 文件，把工具用法和工作流约束**直接编码到版本控制里**。

**解决的问题**：coding agent 进入一个陌生 repo，怎么知道"这个项目的测试命令是 `pnpm test` 不是 `npm test`"、"提交前必须跑 lint"？没有这种文件，每次都要 agent 自己探索；有了，setup 摩擦消失。

**为什么是"轻量"选择**：不需要任何运行时机制，纯文本约定。代价是不能动态发现新工具，但适合稳定的项目级约束。

## 3. Tool Description / Discovery / Selection（描述、发现、选择）

### 3.1 协议解决了"怎么调用"，但没解决"调用哪个"

协议层规定了 wire format 和发现机制。下一个瓶颈是：**当 menu 有 100 个工具时，每一步该浮现哪几个工具供模型选择？**

这是检索问题（retrieval）伪装成 agent 问题。

### 3.2 主要研究方向：把"工具选择"做成一等问题

学界沿几条线攻这个"检索"问题，每条针对"选不对"的一个侧面——从"选得准"到"自动配流程"再到"连 skill 一起选"：

| 系统 / 工作                               | 关注点                                         | 解决的具体问题                                      |
| ------------------------------------- | ------------------------------------------- | -------------------------------------------- |
| **EASYTOOL**                          | 从大型工具清单里选合适工具                               | 简化 tool description、压缩 selection prompt      |
| **AnyTool / CRAFT**                   | 自动构造或精化 tool-use pipeline                   | 降低人工指定每个工具用法的负担                              |
| **MetaTool**                          | benchmark 评估 tool retrieval 与 invocation 质量 | 揭示不同 domain 与 query 形式间差异极大                  |
| **MCP-Zero / ToolRet / ToolRegistry** | retrieval-aware orchestration、registry 质量   | 把 tool 发现做成一阶能力，而不是塞 prompt                  |
| **SkillRouter / SkillRet**            | 把"工具选择"扩展到**可复用 skill 选择**                  | agent 要找的不只是 API schema，还有 procedural module |


最后一个值得展开：**skill 是比 tool 高一层的抽象**。一个 skill 可能是"如何处理客户退款"这样的多步流程，封装了"调用哪些 tool、按什么顺序、出错怎么办"。Skill 选择问题和 tool 选择问题同构，但粒度不同。参考 [[09-Skills-按需技能]]。

### 3.3 从系统层证据归纳的两条设计原则

#### 原则 1：工具少而精胜过暴力多

**为什么**：直接对应 §1.1 的三个机制——减小 prompt entropy、planner branching、token 成本。

**怎么应用**：宁可写 5 个高质量、覆盖核心场景的工具，也不要堆 50 个细粒度工具让模型每步都纠结。

#### 原则 2：Discovery 管线必须自适应

**为什么**：静态/全局工具列表无法跨快速演化的 repo 或多租户企业部署。一个企业 agent 可能服务多个客户，每个客户有自己的 CRM、自己的内部工具——硬编码的 menu 必然过时。

**怎么应用**：把 tool registry 设计成可查询的服务（"现在这个 context 下，相关工具是哪些？"），而不是部署时固定的列表。

## 4. Tool-Augmented Training & Integration（工具增强训练与集成）

本节回答一个问题：**怎样才能让 agent 真的会用工具？**

### 4.1 核心原理：工具能力是一条串联链，不是三种能力的加总

把一次成功的工具调用拆开，会发现它必须连续闯过三道关卡：

```
tool competence = pretraining/fine-tuning signal   （模型有没有学会调工具）
                × interface schema 质量             （工具说明书清不清楚）
                × runtime selection policy          （该用的工具有没有被摆到模型面前）
```

这三项之所以用**乘法**而不是加法连接，是因为它们对应工具调用发生的三个**先后步骤**，缺一环则整条链断：

```
模型产生"该调工具"的念头 ──► 把调用格式/参数写对 ──► 在候选里看见目标工具并选中
   （训练信号决定）            （schema 质量决定）        （selection policy 决定）
```

- 加法意味着各项可互相弥补：一项弱，靠另一项补强还能及格。
- 乘法意味着**任一项接近 0，乘积就接近 0**：模型不会调（0）× 接口完美 × 策略完美 = 仍然不会调。

因此整节的逻辑是：4.2–4.4 分别讲清这条链的三个环节各解决什么、各自怎么失败；4.5 补充一类常被忽略的工具；4.6 给出工程含义。

### 4.2 第一环 · 模型训练信号：把"会调工具"练进模型

光把工具丢给模型，它不会天生就用。需要在训练阶段教，而"教什么"分三个层次的毛病：


| 工作                                | 解决的问题    | 通俗说法                          |
| --------------------------------- | -------- | ----------------------------- |
| **Toolformer**                    | **时机问题** | 模型本不知道"算这道数该掏计算器，而不是自己硬算"     |
| **Gorilla / ToolLLM / ToolBench** | **规模问题** | 工具有成百上千个时，得挑对那一个              |
| **ToolkenGPT / CREATOR**          | **格式问题** | 把"调用工具"做成 token 级一等操作，调用语法不写崩 |


关键在于这三者是**不同层次的失败**：一个模型可能时机判断对了，却在工具一多时选错（规模差），或选对了却把参数格式拼崩（格式烂）。三者各自独立，不能互相代偿。

- Toolformer 用 self-supervision 学习"什么时候/在哪儿插入 API call"。
- Gorilla 系列靠更大工具语料 + instruction tuning + execution-centric supervision 解决规模。
- ToolkenGPT 把调用做成 token 级操作，而不是事后再解析模型输出。

### 4.3 第二环 · interface schema 质量：工具说明书要让模型读得懂

模型有了调工具的念头后，能不能调对，取决于工具的"说明书"（名字、描述、参数 schema）写得清不清楚。说明书含糊，模型就填错参数、调错工具——这一环的失败表现为**格式正确但用法错误**。本节不展开，详见 §2 的接口设计原则。

### 4.4 第三环 · runtime selection policy：该用的工具得先被摆到模型面前

**原理**：模型每次只能"看见"被放进它上下文（prompt）里的那批工具。没放进去的工具，对模型而言等于不存在。"运行时选择策略"就是决定"这一次把哪些工具放进上下文给模型看"的那套逻辑。

**为什么不能把所有工具都给模型看**：

- 每个工具的说明书都占 token，全塞进 prompt 会撑爆上下文窗口。
- 企业级 agent 背后可能挂着成百上千个工具（每个客户的 CRM、各类内部 API）。
- 候选越多，模型越容易选错——对应 §3 "工具少而精胜过暴力多"那条原则。

所以系统通常**先检索、再投喂**：

```
用户："帮我查这个客户的订单"
        ↓
运行时检索：跟"订单/客户"相关的工具有哪些？
        ↓
挑出少数几个塞进 prompt  ←── 模型只能从这几个里选
        ↓
模型选工具、生成调用
```

**这一环的失败最隐蔽**：若检索判断错了，该用的"查订单工具"没被挑进候选——模型不会报错、也不会写错格式，它只是**被剥夺了正确选项**，只能在错误候选里硬挑，或回答"没有合适的工具"。类比：厨师很会做红烧肉，但端上桌的只有葱姜蒜、没有五花肉——不是他不会，是食材没摆上台面。

正因为"工具发现"决定了模型能否看见正确工具，它应被当作 agent 的**一等能力**（做成可查询的 registry/retrieval 服务），而不是部署时把一份固定 menu 塞进 prompt 了事。

### 4.5 延伸 · 第二类工具：它们的"输出 schema"是 interface 质量的极端案例

前面三环默认讨论的是**执行型工具**——有副作用：执行命令、读写文件、调 API。但 coding agent 还需要另一类工具：**静态分析、type checker、solver-backed verifier、proof assistant、patch equivalence / fault localization checker**。它们**不执行代码**，只提供"代码会怎么行为"的判断。

之所以把这类工具放进本节，是因为它们**把第二环（interface schema 质量）推到了极端**：执行型工具的输出对错往往一眼可辨（命令报错、文件没写成），而推理型工具的输出本身就是一段"判断"，判断的**信息密度**直接决定了 agent 能不能接着往下推。schema 设计在这里不再是"参数怎么填"，而是"结论该带多少证据"。

**Ugare & Chandra (2026)** 把这种模式框架化为 *agentic code reasoning*：agent 探索 repo、就代码行为推理，**不必真跑代码**。它定位在两个极端之间：

- 太松：无结构的 chain-of-thought（agent 自己脑补代码怎么跑，不可靠）
- 太严：完全 formal verification（用定理证明器严格证明，太贵）
- **中间**：semi-formal reasoning 强制 agent 陈述前提、跟踪程序路径、推导显式结论——比纯 CoT 准、比 formal 便宜，适合 patch 等价验证、fault localization、代码问答。

**因此对 Tool 层的设计要求**：这类推理工具应返回**承载证据的产物**（trace、proof obligation、counterexample、structured certificate），而非 black-box 的 yes/no。原因：agent 拿到光秃秃的 "false" 无法继续推理；拿到 counterexample 才能理解"为什么 fail"并调整——这正是"interface schema 质量"在推理型工具上的具体落地。

### 4.6 工程含义：三层是一个系统，不能单独评估

回到 4.1 的乘法链，反面举例最清楚：

- 只优化 schema，但模型没学过工具调用 → 模型乱用
- 模型很强，但 schema 写得烂 → 调用格式错误
- 前两者都好，但 selection policy 把工具淹没在 menu 里 → 模型根本看不到该用的工具

结论：**评估或改进 agent 的工具能力，必须把"训练信号 + interface schema + runtime selection"当成一个系统看**。单独优化或单测某一层，意义有限。

## 5. Scalability & Session Management（可扩展性与会话管理）

**承上**：§1–§4 讨论的是**单次工具调用**——怎么设计接口、怎么选对、怎么调对。本节换一个维度：当 agent 在一个任务里**连续多次、甚至长时间**调用工具时，会冒出哪些新问题。

### 5.1 根源：长会话被迫把状态分居两处

**stateful / stateless 指工具那一侧记不记得状态**（`state` = 上次操作留下、这次还要用的信息）：

- **stateless（无状态）**：工具不记，每次调用从零开始、调完即失忆。
- **stateful（有状态）**：工具维持一个会话(session)，**同一任务里多次调用，后一次能用到前一次留下的状态**。例：shell 里先 `cd /tmp` 再 `ls`——stateful 时 `ls` 列出 `/tmp`，stateless 时回到默认目录。

> ⚠️ 不是"后一次调用保存了前一次的 state"，而是 **state 自始至终待在工具侧没动**，多次调用都连到同一份；后一次是去**访问**它，不是接收上一次传来的东西。靠什么连到同一份？靠一个 **handle**（`connection_id`、session token、占座号）——它是"多次调用指向同一份状态"的唯一纽带。

**为什么状态非得留在工具侧、不能全返回给 agent 记？** 取决于状态是哪一类：


| 状态类型          | 能否返回给 agent 记                            | 例子                              |
| ------------- | ---------------------------------------- | ------------------------------- |
| **数据 / 值**    | **能**——返回后写进 memory 即可（这正是 stateless 做法） | 查询结果、算出的数字、一段文本                 |
| **活的资源 / 会话** | **不能**——服务器那头一个正在"活着"的东西，无法序列化成文本传回      | 数据库连接、登录态、shell 进程、进行中的事务、占住的座位 |


所以 stateful 不是偷懒，而是物理上躲不掉：活资源（活的 socket、未提交的事务、被锁的库存）传不回来，agent 顶多攥一个指向它的 handle。**于是状态分居两处**：


| 状态在哪               | 角色                         | 类比（旅行订票）          |
| ------------------ | -------------------------- | ----------------- |
| **工具侧**            | 状态的**源头**（活资源本体）           | 航空公司系统里"帮你占住的座位"  |
| **agent 的 memory** | 对源头的**追踪**（一个 handle + 记录） | 笔记本上写的"已占座、占座号 X" |


工具持有真状态，memory 拿 handle 追踪它——**这份"源头 vs 追踪"的同步关系，正是本节要管的东西**（也是为什么本节属 Tool 层却始终牵扯 memory）。同步一旦失准，就是 §5.2 的三种失败。

### 5.2 三种失败 = 同步失准的三种形态


| 失败               | 失准形态                       | 一句话            |
| ---------------- | -------------------------- | -------------- |
| **Stale handle** | memory **过时**：追踪还在，源头没了    | 攥着房卡，酒店已换锁     |
| **重试态不一致**       | memory **落后**：源头变了，追踪没跟上   | 转账重试，扣了两次      |
| **上下文撑爆**        | memory **过载**：追踪侧自己被源头输出淹没 | 笔记记太厚，开头的事翻不到了 |


下面各配一个具体 case。

#### ① Stale handle（句柄失效）—— 源头死了，追踪还指着它

agent 第 1 步 `open_connection` 拿到 handle `conn_42`，之后停下来思考了几分钟。数据库嫌连接闲置太久把 `conn_42` 回收了（**源头消失**）。agent 的 memory 里还记着 `conn_42`（**追踪未更新**），第 N 步拿它去查 → 工具一校验："没有 conn_42 这号" → 当场回 `invalid connection`。**特征：必然当场报错。**

#### ② 重试态不一致（inconsistent state across retry）—— 源头变了一半，追踪记成"没变"

走一遍转账：

```
agent 调 transfer(from=A, to=B, amount=100)
  工具侧：① 从 A 扣 100  ✅
          ② 正要给 B 加 100 时，网络断了 ✗
  agent 收到：超时 —— 它不知道工具到底做到哪一步（没扣？扣了没加？全做完？）

agent 判断"这次失败了"，于是重试：
agent 再调 transfer(from=A, to=B, amount=100)
  工具侧：又从 A 扣 100  →  A 被扣两次共 200，B 只该收 100
```

**根因两条缺一不可**：(a) 工具侧**已部分改动**（A 已扣），但 memory 只记到"超时/未知"，没跟上真实状态；(b) 这个操作**不幂等**（重复执行结果会叠加）。两者叠加 → 重试把伤害翻倍。**特征：可能报错（如重试触发 `duplicate key`），也可能不报错、但后果当步可见（钱多扣了）。**

#### ③ 上下文撑爆（context-window saturation）—— 和 ① 正好相反：源头活着，追踪侧自己坏了

这里先回答一个很自然的疑问：**"agent 不是有 handle 吗，上下文被截断为什么还会出事？"**

关键：**handle 只是一个"地址/提货单"，它不携带含义、计划和周边事实**。上下文撑爆砍掉的是 memory（追踪侧），砍到哪行丢哪行，可能砍掉两样东西：

- **砍掉 handle 本身**：`conn_42` 也只是早期某条工具返回里的一行，滚出窗口就没了 → agent 连"地址"都不剩，没法再发后续调用（哪怕连接在工具侧还好好活着）。
- **砍掉 handle 周边的信息**：handle（地址）还在，但**它指向的东西是什么、为什么调它、调完怎么解读、有什么规矩**——这些"语境"被挤掉了。

具体 case（coding agent 跑长重构）：

```
第 2 步：读配置，得知两件事并写进上下文——
         · 临时表 t1 = "过滤后的错误日志行"
         · 用户明确要求："不要动 legacy/ 目录"
… 中间 40 次工具调用，每次都把大段文件内容 dump 进上下文 …
   → 早期那两条被后来的输出挤出了 context window

第 43 步：agent 要查 t1 / 编辑文件，但——
   · 它记得 t1 这张表存在（handle 还在），却忘了"t1 里装的是什么" → 误用查询结果
   · "别动 legacy/" 那条约束已不在可见上下文里 → 它动了 legacy/
```

**注意**：工具侧一切正常——连接活着、t1 还在、文件可写。坏的纯粹是 **memory 这一侧**：早期的事实/约束被新的工具输出淹没、挤出窗口。这正是它和 ① stale handle 的镜像关系——① 是"追踪在、源头没了"，③ 是"源头在、追踪没了"。

**为什么 ③ 最阴险**：分水岭不在报不报错，而在**有没有即时信号**。① 必然当步报错，② 报错或后果当步可见——都离案发地点很近。③ **完全没有信号**：不报错、也没有当场异常，只是悄悄把上下文吃满，等发现"agent 怎么忽然犯傻、忘了早先的决定"，已隔了几十步，根本想不到根因是"工具痕迹把早期上下文挤掉了"。

### 5.3 因此 harness 必须做的三件事

#### 先讲清楚：session 是什么

**session（会话）= 工具侧为"一连串相关调用"维持的一段持续状态，从开启到关闭。** 它就是 §5.1 里"工具侧那份活着的状态"的载体。

回到 `conn_42` 的例子：`open_connection` 那一刻，工具侧开了一个 session——一条活着的数据库连接，可以在它上面建临时表、记住当前事务。之后所有带 `conn_42` 的调用都跑在**同一个 session** 里，共享这份状态，直到它被关闭或超时回收。agent 手里的 handle，就是指向这个 session 的"提货单"。

> 一句话：session 是工具侧那段"活着、会被多次调用复用"的状态；handle 是 agent 用来找到它的钥匙。

明确了 session，三件事就具体了。

#### 第 1 件：管好 session 的"创建与销毁"（生命周期控制）

**"生死边界"= 一个 session 何时被创建、何时被销毁、由谁负责，必须明确规定，不能放任。** 放任有两种死法，都会出事：

- **只开不关** → session 越积越多，每个都占着工具侧的连接和内存不放 → **资源泄漏**，工具最终被拖垮。
- **悄悄死掉** → session 超时被工具侧回收了，agent 却没收到通知，还以为它活着 → 下次调用才撞上 `invalid`，这就是 **① stale handle**。

**具体做法**：用完显式 `close`；给 session 设明确超时，并让 agent 能**主动感知"它已失效"**（比如续期或收到失效通知），而不是等下次调用撞墙才知道。

> 类比借书：借了要还（close），不还就一直占着名额；到期了图书馆应当**主动通知**你，而不是等你下次来才说书已被收走。

#### 第 2 件：给塞进上下文的工具结果设上限（有界 context injection）

工具每次调用返回的结果，都会被写进 agent 的上下文。**不加限制的话，长会话里这些结果（尤其大段日志、文件内容）会把上下文塞满，把早期的目标/约束挤出去**——也就是 ③。

**具体做法**：给"能往上下文塞多少工具输出"设一个额度，超了就先把旧内容**压缩成摘要**、或丢弃不重要的部分，保住早期关键信息（目标、约束、handle 的含义）。

> 类比记笔记：本子快记满时，把旧的几页浓缩成一句摘要腾出空间，而不是无脑往后翻、翻到最后忘了开头写过什么。

#### 第 3 件：让两类错误能被分辨（可观测性）

长会话出问题时，得先分清是哪一类错，否则根本不知道该修哪儿：

- **模型层面的错**：模型选错了工具、或参数想错了——**脑子的问题**（planner 逻辑错误）。
- **接口/协议层面的错**：工具调用本身失败了，比如 handle 失效、超时——**管道的问题**。

**具体做法**：在调用链上加埋点/日志，把这两类标成不同类别。尤其 ③ 上下文撑爆**看起来很像"模型突然变蠢"**，实则是上下文管理的问题——可观测性要能把它和真正的逻辑错误区分开。这一条是 Tool 层与 [[05-O-可观测性与运维|Observability 层]] 的接口：**协议设计从一开始就要考虑可观测性，事后补监控成本很高。**

#### 这三件事和 §5.2 不是一一对应

特意纠正一个容易产生的错觉——三件事**不是**三种失败的三把解药。准确的关系是：**前两件是"预防"，第三件是横切的"诊断"**：

| 措施 | 性质 | 主要管 §5.2 哪个 |
| ------------ | -------- | --------------- |
| 第 1 件 生命周期控制 | 预防 | ① stale handle（过时） |
| 第 2 件 有界 context | 预防 | ③ 上下文撑爆（过载） |
| 第 3 件 可观测性 | 诊断（横切） | 帮定位全部，尤其 ②③ |

由此暴露一个**不对称，值得记住**：

> **② 重试态不一致（落后）在这三件事里没有专门的预防措施。** 它的真正根治是**工具自身的幂等设计 / 事务回滚**（让"重试一次"和"重试十次"结果一样），属于更底层的工具实现，不在本节这三条 harness 要求之内——第 3 件只能帮你**事后发现**它，发现不了就只能靠幂等性从源头堵住。

## 6. 本层小结

### 6.1 核心约束总览


| 约束            | 表现                                                                  | 工程对策              |
| ------------- | ------------------------------------------------------------------- | ----------------- |
| **菜单越大决策越糟**  | tool count 推高 prompt entropy、planning error、token 成本                | 少而精；自适应 discovery |
| **协议生态层级不重叠** | MCP / A2A / function calling / OpenAPI 占的是不同 *integration boundary* | 按边界选标准，不按时髦选标准    |
| **能力的三方耦合**   | 训练信号 × schema 质量 × runtime selection policy 共同决定 tool competence    | 评估时三层一起看          |
| **会话长跑要可观测**  | bookkeeping、stale handle、context bloat 必须由 [[05-O-可观测性与运维\|Observability 层]] 配合诊断 |


### 6.2 Tool 层与 Execution 层的关系——capability/control 张力

Tool 层和 [[01-E-执行环境与沙箱|Execution 层]] 是**互补面**：

- **Execution 层**管"执行后的爆炸半径"——一旦工具被调用，怎么限制它能造成的伤害
- **Tool 层**定义"哪些动作根本不准发生"——通过控制 tool menu 决定能力边界

**只有两者结合才构成完整的 capability-control 权衡**：

- 光有 Execution 没有 Tool：menu 暴露 `rm -rf /`，沙箱也救不了误删
- 光有 Tool 没有 Execution：menu 控得很严，但允许的命令一旦写错参数还是出事

这条 capability-control 张力会在 [[08-跨层综合与开放问题]] 作为系统级现象重现——它不只是 Tool 和 Execution 的局部问题，是整个 agent 设计的元约束。
