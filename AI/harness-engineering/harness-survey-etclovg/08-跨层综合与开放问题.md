# 跨层综合与开放问题（Cross-Cutting / Synthesis / Open Problems）

> 前面七层笔记是"逐层拆开看组件"。这篇是**合起来看系统行为**——把 §10–§13 串成一条线：七层之间怎么互相牵扯、合起来暴露哪些系统级矛盾、还剩哪五个没解决的硬问题。回到 [[00-Survey总览-ETCLOVG七层框架]] 看七层全景。

## 1. Cross-Cutting Concerns（§10）——七层不是独立的

### 1.1 层与层之间是"依赖结构"，不是"零件清单"

最容易犯的错，是把 ETCLOVG 七层当成"可以各自挑选、各自优化的七个独立模块"。实际上它们互相约束：

| 关系 | 具体怎么牵扯 |
|---|---|
| [[01-E-执行环境与沙箱\|Execution]] → [[04-L-生命周期与编排\|Lifecycle]] | 执行环境**限定了**哪种编排策略可行——比如沙箱起得慢，fan-out 出几十个并行 agent 就不划算 |
| [[03-C-上下文与记忆管理\|Context]] → [[06-V-验证与评估\|Verification]] | 上下文管理**影响**评估的可复现性——上下文每次组装得不一样，同一题就跑不出稳定结果 |
| [[07-G-治理与安全\|Governance]] → 全部 | 身份 / 权限 / 审计**横切**其它六层，无处不在 |

→ **harness 设计应当当成"依赖结构"来读**——动一层会牵动其它层——而不是当成"可以随便拼的组件清单"。

### 1.2 Cost-Quality-Speed 三难（trilemma）的初步形态

一个反复出现的矛盾：更强的 Verification、更严的 Governance、更丰富的 Observability、更保真的 Execution——**每一样都同时增加成本和延迟**。成本、质量、速度三者互相拉扯：

- 优化速度，常常牺牲诊断深度或安全余量。
- 优化质量，可能让每次 iteration 贵到日常用不起。

> 所以真正的系统必须做取舍决策：**哪些 check 同步跑（实时拦），哪些挪到 offline（事后批量），哪些 failure 才值得走昂贵的 recovery 路径。** 不能所有维度都拉满。

### 1.3 标准化的压力与它的副作用

MCP / ACP / A2A 这些协议，反映的是对**共享接口**的需求——让 tool、agent、orchestration state 能跨系统通用。这股压力偏向"做 agent-agnostic 的通用基础设施"，而不是"为单个 agent 做定制集成"。

**但标准化有个副作用**：它把治理和可观测性的责任**往后推**了。一句话说清——标准化的 tool call **只有在周围 harness 能跨系统保住 provenance、permission、cost、failure evidence 时才真正有用**。否则统一的只是"怎么调"，却丢了"谁授权调的、花了多少、出错算谁的"。

### 1.4 五个持续存在的生态缺口

这五处恰好都落在"层与层的边界"上，是目前最缺工具的地方：

1. cross-tool interoperability（工具间互操作）
2. cost attribution（成本归因）
3. failure recovery（失败恢复）
4. multi-repository orchestration（跨仓库编排）
5. human-agent handoff（人机交接）

→ 这推动了核心问题的转变：**不再是"每一层有没有工具可用"，而是"把这些工具组合起来后，整个 harness 表现得像一个可靠的控制系统吗"。**

## 2. Cross-Layer Synthesis（§11）——五个系统级效应

> §1 的零散关切，在这里被收拢成五个**系统级**效应。它们是 Claim 1（"harness 是一个独立的 system layer"）的核心支撑。

### 2.1 Cost-Quality-Speed 三难（系统级展开）

| 拧紧哪个旋钮 | 得到什么 + 付出什么 |
|---|---|
| 更强 sandbox + 更保真环境 | ↑ 安全 / 可复现，但 ↑ 启动延迟和基础设施成本 |
| 更丰富的 context / memory 策略 | ↑ 任务连续性，但 ↑ token 消耗、检索 overhead、还引入 staleness（信息变陈旧） |
| 更深的 evaluation / observability | ↑ 诊断能力，但 ↓ 迭代速度、↑ 存储和 trace 处理成本 |

**核心结论：生产系统不能把"质量"当成一个可以单独无限拉高的标量。** 必须做出三类具体决策——哪些 risk 值得用昂贵的 control 去管、哪些 check 挪到异步或回归套件里跑、每个 lifecycle 阶段抓哪些 telemetry 才值。

### 2.2 Capability-Control 权衡（§11.2）——每多一份能力，就多一份失控风险

更强的 harness 给 agent 更多权力。但**每多给一份权力，就同时放大一份 control 问题**：

- 更大的 tool 菜单 → 任务覆盖更广，但 selection error（选错工具）和 prompt injection 的攻击面都增大。
- 持久 memory → long-running 任务变可行，但冒出 provenance（来源可信吗）/ staleness（过期了吗）/ privacy（隐私）三重风险。
- 更宽松的 sandbox → autonomous 执行更有用，但一旦误判或被攻陷，**action 的"爆炸半径"更大**。

→ 所以 security 不是"在一个功能正常的系统上事后加的 add-on"，而是一条贯穿 tool schema、context policy、runtime permission、identity、auditability、human approval 的**设计轴**——从一开始就要和能力一起设计。这正是 [[01-E-执行环境与沙箱|Execution 层]] 和 [[02-T-工具接口与协议|Tool 层]] 都强调过的 capability-control 张力，在系统级的再现。

### 2.3 Harness Coupling Problem（§11.3）——为什么"局部最优"很脆

各层耦合得很深，导致一个反直觉的结论：**单独看有益的改动，组合起来可能让整体退化。** 看几条具体的耦合路径：

- 执行环境通过影响"package 可用性 / reset 语义 / 延迟 / failure 模式"，**间接改变了评估结果**。
- tool description 一边**消耗 context 预算**，一边**塑造模型行为**——改一处动两处。
- observability 抓到的 trace，**只有当 identity / permission 状态也在同一粒度被一起抓下来时，才能当成 governance 的证据**。否则日志再多，也证明不了"谁越权了"。
- evaluation 的设计，会通过"奖励某些 recovery loop"反过来影响 orchestration 的行为。

→ **所以 harness 的任何改动，都应当当成"系统改动"来测，不能当成"局部改动"。** 某个 prompt / tool / memory / sandbox / verifier / monitor 单看是改进，组合进整体后 rollout 反而可能退化。

**这个耦合还解释了一个关键观察**：agent 的分数没法干净地归因到模型头上——必须同时指明"周围那个 controller（harness）长什么样"。在闭环视角下，context policy / tool schema / verifier / recovery loop 任何一处改动，都改变了 controller $C_H$，从而改变了同一个模型被测出来的行为（Bölük 2026b）。

### 2.4 从 Agent Framework 到 Agent Platform（§11.4）

一个正在发生的迁移——做 agent 的东西，正从"框架"长成"平台":

| Agent Framework | Agent Platform |
|---|---|
| 提供局部抽象：agent / tool / memory store / 执行循环 | 在此之上再加：durable workspace、managed sandbox、identity、billing、observability、evaluation、governance、跨多 run / 多 user 的 human handoff |

**驱动力**：long-running agent **不再只是"一个调模型的程序"，而是一个 operational system（运营系统）**——它需要 tenancy（多租户）、合规、fault recovery、trace 留存、组织级 ownership。

→ 于是设计问题本身变了——从 **"如何搭一个 agent?"** 变成 **"如何运营一支 agent 舰队，让它们的行为长期保持可检视、可回滚?"**

### 2.5 由此引出的研究 agenda（§11.5）

综合下来，以 harness 为中心的研究方向：

- benchmark 应衡量 **harness 干预**，而不是只衡量 model weight。
- 需要 **trace-native attribution** 方法，跨层定位失败。
- 需要 **protocol** 来在 agent / tool / sandbox / evaluator / human 之间转移状态和责任。
- 需要 **优化方法**，让 harness 的"瘦身"能跟上模型的升级。

§3 把这些转成五个具体的开放问题。

## 3. 五大开放问题（§12）

### 3.1 加固并规模化执行环境（§12.1）

| 子问题 | 实证起点 |
|---|---|
| **frontier model 已经能利用沙箱弱点** | SandboxEscapeBench |
| 防御侧仍然**分散**、各做各的 | Wu et al. 2025 / Yan 2025 |
| **"一任务一容器"模式撑不住大规模训练/评估**（数万条并行 trajectory，需要便宜的 reset + replay） | SWE-World 走"无 Docker 的 surrogate 环境"方向，但 learned transition 相对真实执行的保真度还没解决 |
| **部署可移植性差** | 基于 Docker 的沙箱继承了 Linux 假设;macOS / Windows / 浏览器 / 桌面 / 混合云各有不同的 isolation 和复现约束 |

**关键 future work**：让运行时底座既**可测**又**可组合**——需要三件配套：统一的 security eval（覆盖 prompt injection / goal misalignment / compositional amplification 三类 agent 特有威胁）+ 一个 cost model（决定何时该用 container / microVM / OS 级 / 完整桌面 VM / 浏览器 / learned surrogate）+ 一个 portability 层。**MCP 这类标准能降低组装成本，但前提是 Tool / Governance / Observability 层暴露出足够的 state，让"选哪种运行时"这个决定可审计、可恢复、安全。**

### 3.2 让 long-running agent 的状态保持可靠（§12.2）

**最深的 context 问题，不是"怎么塞更多 token"，而是"怎么让 agent 内部记录的工作状态，和真实的 task state 长时间保持对齐"。** 每一次 summarize / retrieve / compact / externalize，都可能删掉约束、扭曲优先级、保留过期假设——这就是 [[03-C-上下文与记忆管理|Context 层]] 的 context drift。

**一个有价值的研究 reframe：把 context management 当成 state estimation（状态估计）问题。** 也就是——量化每次 compression / retrieval / forgetting 到底丢了多少"和任务相关的信息"，并给"agent 内部状态"和"真实状态"之间的偏离设一个上界。把模糊的"记忆管理"变成可度量的工程问题。

未来系统需要这些具体能力：

- uncertainty-aware summary（摘要时标注"这条我不确定"）
- 记住的事实带 provenance（来源）
- contradiction handling（发现并处理自相矛盾）
- explicit staleness marker（显式标记"这条可能过期了"）
- recovery 流程：让 agent 能**从可靠的 durable artifact 重建丢失的状态**，而不是盲信自己压缩过的历史

这也意味着 memory 和 evaluation 紧耦合：**评判一个 memory policy，不能只看 recall accuracy（召回准不准），还要看它在多 session 任务里有没有真的阻止了下游的 action error。**

### 3.3 从 agent trace 诊断失败（§12.3）

当前 agent 评估**太以"最终分"为中心**——一趟 run 过了还是没过，这个数被直接当成模型质量的证据。**这对 harness engineering 远远不够**：一次失败的 rollout，根因可能在模型推理、误导性的 tool schema、沙箱配错、stale context、flaky test、benchmark 歧义、judge 不稳、orchestration loop——八个可能，光看"失败"两个字一个都分不出来。

- Anthropic 的 agentic coding eval 显示：**基础设施配置就能可测量地改变 benchmark 分**。
- Bjarnason 2026 表明：**单次 run 的 pass rate 掩盖了巨大的 variance**（同一题跑多次结果飘得厉害）。

→ 所以**评估层必须被当成"测量仪器"来研究**，而不只是一个"排行榜生成器"。仪器本身不准，测出来的都不可信。

**下一步是 trace-native evaluation**：让 trace 成为系统计算 outcome score / trajectory quality / failure attribution / regression test 的**主要对象**。observability 其实已经抓了 span、tool call、cost、retry、exception、中间消息——**但它常和 evaluation 管线脱节**（LangChain 2026 survey:89% 团队用 observability，只有 52.4% 跑 offline eval）。未来系统应当闭环：把异常的生产 trace → 变成回归 case;trajectory 指标直接在 span 上算;诊断信号反哺回 prompt / context / tool / orchestration 的改动。**Reflexion 已在 short-horizon 证明 agent 能从自己的 trace 学习;扩展到 long-running 的多 session 仍是开放问题。**

### 3.4 跨 agent / tool / human 的标准交接（§12.4）

把工作分布到 planner / subagent / tool / sandbox / evaluator / human 之间的那些接口，目前仍然**特别 ad hoc（临时拼凑）**。已有的局部标准：MCP（tool 访问）、A2A（agent 间通信）、OpenTelemetry（trace 通用底座）。

> **缺的是一个 cross-layer handoff contract（跨层交接契约）。** 不管是 planner 把活委派给 executor、agent 调 tool、subagent 把控制权交还、还是系统升级给 human——一次 handoff 应当转移的**不只是一段文字摘要**，还要带上：intent（意图）、constraint（约束）、permission、artifact、provenance、budget state（预算还剩多少）、risk level、trace history、unresolved decision（还没定的事）。只传摘要，接手方就丢了一半上下文。

**这个问题一半是技术、一半是制度**：OpenAI 的 Symphony 把 issue tracker + repository 当成 agent 工作的 control plane;Anthropic 的 long-running harness 强调 durable progress artifact + 干净的交接状态。治理研究从另一个方向得出同样结论：代用户跨系统行动，需要 agent identity、delegation、permission manifest、auditability。**开放问题：设计一个 handoff protocol，既丰富到足以保住 safety / recovery，又简单到能被广泛采用**——它要讲清：谁授权了这个 action、转移了哪些 state、什么证据支撑当前 plan、接手方被允许做什么、什么时候必须把控制权交回去。

### 3.5 模型变强后，怎么让 harness 不变成累赘（§12.5）

**Harness 设计不应默认"越多 scaffolding 越好"。** 每一个 wrapper、reset、verifier、planner、memory rule、permission gate，都编码了一条"**模型自己做不到某事**"的假设。模型一变强，这些干预就应当被**重新评估**，而不是默认它还有用。

Bölük 2026b 主张做 **factorial model-by-harness eval**（模型 × harness 的析因实验），好看清一个干预到底是：对所有模型都有改善、只帮某一类模型、还是反而**颠倒了模型排名**。

- Anthropic 的具体报告：之前对某个模型有用的 context reset，在更强的模型上可以直接砍掉——**移除它反而降了成本、还不掉质量**。（这正是 [[05-O-可观测性与运维|Observability 层]] 里 Opus 4.5→4.6 的那个例子）
- OpenAI 把 harness engineering 框成"**维持 human attention、repo state、agent execution 三者对齐**"，而不是"一味加 scaffolding"。

**Meta-engineering agenda（让 harness 优化和简化自己）**:

- Meta-Harness 把 prompt / tool / control loop 当成 optimization target 去搜索。
- NLAH 让每个 harness module 都可以被显式 ablate（逐个关掉看影响）。
- 生产级 observability + cost 系统（TensorZero / Axon / AgentOps）指向 budget-aware 的 harness 运营。

> **中心风险：benchmark overfit（过拟合基准）**——一个只对着窄基准优化自己的 harness，很可能变脆（基准外一用就崩）。更耐用的目标是 **adaptive simplification（自适应瘦身）**：让 harness 持续追问——当 task / tool / model 能力变化时，**哪些 control 仍然是必要的**，哪些该拆。

## 4. Conclusion（§13）

整篇综述论证一件事：把 agent harness 当成一个**独立的工程 surface** 来看，会得出一个核心论断——**真实世界 agent 可靠性的天花板，是基础设施质量，而不只是模型能力。** 围绕这个 binding-constraint thesis，立了三个 Claim:

| Claim | 内容 | 体现在 |
|---|---|---|
| **Claim 1** | harness 是那个 binding constraint（约束绑定项） | 三组 harness-only 的提升，已经超过同期模型升级的幅度 |
| **Claim 2** | 7 层 ETCLOVG 把 Observability / Governance 从"lifecycle hook 的副产物"提为独立层，反映了生产团队真实的工具栈和 ownership 划分 | [[05-O-可观测性与运维]]、[[07-G-治理与安全]] 各有独立工具栈和团队 |
| **Claim 3** | 148+ 开源项目映射到 ETCLOVG，给出最广的生态快照，浮出采用 pattern、覆盖缺口、新兴设计原则 | §2.9 / §2.4 / 各层 figure |

三段工程演化（prompt → context → harness engineering）+ 跨层综合（cost-quality-speed / capability-control / harness coupling）+ 开放问题 agenda，把 harness 放进了一条更大的工程轨迹里。

**局限性**（作者自陈）:

- 语料偏 English / GitHub 可见 / 开源。
- 偏 coding-agent 生态。
- 扩展到闭源生产系统和非 coding 生态，会让这幅经验图景**更清晰**。

**自我定位**：目前这套分类法是 *descriptive（描述性）*的。把 ETCLOVG 从"仅仅描述 harness 设计"，升级为"**能指导设计决策的 normative（规范性）框架**"——是这本综述希望鼓励的**下一步**。
