## 1. 这一层的核心问题——"正好足够"

### 1.1 一句话目标

这一层要做的事一句话能说清，做对却极难：**让模型每一步看到的信息正好足够。**

"正好"是关键，两边都是悬崖：

- **给少了** → 模型缺了关键状态，没法把任务做对。比如忘了用户三步前说过"别动数据库"，于是动了。
- **给多了** → 性能退化。注意这里的"退化"不是直觉里的"慢一点"，而是**模型答题质量本身下降**——而且这种下降是可测量的、在不同模型上一致出现的、且**学界至今没完全搞懂机理**的现象（§2.3 的 context rot）。

换句话说，上下文不是"越多越保险"。多塞内容既花钱，又主动伤害模型的判断力。这一层全部技术，都是在围绕"如何稳定地命中那个'正好'"打转。

### 1.2 按时间尺度分三档

信息要在多长的跨度里被记住，决定了用什么手段管它。

先界定三个贯穿全章的计量词：**turn** = 一次"输入 → 模型忙完 → 停下等下一句"；**session** = 一次会话从开启到退出，含多个 turn；**run** = agent 为一个任务的一次完整执行（survey 的通用计量词，在 Claude Code 这类产品里大致等同一个 session）。三者里 turn 最小、嵌在后两者内；中期那一档统一用 **run** 作"一轮"的单位。

按这个，三档如下：

| 档位 | 时间跨度 | 具体指什么 |
|---|---|---|
| **短期** | 单次 inference，或会话内的几步 | 此刻喂进模型的 active context window |
| **中期** | 同一 session 跨多个 turn，或同一 task 跨多次 run | 把工作状态**往后传一棒**、跨过"上下文被清空"那道坎（session state） |
| **长期** | 跨 session、跨 task、跨 agent | **可按需检索**的持久 memory：给个 query 就能取回 |

> 注意：表里的"时间跨度"只是直觉尺度，**别拿它当中期 / 长期的判据**——两者真正的分界是右列点出的机制：往后传一棒（前向接力）是中期，可按需检索是长期。详见 §6 开头。

**为什么这个三档分法不是随便切的**：它和操作系统的 memory hierarchy 严格一一对应——短期是 RAM（快、贵、易失），中期是 swap/文件（慢一点、便宜、能跨重启），长期是磁盘（最慢、最便宜、永久且可索引）。这个对应既是直觉来源（前人怎么管 RAM/disk，这里就怎么管 context/memory），也是后文反复用到的术语对照表。本层的 §4/§5/§6 就是依次讲这三档。

## 2. 为什么"context 必须主动工程化"

> 一个很自然的想法：context window 不是越来越大吗（128K、200K、1M）？那"信息装不下"的问题不就自动消失了？**错。** 更大的窗口不自动解决 memory 问题，理由埋在 Transformer 架构本身。

下面三条不是并列堆叠，而是一条**层层堵死"大窗口万岁"的反驳链**——每条从一个新角度，挡掉对上一条的逃避：

| 节 | 它咬住的角度 | 挡掉的逃避 |
|---|---|---|
| **§2.1** | **成本**（贵） | 长 context 单是算就贵到离谱（平方增长）——"贵就贵，算力买得起"？ |
| **§2.2** | **位置**（放哪里） | 就算买得起，信息塞在 context 中间会被忽略——"那放首尾不就行"？ |
| **§2.3** | **长度**（多长） | 就算位置摆对，单是变长模型就整体退化、还没装满就开始——退路堵死 |

三个角度"贵 / 放哪里 / 多长"互不重叠。**尤其别把 §2.2 和 §2.3 混了**：前者固定长度、比位置，后者固定位置、比长度——一个问"放对地方没"，一个问"是不是太长了"。

### 2.1 平方级注意力成本——窗口大，代价大得离谱

Transformer 的 self-attention 要算什么：context 里**每一对 token**之间都要算一个"相关度"。n 个 token，就有 n×n 对关系。

直接后果：**context 翻倍，计算量和显存都是四倍**（2² = 4），不是两倍。

有人会问：FlashAttention、位置编码插值这些优化不是一直在降成本吗？关键区别——**这些优化只降"常数因子"，动不了"平方"这个结构**。打个比方：平方增长是"每多一个人，要和所有已有的人都握一次手"，握手总数随人数平方涨；优化能让你握手更快，但握手的**总次数**改不了。

所以结论是：**context window 是一种稀缺资源，得像预算一样花，不能当免费仓库随便堆。**

### 2.2 U 形注意力曲线——放在哪里，和放不放一样重要

上面是"算力成本"的理由。但还有更反直觉的：**就算算力管够，模型在长 context 上照样会 fail。** 这说明问题不只在成本，在模型"用"长 context 的能力。

Liu et al. (2024) 的关键实证（这篇就是著名的 "Lost in the Middle"）：

- 任务：给模型 20 篇文档做多文档问答，标准答案藏在其中一篇里。
- 发现：**相关那篇放在 context 中间时，准确率比放在开头或结尾低 30% 以上。**
- 画出来是一条 **U 形曲线**——首尾高、中间塌陷。而且这条 U 形在不同模型、不同任务、不同 context 长度上都成立，**连专门为长 context 训练的模型也躲不掉**。

工程含义直白且重要：**信息放在哪个位置，和有没有放进去，几乎同等重要。** 检索系统把对的文档捞回来了，却塞在 context 正中间——等于白捞。这就是为什么后文 §6 的检索、§7 的 compaction，都不能只关心"放没放"，还得管"放在哪"。

### 2.3 Context Rot（上下文腐烂）——还没装满就开始变差

前两条讲的是"贵"（§2.1）和"放哪里"（§2.2）。Context rot 换了个更狠的角度：**不管放在哪，单是输入变长，模型整体就退化——而且窗口远没装满就开始。**

Hong et al. (2025) 在 18 个 frontier 模型（GPT-4.1、Claude Opus 4、Gemini 2.5、Qwen3 等）上做了控制实验，刻意把两个变量拆开测——**单纯增加输入长度** vs **增加任务难度**——好确认退化到底是被哪个引起的。结论：

1. **每个模型都随输入变长而退化**，无一例外。
2. **退化不均匀，取决于任务考验哪种能力。** 先认清长 context 下会**同时**变差的两种能力——**定位**（从一大堆内容里找到相关那段）和**推理**（读懂找到的内容、把它和问题对上）。两类 query 对这两种能力的依赖不同：
   - *exact-match query*（精确匹配查询）：问题和答案**字面对得上**，比如问"订单号 12345"，文档里也写着"订单号 12345"。基本**只考定位**——找到即可，几乎不靠推理。
   - *semantically ambiguous query*（语义模糊查询）：相关段落和问题**字面不匹配**，要靠理解才能对上，比如问"客户为什么不满意"，文档里写的是"配送晚了三天"。**定位、推理都要考。**
   实验发现：**输入变长时，模糊查询的退化比精确匹配陡得多。** 原因就在依赖的能力数量：长 context 让定位和推理**双双退化**——精确匹配只受"定位退化"一种拖累，模糊查询却同时被"定位 + 推理"两种退化夹击，两者在同一个任务上叠加，于是垮得更快。这种"一个任务被两种能力的退化同时拖垮"，就叫**复合失败（compounding failure）**。
	**退化在窗口远未填满时就开始。** 一个标称支持 200K token 的模型，可能在 50K 处就已经显著掉点。"标称容量"和"好用容量"是两码事。

**这不是边角案例，是 agent 的常态。** 任何会累积工具输出、累积中间推理、跨多步读文件内容的 agent，上下文都在持续变长——也就持续踩在 context rot 上。

### 2.4 三条合起来的结论

平方成本（贵）+ U 形曲线（位置敏感）+ context rot（早早就烂）三条叠加，逼出一个硬结论：

> **context management 不能事后补救。** "先让 agent 跑，上下文乱了再说"是行不通的——因为每一个"放什么、放哪里、什么时候移除"的决定，都直接、实时地影响 agent 这一步答得对不对。上下文治理必须是设计的一部分，不是收尾的清洁工作。

## 3. 从 Prompt Engineering 到 Context Engineering

### 3.1 两者的差别：从"写好一句话"到"管好一整套信息流"

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 优化对象 | 单次模型调用的一段**静态文本输入** | 每一步推理时模型可用的**完整信息状态** |
| 时间范围 | 单次调用，写完就定 | 多步任务，每步都在变 |
| 信息来源 | 1 路 input（人写的 prompt） | 多路信息流同时灌入（见下） |

一句话区分：prompt engineering 是"怎么把这一句话问好"；context engineering 是"在这次推理里，到底该让模型看到哪些信息、不看到哪些"。后者的对象是动态的、多源的、每一步都在重算的。

Anthropic Applied AI Team (2025) 给的定义说白了就是：**决定让模型看到哪些内容、不看到哪些。** 完整地说，模型每次生成回答时，要精心挑选并管理好喂给它的全部信息，让这些信息始终保持在最佳状态。指导原则是：**用最少、最关键的内容，把模型答对的概率推到最高。** 这里"最少"和"最关键"是一体两面——不是给得越多越好，而是要用尽量少的篇幅装下尽量多的有效信息。

### 3.2 一次推理里，context 里到底装了什么

部署一个 agent 时，每次 inference 喂进去的 context 通常包含这些组件：

- system prompt + 行为指令（怎么干活的规矩）
- tool 定义和 schema（有哪些工具可用、怎么调）
- 前几轮的历史对话
- 当前这条轨迹里已经产生的 tool call 结果
- 检索回来的文档或 memory record
- 动态注入的输出格式要求

**关键认知**：这些组件全都挤在**同一份有限的注意力预算**里，互相竞争。多给 tool 定义留 token，就少了留给历史的；多塞检索文档，就挤压了 system prompt 的影响力。

所以 context engineering 的本质动作是：**每一步都对每个组件做"显式选择"——这个要不要进、占多少、放哪——而不是让它们自由累积。** 不管它，上下文就会被工具输出之类的东西无声地塞爆（这正是 §2.3 的腐烂之源）。

### 3.3 三层 memory 架构：组织这一层的框架

§1.2 提的三档时间尺度，对应到 OS memory hierarchy，就成了下面这张贯穿全章的对照表：

| 时间尺度 | OS 类比 | 这一档对应的工具 / 技术 |
|---|---|---|
| Active context window | RAM | system prompt 校准、token-efficient tool、JIT retrieval、KV-cache aware design |
| Session-level state | swap / 文件 | 结构化 note-taking、planning-with-files、cross-run injection |
| Cross-session storage | 持久化磁盘 | MemGPT 类 tiered memory、Mem0、A-MEM、Hindsight、Honcho、cq |

这套三层架构现已成为业界主流的组织方式。下面 §4/§5/§6 依次展开每一档。

## 4. 短期：管理 Active Context Window

> 这一档直接影响**每一次调用**的成本和模型行为——是离模型最近、影响最直接的一层。四个抓手：system prompt、工具设计、按需检索、KV-cache。

### 4.1 System Prompt 校准——找对"高度（altitude）"

设计 system prompt 的核心挑战，是找到对的"高度"——既不能贴地（太具体），也不能飘在天上（太抽象）：

- **太具体** → 把每种情况的处理逻辑都写死。结果是 prompt 又长又脆，环境一变就失效，维护成本极高。比如硬编码"如果文件名是 config.json 就这样处理"——多一种文件名就得改 prompt。
- **太模糊** → 只给"请妥善处理"这种话，等于没给指导，模型只能瞎猜。

**推荐流程（这是原理性的，不是凑数）**：

1. 在**能用到的最好的模型**上，从**最小的 prompt** 起跑。
2. **实测**，看它在哪儿翻车（failure mode）。
3. 针对真实翻车点，**有的放矢地补一条指令**。

为什么不能反过来——事先把所有 edge case 都枚举进 prompt？因为那样只会把 prompt 撑爆（回到 §2 的成本与腐烂），却**不提升可靠性**：你预想的大部分 edge case 模型本来就能处理，写进去纯属浪费 token，还稀释了真正重要的指令。**让真实失败来驱动 prompt 增长，而不是想象。**

实操细节：有效的 system prompt 会用 XML tag 或 Markdown header 把 background / instruction / tool guidance / output format 几块分清楚，而不是糊成一大段。

### 4.2 Token-Efficient 工具设计——工具定义是头号 token 吞噬者

**为什么工具定义这么费 token**：每个工具的 schema、name、description、参数类型，**每一次调用都要重新注入 prompt**。一个大工具集，可能在 agent 还没读到用户请求之前，就先吃掉几万 token。

由此得出核心原则：**少而表达力强，胜过多而窄。**

判断一个工具集设计得好不好，有个朴素但有效的检验：**如果连人类工程师都说不清"这种情况下到底该用哪个工具"，那模型更办不到。** 工具之间职责模糊、互相重叠，模型就会反复选错。

好工具的几条特征：self-contained（自包含，不依赖隐藏的上下文）、对错误鲁棒（参数填错时有明确反馈）、用途明确（一看就知道干嘛的）、参数名利用模型的强项（用模型熟悉的自然命名，而不是 `arg1`/`arg2`）。

> 这一节和 [[02-T-工具接口与协议]] 的"工具少而精"原则是同一件事的两个侧面——Tool 层从"决策质量"角度讲，Context 层从"token 预算"角度讲。

### 4.3 Just-In-Time Retrieval 与 Progressive Disclosure——别预加载，用到再取

**反面做法**：在任务开头，把所有"可能相关"的内容一股脑 load 进 context。问题是大部分都用不上，纯占预算。

**正确做法（progressive disclosure，渐进式披露）**：平时只维持**轻量标识符**——文件路径、一个存储查询、一个 web link——这些只占几十 token。等任务真展开到需要某块数据时，再用标识符把它 load 进来。Anthropic Applied AI Team (2025) 给这个模式起名 progressive disclosure。

**Claude Code 的混合策略是个好例子**：

- `CLAUDE.md` 在 session 开始时一次性 load——因为项目级上下文是几乎每步都要用的，值得常驻。
- `glob`、`grep` 让 agent **在需要时**才去 navigate 和 load 具体文件——单个文件内容不常驻，用到再取。

还有个容易忽略的点：**环境元数据本身就带隐式信号，不必全读进来也能判断。** 文件大小暗示复杂度（一个 50 行的文件和一个 5000 行的文件，处理策略不同）、命名规范暗示用途（`test_*.py` 一看就是测试）、时间戳是相关性的代理（最近改过的文件更可能相关）。agent 可以先看这些"目录信息"做判断，而不是把每个文件都读进来。

### 4.4 KV-Cache Aware Context Design——单一最重要的成本优化

> Prompt caching 是生产级 agent **单一最具成本效益**的优化。但它的收益**完全取决于 context 怎么组织**——组织不当，缓存命中率就会跌到谷底。

#### 先搞懂 KV-cache 是什么、为什么能省钱

LLM 处理输入分两阶段：**prefill**（把整段输入 token 一次性算一遍）和 **decode**（一个一个吐出输出 token）。prefill 阶段，每个 token 都要算出它的 key/value 向量（这就是 "KV"），而**一个 token 的 KV 只取决于它自己和它前面的所有 token**。

推论：如果两次请求的**开头一段完全相同**，那这段的 KV 向量也完全相同——**算过一次就能存下来复用，第二次直接跳过重算**。这就是 prompt caching。

省钱有多狠：Claude Sonnet 上，**cached token 0.30 美元/百万 token，uncached 3.00 美元——差 10 倍。** Manus 团队迭代了五次架构后，把 **KV-cache 命中率定为"生产阶段 AI agent 最重要的单一指标"**。

#### 三条铁律（都从"开头必须逐字节相同"推出来）

缓存复用的前提是"前缀完全一致"，于是：

1. **保持 prompt 前缀稳定。** system prompt 开头哪怕差一个 token（比如插了个当前时间戳），其后**全部**缓存立即失效——因为从那个 token 起后面每个 token 的 KV 都变了。所以别在 prompt 开头放任何会变的东西。
2. **把 context 当 append-only 处理。** 只往后追加，绝不回头修改或删除过去的 action / observation。一旦改了中间某条，从那条往后的前缀就变了，缓存全废。
3. **确定性序列化。** 比如 JSON 序列化时 key 的顺序若不固定，两次"语义上等价"的请求会生成不同的字节串，缓存会**静默失效**（表面照常返回，实际没命中）。要锁死序列化顺序。

#### 一个具体陷阱：加减工具会让整段缓存失效

**工具定义通常排在序列化 context 的最前部。** 根据铁律 1，这意味着——**中途给 agent 加一个工具、或拿掉一个工具，会让其后所有 turn 的 cached 内容全部失效。** 这是个很贵的操作，而"根据情境动态调整可用工具"又是常见需求，矛盾就来了。

**Manus 的解法很巧妙，值得记住**：不去改工具定义列表（那会动前缀），而是用一个 context-aware 状态机，**在 decode 阶段直接 mask 掉那些"当前不可用工具"对应的 token logits**。

拆开讲这个 mask 动作：模型生成 function call 时，要在某一步"挑工具名"。正常它会从所有工具里按概率挑。"mask logits"就是在这一步，把禁用工具对应 token 的概率**强行压到接近 0**，模型就选不到它们了。**关键在于：工具定义在 prompt 里一个字没动（前缀不变、缓存保住），但模型实际能选的范围被收窄了。** 用"挡住选项"代替"删掉选项"，鱼和熊掌兼得。

#### "把概率压到接近 0"到底怎么做到

这一步**在工程层做，不碰模型权重**。要理解它，先看模型是怎么挑下一个 token 的：

1. **算 logit**：模型对词表里每个 token 打一个原始分数，叫 logit（可正可负，量级一般在 ±十几）。
2. **softmax 转概率**：所有 logit 过一道 softmax，变成加起来等于 1 的概率分布，分数越高概率越大。关键性质——**logit 越小概率越接近 0；小到负无穷，概率就是 0。**
3. **采样**：按这个概率分布抽一个 token 输出。

mask 就是利用第 2 步：**在 softmax 之前，把禁用工具对应 token 的 logit 改成一个极大的负数**，它的概率随即归零，模型再也抽不到。改的只是内存里一个浮点数组的几个元素——所以是工程动作，模型本身全程不知情。

**工程上在哪插手**：模型算出 logit 后、采样之前，推理框架留了一个钩子专门让外部改写这个数组（HuggingFace 的 `logits_processor`、vLLM 的 `logits_processors`、OpenAI API 的 `logit_bias`）。流程是：状态机决定这一步禁哪些工具 → 查出工具名对应的 token id → 在钩子里把这些 id 的 logit 压低。

**以 OpenAI 的 `logit_bias` 为例**：它是请求参数，传一个 `{token id: 偏置}` 的 map，偏置范围 −100~+100，直接加到对应 logit 上。`-100` 远超正常 logit 的量级，加完概率几乎归零，等于封禁。用法是先把工具名编码成 token id，再给每个 id 设 −100：

```python
enc = tiktoken.encoding_for_model("gpt-4o")
bias = {tid: -100 for tid in enc.encode("db_query")}  # 禁用 db_query

client.chat.completions.create(
    model="gpt-4o",
    messages=[...],      # 工具定义照旧写在这里，前缀不变、缓存保住
    logit_bias=bias,     # 约束只加在输出端
)
```

两个注意点：

1. **token 级封禁会误伤**：`logit_bias` 锁的是 token，不是完整字符串。如果 `db_query` 的第一个 token 恰好和某个允许的工具共享，会把那个也连带压低。要精确控制得分析 tokenization，或改用下面的高层方案。
2. **更现代的做法是 `tool_choice`**：OpenAI 的 function calling 提供了 `tool_choice` 参数，能直接在工具粒度上指定"只允许 / 禁止哪些工具"，比手搓 `logit_bias` 干净。`logit_bias` 的价值在于它**通用**——任何 token 都能压，不限于工具名（比如禁某个敏感词、强制某种输出格式）。

Anthropic 则通过显式的 `cache_control` breakpoint，在产品层把这套缓存机制暴露给开发者用。

## 5. 中期：Session State 与跨 Run 持久化

> 这一档填补"active context window"和"完整长期 memory 系统"之间的空隙。核心洞见：**只要几百 token 的结构化工作状态，就能跨过 context reset，让 agent 不丢失累积的进度。** 投入小，收益大。
>
> 中期的本质手段是**前向接力**——把关键状态一棒棒往后传给下一段轨迹，而不是建一座能回头按需检索的库（后者才是 §6 长期 memory 的事）。先记住这条机制分界：§5.3 的反直觉例子和 §6 开头的结论都会回到它。

### 5.1 结构化 note-taking——把工作记忆外置到文件

**最简版本**：让 agent 维护一个持久化的 note 文件（典型是 `NOTES.md` 或 `todo.md`）。规则就两条——**run 开始时读它，context 被清空之前写它。**

**为什么有效，有一个极具说服力的实测**：Anthropic 让 Claude 玩宝可梦，连续跑数千个 game step。没有给任何显式的 memory 指令，agent 自己就发展出了——探索区域的地图、战斗策略的胜负统计、跨 context reset 追踪的长期目标。每次 compaction step 把主对话历史清空后，agent 读回自己写的 note，就能继续之前已经进行了好几个小时的训练序列，**不丢失连贯性**。

**关键洞见**：note-taking 的本质是**把 working memory 外置**——agent 把重要内容写到外部 store，需要时读回，**不再依赖对话历史本身去承载 task state**。对话历史会被压缩、被清空、被腐烂，但文件不会。这等于给 agent 配了一个"不受 context window 限制的草稿本"。

### 5.2 File-Based Planning——把整个计划 externalize 到磁盘

note-taking 记的是零散事实，这一节更进一步：把**整个 planning 表示**搬到磁盘上。

- `planning-with-files`——一个持久化的、基于文件的 planning skill 包。
- **Trellis**——管理 project memory 和 spec injection，按每个 step 的需要**选择性注入**（而不是一次全塞进去）。

工作方式：每到一个 milestone，就把 task state、spec、中间结果、dependency graph 写到 filesystem；下一次 run 开始时，**只选择性 load 当前这步真正需要的部分**。这样就绕开了"把目前还不相关的内容也装进 context window"的浪费——和 §4.3 的 progressive disclosure 是一个思路，只是作用在跨 run 的尺度上。

### 5.3 Cross-Run Injection——把上一轮的成果"传"给下一轮

这是个补充模式：**捕获前一轮的显著输出，注入到下一轮的开头。**

- `claude-mem`——一个 plugin 风格的 memory layer：捕获上一段 session 历史，从中提取对后续有用的信息，prepend 到下一段 session 的 context 前面。它**不需要向量库、不需要图 store**，仅靠这个简单机制就提供了大量连续性。
- `everything-claude-code`（GitHub 150K+ star）是这种模式最大的公开集合——它的体量本身就证明了：**中段记忆（mid-tier memory）已经被广泛地用在了生产里**，不是实验室玩具。

**这里有个反直觉、却最能说清本质的点**：claude-mem 明明跨了 session，却仍归在中期、而不是长期。原因恰恰是判据所在——它只是把上一轮的结果**往前 prepend**（前向接力），并没有建一个能按 query 检索的库。**可见中期与长期的分界不在"跨不跨 session"，而在"前向接力，还是索引检索"。**

### 5.4 中期方案的权衡

| 优势 | 限制 |
|---|---|
| 比单纯的 in-window 管理，给出**显著更高的连续性** | 信息只能**前向流动**（这一 run 传给下一 run），**不能按需索引检索** |
| 成本远低于完整的 long-term memory 系统 | 不容易 scale 到海量历史 |
| 简单，贴近现有 coding-agent 的工作流 | 一旦需要"翻很久以前的事"或"精确检索"，就得上长期 tier |

一句话定位：中期方案是"顺手往下传"，便宜好用；但它做不到"任意翻旧账"——那是 §6 长期 memory 的活。

## 6. 长期：Persistent Memory Systems

> 长期 memory 提供**索引化、可检索**的存储，跨 session / task / agent 持久。
>
> **中期 / 长期的真正分界**：不要用"跨不跨 session"这种时间边界来分——中期方案（如 §5.3 的 claude-mem）也能跨 session。真正的判据是**传递方式**：**前向接力**（把状态往后传一棒，传过就过了）→ 中期；**索引检索**（进一个库，日后给一个 query 就能 recall 出任何时候存的相关 memory）→ 长期。中期像传纸条，长期像有索引的档案馆。

### 6.1 三个奠基性架构——记住三个核心思想，而不是三个名字

| 工作                                       | 它贡献的核心思想                                                                                                                                                                                                       |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MemGPT**（Packer et al., 2023）          | **把 OS 的分页思想搬到 memory 上**：LLM 的 context window 当 RAM，外部 storage 当 disk，模型像操作系统一样**显式地把数据在两者间换入换出**。这是"分层 memory"的源头。                                                                                           |
| **Generative Agents**（Park et al., 2023） | **Memory Stream 三件套**：每条 observation 都带 timestamp（何时发生）+ importance score（多重要）；检索时综合三个维度打分——recency（多近）、importance（多重要）、relevance（多相关）；再加上**周期性 reflection**——定期把一堆零散观测合成更高层的 insight（"我注意到这个用户总是赶 deadline"）。 |
| **MemoryBank**（Zhong et al., 2024）       | **借用艾宾浩斯遗忘曲线做主动遗忘**：不重要、不常用的 memory 随时间自然衰减淡出；同时维护层级化的 user-personality summary。让 memory 系统**会忘**，而不是无限堆积。                                                                                                     |

**这三者合起来沉淀出一个标准设计词汇——observation–reflection–retrieval（观测—反思—检索）三件套**，至今仍是 agent memory 的标准骨架：先记下发生了什么，定期反思提炼，需要时按相关性取回。

### 6.2 生产级 memory 系统——每个系统主要解决一个具体痛点

读这张表的正确方式：不要记"有哪些系统"，而是记**"每个系统是为了解决前人没解决的哪个问题而出现的"**。

| 系统                       | 它的核心设计                                                                                                                                        | 它解决的问题 / 工业证据                                                                                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Mem0**                 | **三种后端各管一类信息**：向量库管语义（"意思相近"）+ 图库管关系（"谁和谁有关"）+ KV 库管事实（"确定的值"）。用 LLM 做 extraction，把每条 interaction 路由到对应的后端。                                   | 解决"一种存储装不下所有类型记忆"。证据：1400 万次 Python 包下载、41K star，原生集成 CrewAI / Flowise / Langflow，被 AWS Agent SDK 2025 独家选用；LOCOMO benchmark 上比 OpenAI 原生 memory **准确率高 26%、token 用量少 90%**。 |
| **A-MEM**                | **Zettelkasten（卡片盒笔记法）启发的动态知识网络**：存的不是一条条扁平 record，而是带 keyword / tag / 上下文描述 / 动态 link 的结构化 note；**每新增一条 memory，就回头更新相关的旧 memory**。           | 解决检索系统的一个根本毛病——**写入时根本看不出一条信息有多相关**，它的价值往往要等后来的 memory 出现、和它建立关系后才显现。A-MEM 用"回填更新"补上了这个时间差。                                                                                  |
| **Hindsight**            | API 就三个操作：`retain`（留存）/ `recall`（取回）/ `reflect`（反思）。内部有一条 reasoning pipeline：提取带时间的实体、去重重叠的事实、构造**有证据支撑的** knowledge record。                  | 它把 memory 从"记住（remember）"重新表述为"学习（learn）"——不只是存原文，而是消化成结论。LongMemEval 上达到 state-of-the-art。                                                                                  |
| **Honcho**（Plastic Labs） | **构建用户的"模型"，而不是事实的集合**。有一条异步的 reasoning pipeline 在持续"做梦"——从过去交互里提取**推断性结论**（这个用户的偏好、沟通风格、目标），而不只是记录原话。                                        | 它的 entity-centric 数据模型天然支持多 agent 环境——每个 agent 有自己的观察视角，但**共享同一个 user model**。                                                                                               |
| **cq**（Mozilla AI）       | **跨 agent 实例的共享 memory**。大部分 memory 系统是 per-agent / per-user 的，导致多个 agent 各自重新踩别人已经踩过的坑。cq 是 **MCP-native**，分三层（本地开发机 / org 共享 / cross-team）。 | 解决"经验无法在 agent 之间共享"。典型模式：post-error hook——某个 agent 遇到错误时，cq 自动去查共享知识库，**防止同一个失败在不同部署里被反复独立踩中**。                                                                             |

### 6.3 学术分类——给这个领域建坐标系

这几篇 survey 的价值在于提供"看待 memory 的坐标轴"：

- **Zhang et al. (2025) memory mechanism survey**——区分 short-term / long-term；long-term 再细分 semantic（语义事实）/ procedural（操作流程）/ episodic（具体经历）。它确立了 **write-read-manage loop（写—读—管理 循环）** 这个标准词汇。
- **Du (2026) survey**——把 memory 形式化为 POMDP 风格 agent cycle 里的一个循环，提出三维分类（scope 范围 / format 格式 / compositional structure 组合结构），并描述三种工程 pattern：**A 单一 monolithic context**（全塞一个窗口）、**B context window + retrieval store**（窗口 + 检索库）、**C tiered memory + learned control policy**（分层 memory + 学出来的调度策略）。这三种 A/B/C 恰好对应本章的短 / 中 / 长期。
- **Gao et al. (2023) RAG survey**——retrieval-augmented generation 的背景综述，是检索这条线的理论底座。

## 7. 长程技术（维持 100+ turn 的 coherence）

> 前面 §4/§5/§6 各管一个时间尺度。但真正的 long-horizon 任务——大代码库迁移、跨多个 session 的研究、长时间自治的 workflow——需要**同时协调三层**，并且实时决定"此刻该用哪种技术"。这一节讲跨尺度协调的几个手段。
>
> **先消除一个误解**：§7 不是独立于前三章的新主题，而是它们的**调度层**——它不发明新的存储方式，只是在长任务运行时动态编排已有手段：§4 的**即时加载**（按地址把数据 load 进窗口）、§5 的**外置接力**（写文件、下轮读回）、§6 的**索引召回**（按 query 从持久库搜回），按当下情况决定该压缩历史、该派子 agent、还是该回查长期记忆。一句话，§4–6 回答"信息存哪一档"，§7 回答"长任务里怎么把这几档协同起来用"。

### 7.1 Context Compaction（上下文压缩）

**做法**：当上下文逼近窗口上限时，把当前 context **总结**成一个压缩表示，然后用这个压缩版**重启执行**——相当于给 agent 做一次"长话短说"。

**校准挑战在哪**（Anthropic Applied AI Team, 2025）：总结时，**该留的必须留，该扔的必须扔**——

- **必须保留**：架构决策、还没解决的 bug、关键实现细节。
- **可以丢弃**：冗余的 tool 输出、已经被吸收进结论的中间推理。

难就难在分辨这两类。**推荐的调优流程是有方向性的，方向反了会出大事**：

1. **起步阶段：最大化 recall**——先把轨迹里**所有可能相关**的东西都保留下来（宁可多留）。
2. **迭代阶段：删冗余、提 precision**——再逐步把确认无用的删掉。
3. **绝对不能反着来。** 如果一开始就激进地删，agent 会丢掉"当时看着没用、后来才发现需要"的 context——而且**这种丢失不可恢复**（信息已经不在了，没法再捞回来）。所以宁可先多留再删，不可先删了后悔。

**Tool result clearing 是最轻量的 compaction**：一旦 agent 已经根据某条 tool 输出采取了行动，就把那段原始 output 替换成一个简洁的路径引用（"结果见 path/to/x"）。这个动作可以连续反复用，现在已经是 Anthropic 开发者平台的产品级 feature。

> 工程落地实例：[[上下文压缩方案研究]]——其异步压缩 + 5 级管线 + anchor 物理保护，正好对应本节"该留必须留、该扔必须扔"的校准难题（它用规则锚定 task 状态、只把非结构化内容交给 LLM 摘要）。Pi 的具体 compaction 实现见 [[07-Compaction-上下文压缩]]、[[24-AgentEvent-订阅模型与-Compaction-子系统]]。

### 7.2 Sub-Agent Context Isolation（子 agent 上下文隔离）

**问题场景**：某个子任务需要深入探索（比如"在这个大 repo 里搞清楚 auth 模块怎么工作"）。探索过程会产生**大量中间 context**——读了几十个文件、试了好几条线索。这些中间过程对**做这个子任务**有用，但对 orchestrator（主控 agent）的**整体视图是纯污染**——主控并不需要知道你翻了哪些文件，只需要结论。

**解法**：把子任务委派给一个独立的 sub-agent，**每个 sub-agent 有自己全新的 context window**，干完只返回一份 1,000–2,000 token 的浓缩 summary。中间那一大堆探索过程，留在 sub-agent 的窗口里，不污染主控。

两种粒度：

- **简单子任务**：context 完全不共享，sub-agent 从零开始。
- **复杂子任务需要共享 state**：把 orchestrator 的完整 context 传给 sub-agent。

**但共享 context 在 agent 之间是昂贵的**，得权衡：传完整 context 意味着更大的 prefill 开销，而且 sub-agent 的 system prompt 和主控不同，**两者之间无法复用 KV-cache**（回到 §4.4——前缀不同，缓存就用不上）。所以**每一类任务都得显式地算一笔账**：隔离省下的"防污染"收益，对不对得起共享 context 的"协调成本"。

### 7.3 Hybrid Decision Frameworks（混合决策框架）

**核心事实**：真实的生产部署，**从不"用一种技术统一打天下"**，而是在执行过程的不同节点、按任务结构选不同技术：

- **总是需要**的内容 → 预加载（如 CLAUDE.md）。
- **只在特定条件下需要**的 → just-in-time 检索（§4.3）。
- 窗口**接近饱和**时 → compact history（§7.1）。
- 子任务探索**会污染主控**时 → spawn sub-agent（§7.2）。

**Harness 层的视角（这是本节的落点）**：context management **应当是基础设施（harness）的职责，而不是模型自己的职责。** 当 harness 自动处理 compaction 和 consolidation，模型才能腾出注意力**专注在 task reasoning 上**——而不是一边干活一边操心"我的上下文是不是快满了"。让基础设施管内存，让模型管思考。

## 8. Context Drift（上下文漂移）——当前最难的开放问题

### 8.1 先把 Context Drift 和 Context Rot 区分清楚

这两个词长得像，但是**两个不同层面的东西**，混了就全乱：

| 性质    | Context Rot（腐烂，§2.3）                   | Context Drift（漂移，本节）                            |
| ----- | -------------------------------------- | ----------------------------------------------- |
| 是谁的属性 | **单个 inference step** 的属性              | **整条扩展 trajectory** 的属性                         |
| 怎么触发  | 给定一份固定 context，token 一多，这一步的检索/推理质量就退化 | 跨 turn 持续累积，行为**渐渐偏离**最初的意图                     |
| 表现    | 一次调用就答错了                               | 100+ turn 之后，**重复做已经做完的工作、和早前的决策自相矛盾、忘掉最根本的动机** |
| 能否治   | compaction / 检索能缓解                     | compaction / 检索能**减缓，但无法阻止**                    |

简单说：rot 是"这一口没吃好"，drift 是"走了很远之后发现整个方向歪了"。

### 8.2 Drift 的根因——长程上的小误差被累积放大

很容易以为 drift 就是"窗口装满了导致的"，但这个归因太浅：**即使窗口永远够用、或做了激进的 compaction，drift 照样发生。** drift 的本质不是"装不下"，而是——**长程上每一步的小误差被一步步累积、放大**。就像反复转述一句话，每次只走样一点点，传到第 50 个人嘴里已经面目全非。

这种小误差至少有三个来源，叠加在一起把轨迹一点点带偏：

1. **单步 rot 的累积。** §2.3 的 context rot 是"这一步偏一点"；长任务里这样的步有几百个，每步都因 context 变长而判断略有退化，攒起来就成了整条轨迹的偏离。**rot 正是 drift 的微观成因之一**——前者是单步的病，后者是这病在长程上的累积。
2. **compaction 的有损误差。** 每一次 compaction step 留下的 summary 都带细微的 inaccuracy（不精确），一次次压缩叠加，误差复合放大。注意这条的两面性：compaction 既**拦不住** drift（因为来源不止它一个），自己还**额外制造** drift（主动丢信息、掺进不精确）——它是来源，不是解药。这条来源有一个干净的工程解法：把"每轮全量重写旧摘要"（fold）改成"只摘增量"（append-only），单个事实的重写次数从 O(压缩轮数) 降到摊还 O(1)，复合放大的乘法因子被砍掉——见 [[上下文压缩方案研究]] 第四节。
3. **没有纠偏机制。** 当前架构里，没有任何东西在检测这种 divergence（偏离）。误差只进不出，没人喊"停，你已经跑偏了"。

所以 drift 不是单一原因造成的，更不是"主要由 compaction 引起"——它是 rot、有损压缩、缺乏监测三者合力，在长程上把累积误差放大的结果。

### 8.3 评估缺口——现有 benchmark 测不到 drift

**标准 benchmark 评估的都是"几十个 step 内就完成的任务"**——而 drift 是 100+ turn 之后才浮现的 failure mode，**根本没被这些 benchmark 捕获**。最近的工作开始补这个缺口：

- **MemBench**（Tan et al., 2025）——评估跨多 session 场景的 memory 质量：temporal reasoning（时间推理）、knowledge update（知识更新）、cross-session aggregation（跨会话聚合）。
- **MemoryArena**（He et al., 2026）——专门针对**相互依赖的多 session 任务**，这正是 context drift 最具破坏性的条件。
- **Hu et al. (2025b)**——提出 incremental multi-turn 的评估方法学，**把 memory 质量从 generation 质量里隔离出来单独测**（否则分不清是记错了还是单纯答得差）。

但要警惕一点：**这些 benchmark 必要但不充分**——它们能**证明 drift 确实发生了**，却**给不出"怎么防止它"所需要的机理理解**。能测出病，不等于会治病。

### 8.4 为什么现有技术都不够

逐个看 §7 的三大技术，都各有死角：

- **Compaction**：能减少 token 数，但**不保证压缩后的表示准确捕获了所有相关 state**——每次压缩丢掉的信息，是真丢了。
- **Retrieval**：能浮出相关的历史 memory，但前提是 **query 得"问得好"**——而一个正在 drift 的 agent，恰恰**不知道自己该检索什么来纠偏**（它都不知道自己偏了）。
- **Sub-agent isolation**：能防子任务污染主控，但**主控自己的 context 照样在累积 drift**。

**Bowne-Anderson & Huber (2026) 的论断**：这些限制共同划出了一条边界——**context engineering 单靠自己，解决不了 long-horizon 的可靠性问题。**

那需要什么？需要一套**完整的 harness 层**来兜底：verification loop（验证回路）、在关键节点插入的 human-in-the-loop checkpoint（人工检查点）、能识别 behavioral divergence 的 anomaly detection（异常检测）。这就是为什么 [[05-O-可观测性与运维|Observability 层]] 和 [[07-G-治理与安全|Governance 层]] 是 context engineering 的**必要补充，而不是分离的关注点**——光管"喂什么给模型"不够，还得有人盯着"模型是不是跑偏了"。

## 9. 本层小结

### 9.1 三层架构对应表

| 时间尺度 | 解决的核心问题 | 代表技术 |
|---|---|---|
| **短期（active window）** | 单步的效率与可靠 | system prompt altitude、token-efficient tool、JIT retrieval、KV-cache 友好序列化 |
| **中期（session state）** | 跨 turn / 跨 run 的连续性 | NOTES.md / planning-with-files / Trellis / claude-mem / cross-run injection |
| **长期（cross-session）** | 真正的记忆与学习 | MemGPT / Mem0 / A-MEM / Hindsight / Honcho / cq |

### 9.2 三个反复出现的工程约束

1. **窗口大不解决 memory 问题**——平方注意力（贵）+ U 形曲线（位置敏感）+ context rot（50K token 处就开始烂）三条叠加，逼出"上下文必须主动工程化"。
2. **KV-cache hit rate 是单一最重要的成本指标**——它驱动了三条纪律：prompt 前缀稳定、append-only、确定性序列化。
3. **Long-horizon 可靠性需要跨层补救**——context engineering 是基础，不是终点；剩下的 drift 缺口要靠 Observability / Verification / Governance 层补。

### 9.3 承上启下

Context 层的限制（尤其 §8 的 context drift）把综述推向了下一组层——**控制面（control plane）**：它们把 reliability 当成一个可以被**独立监控、评估、约束**的属性来对待。也就是说，"把信息喂对"之外，还需要专门的层来"盯着 agent 别跑偏"。
