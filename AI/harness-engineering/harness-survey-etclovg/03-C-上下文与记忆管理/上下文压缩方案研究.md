## 一、问题与两个约束

**一句话**：在对话历史撑爆上下文窗口之前，把旧内容压掉，同时保证任务状态一个字都不丢。

难点不在"压"，而在两个约束的夹缝里压：

1. **压缩要调 LLM，慢**——不能卡住用户当前这轮对话。
2. **任务不能丢**——单 session 里可能并行好几个 task（查天气、订会议室、查航班），压缩绝不能弄丢任何一个 task 的 id / 状态 / 结果。

三家 harness 都在解这同一个问题，做法各有侧重，但收敛出的最优解高度一致。整篇按"何时压 / 压什么 / 怎么压 / 怎么不崩"四段展开。

```text
                token 用量
                   │
        ┌──────────┴───────────┐
   软阈值(触发压缩)          硬限制(窗口天花板)
        │   ◄─── 安全区 buffer ───►  │
   触发后台压缩              当前轮照常跑完
        │
        ▼
   压缩在后台进行（不阻塞当前对话）
        │
        ▼
   下一轮：压缩结果自动顶替旧历史
```

## 二、最优方案总览

骨架四段，每段给一句话最优解：

| 段 | 问题 | 最优解 |
| --- | --- | --- |
| **何时压** | 压缩慢，不能卡对话 | 判断与执行分开：判断每次调用前都做（廉价）；执行排三道防线——提前异步 → 临调用同步 → 撞墙被动 |
| **压什么** | 关键状态不能丢 | 结构化走规则物理保护、非结构化才交给 LLM 语义压缩 |
| **怎么压** | 既要压得多又要质量高 | 递进管线：无损清理 → 可逆外置 → 有损摘要 → 硬截断，每级查预算、够了就停 |
| **怎么不崩** | 反复摘要会磨损事实 | append-only / 保留边界：老段封存、只摘增量，杜绝迭代重写 |

三家在这四段上的定位：

| harness | 何时压 | 怎么压 | 独到之处 |
| --- | --- | --- | --- |
| **sigma** | 每 turn 开头判定；异步软阈值后台压 + 同步硬限制截断兜底 | 5 级管线 | 异步不阻塞、重要性三级分级、漂移分析最透 |
| **Claude Code** | 每次模型调用前逐级前置治理 + 流式中撞 PTL 的 reactive 三层恢复 | microcompact → context collapse → autocompact | 粒度最细、collapse 的 staged/commit 恢复余量 |
| **Pi** | loop 之外（turn 间）判定；threshold 主动 + overflow 撞错重试 | tool result 截断 → LLM 摘要 | Split turn 切入单 turn 内部、累计文件读写追踪 |

下面四节逐段给最优解，并标注各家落地。

## 三、何时压：判断与执行分开（分离一）

压缩要调 LLM、慢，核心矛盾只有一个：**压缩延迟 vs 不能卡住对话**。分离一的本质就是对它的回答——把"判断要不要压"和"实际执行压缩"拆开：判断廉价，可以每次都做；执行昂贵，要分多道防线躲开关键路径。下面先看判断、再看执行，三家所有触发设计都是这条原理的推论。

### 3.1 判断：廉价，所以每次调用 LLM 前都做

判定依据是**实际 token 用量**逼近窗口的程度，而非轮次计数。判断本身极廉价（字符数估算、微秒级），所以最优粒度是**每次调用 LLM 之前都估一遍**——一个 turn 内主循环会多次调用 LLM、每次都把新的 tool result 累积进上下文，只在 turn 开头判一次会留下"单 turn 内瞬间撑爆"的盲区。

> [!info] 检查 ≠ 执行
> "每次调用前都判一遍"指的是**检查**每次都做，不是每次都真压。检查只是估个 token，没超预算就直接放行（多数时候如此）；超了才进入下面的执行环节。所以"每次都判"几乎没有成本。Claude Code 的 `snipCompactIfNeeded` / `applyCollapsesIfNeeded` 命名就是这个语义。

### 3.2 执行：昂贵，所以排成三道防线

判断触发后，压缩怎么执行才不卡对话？按"离关键路径由远到近"排成三道防线，层层兜底——前一道漏了后一道接：

**第一道 · 提前异步压**（最优）。用量一过软阈值（如窗口的 70%）就在**后台**启动压缩，当前轮靠剩下的安全区跑完，结果**下一轮**才顶替旧历史。压缩延迟完全不在关键路径上、零阻塞。这是 sigma 相对另两家同步压缩的优势。

> [!info] 异步带来的"多轮生命周期"
> 异步压缩天然跨多个 turn，状态机如下（节点用概念词，非代码符号）：
>
> ```text
> 第 N 轮：用量超软阈值 → 拍历史快照、后台开压；本轮仍用原始历史
> 第 N+1 轮：还在压 → 跳过重复触发；仍用原始历史
> 第 N+2 轮：压完 → 命中缓存
>           → 拼接[压缩后的旧历史] + [N+1、N+2 两轮的新消息] → 交给模型
> ```
>
> 这一道的触发判定每 turn 一次即可（压的过程中跳过重复触发）；turn 内更细的保护交给下面第二道。

**第二道 · 临调用同步压**。异步有窗口期（后台还没压完），而且不是每家都具备异步能力。所以在**每次调用 LLM 之前**再同步走一遍管线：超预算就地压、没超直接放行（多数空过）。它粒度最细，专补第一道盖不住的"单 turn 内爆窗"盲区；代价是真要压时会阻塞这次调用，但因"够了就停"成本可控。Claude Code 的 query loop 就是每次调用前同步跑一遍递进治理。

**第三道 · 撞墙被动压**（最后保命）。token 估算难免漏判，请求真的因上下文超限失败时（provider 返回 overflow / HTTP 413），就**捕获错误、就地压、重试**，而不是直接失败：

- Pi 的 `overflow` 触发：撞错 → 压缩 + 移除出错的最后一条消息 → 重试。
- Claude Code 三层递进：collapse drain（暂存折叠一次性生效，最廉价）→ reactive compact（调模型摘要）→ truncateHead（连摘要请求都超窗时砍最早的对话），越往后越狠。
- sigma 的同步硬限制截断（超窗就地极速截断保命）是这道的轻量版。

> 三道防线没有哪家全占：sigma 有第一、三道、缺第二道（这正是它"单 turn 内盲区"的来源），Claude Code 占第二、三道，Pi 以第三道为主。最优方案是三道都上、层层兜底。

### 3.3 一个特例：单 turn 过大 → Split turn

上面的切分点默认落在 turn 边界（一个 turn = 一次用户输入触发的完整主循环，含其后所有 assistant / tool 消息）。但**单个 turn 自身就超过保留预算**时，必须允许切分点落到 **turn 内部**的合法位置——这是 Pi 的 **Split turn** 机制：

- 切分点可落在 turn 内的 user / assistant 消息上，对 turn 前缀单独摘要、再与历史摘要合并。
- **铁律：绝不切在 tool result 上**——tool call 与它的 result 必须配对保留，否则模型看到一个没有结果的调用会错乱。

## 四、压什么：结构化物理保护，非结构化语义压缩（分离二）

"任务零丢失"的真正机理，是按"**能不能赌 LLM 摘要时记得带上**"把信息分两类，给两种根本不同的保住方式：

| 信息类型 | 例子 | 保住方式 | 机理 |
| --- | --- | --- | --- |
| **结构化** | 子 agent 的创建 / 状态 / 工具结果、task id | **物理保护**——纯规则识别，原样保留、不进压缩管线 | 一个字节都不改、不调 LLM，"硬"留原文本身 |
| **非结构化** | 用户意图、上下文、决策过程 | **语义压缩**——送进压缩管线，最深一级才交给 LLM 摘要（见 §5） | 交 LLM 重述，措辞会变、可能漏，"软"留转述版 |

**灵魂一句：关键状态能用规则确定性保住，就绝不交给 LLM 摘要的"自觉"。** 结构化状态丢一个 task id 就可能让整条任务断掉——这种东西不能赌概率，必须走"硬"的一侧。

所以物理保护的工程核心，是**怎么用纯规则圈出"碰到就跳过"的那批消息**。三家各有锚定方式：

- **sigma — anchor**：把 task 相关消息标成 anchor（tool call 名为 `agent` 的消息、按 `agent_id` 分组的事件、命中 anchor 的 tool 消息），管线各级一律跳过、原样保留。所有实验里 anchor 完整性始终 **100%**。
- **Claude Code — tool 配对**：锁定 tool call 与其 result 一起留、绝不拆散——拆了模型会看到一个没有结果的调用而错乱。
- **Pi — 文件读写追踪**：摘要时累计记录 read-files / modified-files 清单，多层嵌套摘要也不丢这份账。

> [!info] 物理保护与摘要的分工
> 两侧要划清边界：prompt 里明确告诉摘要 LLM「不必复述已被物理保护的内容」。否则 anchor 原文与摘要转述两头重复保留，白白烧 token。

## 五、怎么压：递进管线（无损优先，够了就停）

承 §4：锚点（结构化）已被物理保护、不进管线，本节只谈**剩下的非结构化部分如何逐级压**。三家最强的共识是**按代价从低到高排级、每级查预算、够了就停**——先零成本无损清理，再可逆外置，最后才上有损 LLM 摘要；绝大多数会话停在前几级，根本走不到摘要。下图是骨架、表是三家对照，随后逐级展开。

```text
（前提·见 §4）锚点不进管线，下面每一级遇到就跳过
   │
   ▼
① 清理碎片         →  小 tool result 占位 / 删配对    ┐ 无损
   │  预算够? → 停                                    ┘
   ▼
② 可逆外置 / 折叠   →  大内容换成 链接/短摘要，可还原    ←  可逆
   │  预算够? → 停
   ▼
③ 有损摘要         →  重要性分级 + CoT + 结构化段落     ←  有损
   │  预算够? → 停
   ▼
④ 硬截断到最近若干轮 →  兜底
```

三家管线对照（同一套递进，只是命名与粒度不同）：

| 级别        | sigma                      | Claude Code                     | Pi                      |
| --------- | -------------------------- | ------------------------------- | ----------------------- |
| 清理碎片（无损）  | ①清小 tool result ②删 tool 配对 | microcompact（清陈旧 tool result）、history snip | tool result 截断到 2000 字符 |
| 可逆外置 / 折叠 | ③归档外置（Redis + 链接）          | context collapse                 | （并入截断）                  |
| 有损摘要      | ④重要性感知摘要                   | autocompact                     | LLM 摘要                  |
| 硬截断（兜底）   | ⑤硬截断到最近若干轮                 | truncateHead                    | keepRecent 边界           |

### 5.1 清理碎片（无损）

一次工具调用在历史里是**两条消息**：assistant 发出的「调用」（tool call）+ tool 返回的「结果」（result）。最便宜的清理就是对这对消息下手：

- **清 result**：把"结果"挖空成占位符，保留"调用"那条。模型仍看得到"查过北京天气"，只是拿不到具体数据。
- **删配对**：把"调用 + 结果"整对删掉，连痕迹都不留。

之所以无损：旧的小工具结果 agent 早已消化、后续基本不再回看。**只动小的**——大结果留给下一级外置（可还原），避免无脑删掉还可能要用的大块数据。

Claude Code 的 **microcompact** 就是这一级的落地：逼近上下文上限前自动清掉早已消化的旧 tool result，不调 LLM、不动对话主体，与 sigma 的「清小 tool result」同类。

### 5.2 可逆外置 / 折叠（把"有损"变"可逆"）

超过阈值的大 tool result 不直接删，而是**换成一个可还原的短表示**——这是"删之前先留后路"的思想，三家各有实现：

- **sigma 归档外置**：大 result 存入外部存储（Redis），原消息替换成"链接 + 一句话摘要"。需要原文时按链接取回；存储与 session 同寿，过期后取回返回友好提示，LLM 可继续工作。这套"外置 + 引用 + 按需取回"是业界通行模式（Manus 有公开阐述，见 §8.2），sigma 是用 Redis 把它落地。
- **Claude Code context collapse**：把单条旧大消息替换成**本地按工具元数据拼的模板短摘要**（如"读了 auth.ts，180 行，含 JWT 配置"），**不调 LLM**。原文留在完整历史里不动，只在**读取时投影**出替换后的视图（read-time projection）。
- **Pi**：送摘要 LLM 时把 tool result 截断到 2000 字符并标注截掉多少。

> [!tip] context collapse 的精彩设计：staged / commit 当恢复余量
> Claude Code 的折叠分两阶段（借 git 概念）：平时每轮算好可折叠消息的替换方案但**只暂存（staged）不应用**，故意保留更完整的上下文；真撞上 prompt-too-long 时再把所有暂存折叠**一口气生效（commit）**，瞬间释放空间后重试。把"该折叠但还没折叠"的部分当成**预留的恢复余量**——这正是第三道防线（撞墙被动压）的第一层。

关键共性：可逆外置都是**确定性、不调 LLM、可还原**的，介于无损清理和有损摘要之间。能靠它解决就不必上摘要。

### 5.3 有损摘要（最复杂的一级，也是三家共识最强的一级）

只有极端长对话才会走到这一级。三家的摘要做法收敛出三个机制，正好串成一条线——**留什么**（重要性分级）→ **怎么摘才不漏**（CoT 草稿）→ **摘成什么形状**（固定段落结构），再加一个旋钮统管**留多少**（双重控制）：

**(1) 重要性分级**（sigma，最细）——核心前提"并非所有上下文同等重要"：

| 级别 | 内容 | 丢了会怎样 |
| --- | --- | --- |
| **HIGH**（原文/近似保留） | 用户指令、纠正与偏好变化、用户反馈、决策及理由、具体数据值（姓名/日期/URL/代码） | agent 与用户矛盾、回退错误信息、幻觉、重复劳动 |
| **MEDIUM**（压成要点） | 影响决策的工具结果、中间推理、背景上下文、澄清交流 | 保留结论、去掉原始数据即可 |
| **LOW**（直接省略） | 寒暄、冗余确认、冗长工具输出、重复信息 | 不影响后续行为 |

**(2) CoT 草稿**（sigma + Claude Code 都用）——核心手法是**不让模型直接吐摘要，先逼它把推理过程写出来**：先在 `<analysis>` 里把消息按时间线逐条复述一遍（草稿纸），再在 `<summary>` 里写正式摘要，事后剥离 `<analysis>` 只留 `<summary>`。直接写摘要容易"扫一眼就下笔"、漏掉埋在中间的用户纠正；强制先逐条过一遍再总结，遗漏率显著下降。sigma 的消融实验显示：每个压缩档上开 CoT 都比不开准确率更高（+0.2~+6.2pp）。

**(3) 固定段落结构**（三家共识）——给摘要一副固定骨架，每段防一种特定退化，也方便下次 review 和 LLM 消费：

| sigma（6 段） | Pi（6 段） |
| --- | --- |
| 对话摘要 / 用户消息 / 关键事实与决策 / 错误与修复 / 当前工作 / 待办事项 | Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context |

Claude Code 的 autocompact 摘要也是同款多段结构（Primary Request、Key Concepts、Files、Errors & fixes、Pending Tasks、Current Work 等），并配 `<read-files>` / `<modified-files>` 块。**段落里普遍专门留一段记"被否决方案及原因"和"踩过的坑 + 用户对修复的反馈"，防重复提议、防重蹈覆辙。**

> [!tip] 压缩力度的双重控制：prompt 管留什么、token 上限管留多少
> 一个百分比旋钮（压缩档位）同时驱动两套控制：**定性**——按档位调重要性分级指令的力度（管保留什么）；**定量**——按档位算出摘要输出的绝对 token 上限（管保留多少）。两套缺一不可：没 prompt，LLM 把 token 浪费在 LOW 内容上；没 token 上限，LLM 干脆无视压缩目标。

## 六、怎么不崩：抗摘要漂移（append-only / 保留边界）

§5.3 解决的是"单次摘要怎么摘得好"；但摘要这一级会被**反复触发**——由此引出整套方案里最反直觉、也最值得记住的一点。

**问题**：若每轮压缩都把上一轮的摘要**折回原文一起重写**（fold），那么第 N 轮压缩后，最早的事实已被 LLM 重写过 N 次——**重写次数是漂移的乘法因子**，事实被逐轮磨没。sigma 的数据很硬：单轮压缩近无损（LongMemEval_s：62 ≈ 全量 68），但压到约 12.6 轮就崩到 22，连纯检索基线 44 的一半都不到；逐题剖析确认根因是"反复重写"而非"单次有损"。

**解法：fold（每轮全量重写）→ append-only（只摘增量）。**

```text
旧做法（fold，每轮全量重写）:
  round 2: [S₁ + 新轮次] 全部重摘 → S₂     ← 老事实被重写第 2 次
  round 3: [S₂ + 新轮次] 全部重摘 → S₃     ← 老事实被重写第 3 次

新做法（append-only，只摘增量）:
  round 2: S₁ 逐字保留, 只摘新轮次 → [S₁, S₂]
  round 3: 同上                    → [S₁, S₂, S₃]
  段太多超预算: 只合并最老的一半段（仅此一次重写）→ [S₁₋₃′, S₄, …]
```

效果：单个事实的重写次数从 **O(压缩轮数) 降到摊还 O(1)**（只在段合并时重写一次）。这也点破一个常见误区——漂移 = 单次失真 × 重写次数，**次数才是主因**；"嘱咐 LLM 保留原措辞"只压得低单次失真、砍不掉次数，唯有 append-only 把次数砍到 1 才是治本。

三家其实都带这个"保留边界、不重复重写老内容"的思想，只是 sigma 讲得最透：

- **Pi**：重复 compaction 时，被压区间起点是**上次的保留边界**（`firstKeptEntryId`）——上次幸存下来的消息这次不会再被压。
- **Claude Code**：每轮从 **compact boundary 之后**取消息——压缩点之前的内容已被摘要替代，不再二次重写。

> [!warning] append-only 的实现坑：快照别算"在途轮"
> 每段一辈子只摘一次——某段当初没摘全，以后没有任何一轮会回头补它，等于永久丢失。所以拍快照时**别把"在途轮"（当前回复还没落库的那轮）算进去**，否则水位线判它已覆盖，稍后写入的回复就被永久漏掉。

## 七、可迁移的设计原则

把三家的最优解抽成通用原理，后半句括注各家落地：

1. **判断与执行分开**——判断廉价（每次调用 LLM 前都估一遍 token），执行昂贵（要躲开关键路径）。这是"何时压"的总原理。（三家共识）
2. **执行排三道防线、层层兜底**——提前异步（过软阈值就后台压、零阻塞，最优）→ 临调用同步（每次调用前走一遍、补单 turn 盲区）→ 撞墙被动（撞窗口错误再压重试）。（sigma 占一、三道；Claude Code 占二、三道；Pi 以三道为主——最优是三道都上）
3. **递进式管线、无损优先**——按代价从便宜到贵排，每级查预算、够了就停，多数会话停在前几级。（三家共识）
4. **结构化物理保护、非结构化语义压缩**——关键状态别赌 LLM 摘要的自觉，走规则确定性保留。（sigma anchor；Pi 文件追踪；Claude Code tool 配对）
5. **外置 + 取回闭环**——把"删除"变"可逆"：外置/折叠 + 留指针 + 能还原，且不调 LLM。（sigma 归档 Redis；Claude Code context collapse 的 read-time projection 与 staged/commit）
6. **重要性分级 + 双重控制**——prompt 管留什么、token 上限管留多少。（sigma HIGH/MEDIUM/LOW + 输出 token 硬上限）
7. **CoT 草稿提升摘要质量**——先逐条过一遍再下笔，事后剥离草稿。（sigma + Claude Code 都用 `<analysis>`/`<summary>`）
8. **固定段落结构**——每段防一种退化，专设"被否决方案""踩过的坑"段。（sigma 6 段 / Pi 6 段 / Claude Code 多段）
9. **单 turn 过大要能切入内部**——切分点优先 turn 边界，超预算就落到 turn 内合法位，绝不切 tool result。（Pi Split turn）
10. **警惕迭代重写漂移**——摘要的摘要 = 事实磨损器；append-only / 保留边界把重写次数砍到摊还 O(1)。（sigma fold→append-only；Pi firstKeptEntryId；Claude Code compact boundary）
11. **非破坏性**——压缩只读原文、另产副本/投影，从不就地改原文；原始历史始终是兜底数据源。（三家共识：sigma 压缩副本、Claude Code read-time projection、Pi CompactionEntry 追加）
12. **快照排除在途状态**——对"正在写入"的轮做快照会丢数据，append-only 下尤其致命。（sigma 快照排除在途轮）

## 八、效果数据与业界对标

### 8.1 效果数据（sigma 内部实验，三家中唯一有公开口径数据者）

> 数据均为 sigma 内部实验：用公开基准 LongMemEval / LoCoMo / CAME-Bench 跑自家管线。非学术论文结论，作为方案有效性的佐证。

**一个反直觉结论：超长对话里，压缩是纯增益。**

| 对话规模 | 关键现象 |
| --- | --- |
| **超长（>100K tokens）** | 所有压缩档都**优于不压缩**。LLM 在超长上下文"大海捞针"会失败，压缩提升信息密度后反而定位更准 |
| **中等（<30K tokens）** | 40% 以下基本无损，超过约 30% 实际压缩率后质量骤降 |

LongMemEval（~163K）实测：compress_40 准确率 62.2%，比不压缩高 +13.4pp，TTFT（首字延迟）最高减半；LoCoMo（~29K）则相反，compress_90 掉 28pp。

**档位建议**：< 30K 不压或轻度（≤20%）；30K–100K 标准（40–60%）；> 100K 积极（60–90%）。

**与 Agent Memory 叠加**（CAME-Bench 960 queries）：Agent Memory 是核心收益（Resolution 55%→77%），Compact 在没有 Memory 时价值更大，两者叠加最优（Resolution 82%、State Alignment 77%）。
