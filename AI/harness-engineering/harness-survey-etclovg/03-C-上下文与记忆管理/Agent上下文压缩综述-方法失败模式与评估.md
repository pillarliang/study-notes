## 这篇综述要解决什么

一句话：**LLM 从"答一句话"变成"自己跑一长串任务的 agent"之后，上下文不再是一次喂进去的静态文档，而是一条只增不减的交互轨迹；怎么在固定的上下文预算里管住这条轨迹，成了系统级的核心难题。**

综述把这个原本零散的领域收进一个统一框架，做了三件事：

1. **三维分类法**——任何一种压缩方法，都能用三个问题定位：压什么（target）、怎么压（mechanism）、谁决定何时压（control policy）。
2. **三类失败模式**——按"最早在哪一步出错"，把压缩引发的下游故障分成 F1 / F2 / F3。
3. **评估反思**——指出"只看任务成功率"判断不了压缩好坏，改提一套直接衡量"压缩后状态质量"的四维指标。

正文顺着论文走：先讲清 agent 上下文为何特殊（§1），再立统一管线和形式化目标（§2-3），然后是分类法（§4）、失败模式（§5）、领域差异与评估（§6-7），最后是代表方法的实现和开放问题（§8-9）。

## 1. 为什么 agent 的上下文压缩是个独立难题

### 1.1 上下文爆炸：只增不减的轨迹撞上固定窗口

agent 干一件事不是一步到位，而是走很多步。每一步最典型的形态是 ReAct 范式的 **A-T-O 循环**，产出三样东西：

- **Thought（想）**——这一步打算干什么、为什么；
- **Action（做）**——调哪个工具、传什么参数；
- **Observation（看到）**——工具返回的结果、报错、截图。

每走一步，这三样就追加进上下文。于是上下文只增不减，很快撑爆模型窗口——这就是**上下文爆炸（context explosion）**。撑爆的后果不是"慢一点"，而是模型答题质量本身垮掉：信息被稀释、关键约束被淹没、长程规划散架。

一个常见的反驳是"那把窗口做大不就行了"。不行：**窗口大不能替代压缩。** 模型本来就不擅长在海量含噪文本里高效取信息（机理见 [[03-C-上下文与记忆管理]] §2 的平方成本 / U 形曲线 / context rot 三连），窗口再大也只是把噪声一起装进去。所以管好上下文是 agent 自主性的刚需，不是可选优化。

### 1.2 四个特点：它为什么不是"静态长文压缩"

过去的长文档压缩、prompt 压缩，处理的都是**一次给全、结构一目了然**的输入。agent 轨迹完全不同，有四个特点，正是这四点让老办法失灵。

形式上记一下：上下文是一个随时间更新的状态 $C_t$，每一步把交互三元组 $x_t = (a_t, t_t, o_t)$（action、thought、observation）追加进去。四个特点：

| 特点 | 是什么 | 对压缩意味着什么 |
|---|---|---|
| **动态增长** Dynamic Growth | 内容一步步来，压的当下根本不知道后面会发生什么 | 只能"盲压"眼前这段，做不到像静态文档那样先通读全局、再决定删哪 |
| **异构混杂** Heterogeneous Composition | 自然语言、代码、JSON、截图、报错全混在一起 | 得分类型对待：自然语言能容忍含糊改写，代码和工具输出必须一字不差 |
| **多步依赖** Multi-step Dependency | 这一步看着没用、被丢掉的，几步后可能正是关键 | 一条信息 $e$ 的真实价值 $\mathcal{U}(e) = \mathbb{E}\!\left[\sum_{\tau=t}^{T} \gamma^{\tau-t}\cdot u_\tau(e)\right]$ 摊在未来多步上，压的当下**根本看不出来** |
| **错误传播** Error Propagation | 压坏的地方不会当场暴露，而是顺着轨迹往后扩散 | 失真 $\delta_t = d(C_t, \tilde{C}_t)$ 被后续推理当成"事实"继续用，$C_{t+k} = U^{(k)}(\tilde{C}_t, x_{t+1:t+k})$，**不可逆地累积**，把 agent 越带越偏 |

> [!warning] 第三、第四条是最反直觉、也最要命的一对
> **多步依赖**说的是"现在没用"不等于"以后没用"，可压的当下你判断不了；**错误传播**说的是一旦压错，错误不会被就地发现，而是被后面每一步当成既定事实层层放大。两条一叠加：该留什么你猜不准，猜错了还救不回来。这正是 [[上下文压缩方案研究]] 里"摘要漂移"的理论根源——漂移 = 单次失真 × 重写次数。

### 1.3 为什么传统压缩会失败

传统压缩（比如 KV cache 压缩）只盯一个目标：**当下这一刻别超预算**，做法是把此刻注意力分数低的 token 踢掉。把这种"静态、一次性"的判断，套到一个不断演化的 agent 循环上，上面四个特点就会让它**层层失真**——因为"哪条信息重要"在持续交互里根本没法被一次性定死。

> [!note] 和几个相邻领域划清界限
> - **KV cache 压缩 / 模型压缩**：管的是模型或系统层的效率；本篇管的是执行期、应用层的上下文取舍。
> - **prompt 压缩**：缩的是单轮的静态输入；本篇面对的是多轮、相关性随时间变化的轨迹。
> - **agent memory 综述**：按"信息存成什么形态"来分类；本篇按"在哪一步介入、压的是什么、压完变成什么"来分，把压缩当成 agent 的一等能力来处理。

## 2. 统一操作管线：Select → Compress → Store → Recover

这是全文的骨架。综述把压缩拆成上下文生命周期上的一个**四阶段算子系统**：

$$C_{t+1} = \underbrace{R(q_{t+1}, \mathcal{M}_t)}_{\text{Recover}} \oplus \underbrace{M\big(\Phi(S(C_t))\big)}_{\text{Store}\leftarrow\text{Compress}\leftarrow\text{Select}} \oplus\; x_{t+1}$$

读法：下一刻的上下文 = 从外部存储取回的旧信息 + 把当前上下文"选出→压缩→落库"的结果 + 新来的这一步交互。四个算子：

```text
当前上下文 C_t
   │
   ▼
[选 Select]   分诊：哪些能压、哪些必须原样留
   │
   ▼
[压 Compress] 变换：从直接截断，到语义改写，到塞进隐空间
   │
   ▼
[存 Store]    落库：压完的结果留在手边，或卸到外部存储 M_t
   │
   ▼ ……（下一轮，需要时）
[取 Recover]  取回：用当前问题 q_{t+1} 从 M_t 里检索、解码出要用的旧信息
```

四个算子各管一段：

- **Select（选）**：分诊——判断上下文里哪部分能压、哪部分必须精确保留。后面很多失败都源于这一步（选错就是 F1）。
- **Compress（压）**：在选中的部分上做变换，轻到直接截断、重到编码进隐空间。
- **Store（存）**：压完的结果，要么留在手边的工作记忆里，要么卸到外部存储 $\mathcal{M}_t$。
- **Recover（取）**：因为价值是延迟的（特点三），要用时再用当前问题从 $\mathcal{M}_t$ 里检索、解码回来。

> [!tip] 这条管线是全文的坐标系，值得记牢
> 后面全挂在它上面：§4 三维分类法（target = Select 的输入、mechanism = Compress + Store、control policy = 何时触发各阶段及 Recover）、§5 三类失败（F1=选错、F2=压坏、F3=取不对）、§7 评估，都是这四个阶段的展开。

## 3. 把压缩理解成"够用就好的状态近似"（进阶）

综述给压缩下了个更本质的定义：**目标是留一份"对未来行动还够用"的最短表示**。这把整个领域统一成一个**充分状态近似（sufficient-state approximation）**问题——"够用"和"最短"是一对矛盾，所有方法都在这对矛盾里找平衡。

### 3.1 压缩 = 一次状态变换

把每种压缩方法都看成一个变换 $O_i: \mathcal{C} \to \mathcal{C}$，$C_t' = O_i(C_t)$，即在任务约束下，把当前状态变得更短 / 重组 / 外置。这个抽象够宽，能装下后文所有算子族：truncation、pruning、summarization、externalization、representation-level compression。

### 3.2 理想状态：够用的最短记忆 $L_\varepsilon$

从算法信息论看，这些算子都是在逼近一个**理想的"够用记忆"**。设 $E_t$ 为当前能访问的环境，$A$ 为 agent 策略，$\tau$ 为任务分布，$\varepsilon$ 为能接受的性能下降上限，定义理想记忆长度：

$$L_\varepsilon(C_t) = \min_{\tilde{C}_t \in \mathcal{S}_t} K(\tilde{C}_t \mid E_t) \quad\text{s.t.}\quad \Delta_\tau(A; C_t, \tilde{C}_t, E_t) \le \varepsilon$$

逐项看：

- $\mathcal{S}_t = \mathcal{S}(C_t, E_t)$：从 $C_t$ 能压出来的所有"合格压缩状态"；
- $K(\tilde{C}_t \mid E_t)$：**条件 Kolmogorov 复杂度**——给定环境后，描述这个压缩状态最少要多少信息（"最短"的严格度量）；
- $\Delta_\tau(\cdot)$：拿 $\tilde{C}_t$ 替换 $C_t$ 后未来任务掉多少分，要求不超过 $\varepsilon$。

> [!note] $L_\varepsilon$ 不是训练目标，是一把"理论标尺"
> 它算不出来、也不拿去训练，只用来立一个理想下界：**一个压缩状态有用，当且仅当它同时做到紧凑（compact）、够用（task-sufficient）、可取回（recoverable）。** 这三个词，正好是后文评估的三个维度。

### 3.3 从"近似"到"失败"：每种机制各赌一件事

这个目标把后两章压成一个问题：**一种方法怎么逼近"够用的未来状态"，又会在哪里失手？** 每种机制本质上都在赌一件事：

- **截断 Truncation** 赌的是：丢掉那段，以后用不上。
- **剪枝 Pruning** 赌的是：留下的就够了（而且留下的一字没动）。
- **摘要 Summarization** 赌的是：改写出的抽象，能替代原始证据。
- **外置 Externalization** 赌的是：挪出去的，要用时取得回——瓶颈从"压缩"挪到了"取回"。
- **表示压缩 Representation** 赌的是：塞进隐空间还够用，代价是没人看得懂了。

在这个视角下，分类法（§4）比的是各种**近似策略**，失败模式（§5）定位的是"够用或可取回"**在哪一步丢的**。

## 4. 三维分类法：压什么 / 怎么压 / 谁来决定

§2 的管线，可以读成一张**设计空间地图**，三条轴：

```text
What  压什么（Select 的输入）  →  5 类对象
How   怎么压（Compress + Store）→  5 类机制
Who   谁决定何时压（Control）   →  4 类策略 + 何时 Recover
```

### 4.1 What — 压缩对象（5 类）

不同对象的粒度、信息密度、因果耦合、可恢复性都不一样，这四项一起决定了它"好不好压"和"压坏了出什么症状"。

> [!info] 对象特性对照表（Table 1）
> ★ 越多代表该倾向越强；"—"表示该维度不适用。
>
> | 对象 | 粒度 | 信息密度 | 因果耦合 | 可恢复性 | 典型失败症状 |
> |---|---|---|---|---|---|
> | **Observation**（观察） | Token / 片段 | ★★ | ★★ | ★★★ | 结构失真 Structural Distortion |
> | **Trajectory**（轨迹） | Episode | ★ | ★ | ★★ | 规划漂移 Planning Drift |
> | **Plan & Reasoning**（计划与推理） | State | ★★★ | ★★★★ | ★ | 元认知错误 Metacognitive Error |
> | **Memory State**（记忆状态） | State | ★★★ | ★★★ | ★ | 检索盲区 Retrieval Blindness |
> | **Representation**（表示） | Token / Latent | ★★★★ | — | — | 语义坍塌 Semantic Collapse |

五类对象：

1. **Observation（观察）压缩**——压原始输入：工具输出、HTML DOM、日志、截图。量大又冗余，但里头一个被删的选择器、一行堆栈、一个视觉线索，都可能决定下一步。所以多被当成**便宜的前置过滤**，手段以 masking、浅层过滤为主。代表：The Complexity Trap。
2. **Trajectory（轨迹）压缩**——压攒下来的多步历史：失败尝试、绕的圈、重复动作。难在价值延迟（特点三），这一步看着没用的，几步后可能救命，所以**最容易踩 F2**。代表：AgentDiet、ReSum、AgentFold。
3. **Plan & Reasoning（计划与推理）压缩**——压内部产物：子目标、推理过程、自我反思、任务拆解。又紧凑又**脆**——删掉一个不起眼的前提，整个下游计划可能就废了，所以**最怕 F1**（得准确判断哪些推理是决策命脉）。代表：ACON、Focus。
4. **Memory State（记忆状态）压缩**——把没完没了的交互流，压成一份固定大小、能跨窗口存活的状态。它对应 **Store**，瓶颈不在"压得准不准"，而在"用时找不找得回"，所以**最容易踩 F3**。代表：MEM1（把"怎么存"和"将来好不好取"一起训练）。
5. **Representation（表示级）压缩**——在自然语言**底下**动手，压 KV cache、多模态 token、隐状态。效率收益最大，但几乎取不回、也看不懂，等于把"改文字"变成了"管一团不透明的状态"。代表：AgentOCR、Q-KVComm、SAC。

### 4.2 How — 压缩机制（5 类）

机制之间的根本差别只有一个：**压完的东西和原文是什么关系**——删掉、改写、精确保留，还是存起来待取。压缩比相近的两个方法，可能在"保不保真、看不看得懂、取不取得回"上天差地别。

- **Masking & Truncation（遮蔽 / 截断）** — `O_trunc(C)=C[:k]`、`O_mask(C)=mask(C,S)`
  保留头尾、或遮掉指定片段。通用、便宜、好上手；但删了就没了（除非另存一份）。适合"越旧越没用"的场景，比如滑动窗口、硬预算。
- **Summarization & Abstraction（摘要 / 抽象）** — `O_sum(C)=Ĉ`、`|Ĉ|≪|C|`
  靠"改写"而非"删除"来缩短，信息密度高、长程更省地方，所以研究 / 搜索类 agent 爱用。代价：保不保真全看模型——漏写、过度概括、凭空推断，是 **F2 的重灾区**。代表：LCoW、COMPASS、ReSum。
- **Pruning & Reduction（剪枝）** — `O_prune(C)=C\R`
  按相关性 / 依赖 / 结构挑出一部分**精确删掉**，留下的一字不改。当句法、指针、执行轨迹必须精确时特别有用（编码、GUI）。但除非冗余很多，压缩力度一般不如摘要。代表：SWE-Pruner、WebClipper。
- **Externalization & Retrieval（外置 / 取回）** — `O_ext(C)=(C',M)`、`O_ret(C,M)=C⊕r(M)`
  把上下文拆成"留在手边的工作态 + 卸到外部的存储"，是 Store + Recover 最纯粹的实现。唯一能同时做到"压得狠"和"还取得回"的机制；风险随之从"压坏"转成 **F3**（漏取、取错、取晚）。代表：Step-DeepResearch、CAT、WebWeaver。
- **Representation Compression（表示压缩）** — `O_repr(C)=C̃`
  直接在隐空间里压，不做显式文本改写，效率最高；但压缩挪到了文字接口之下，可解释、可控、可精确恢复都变差。代表：DebateOCR。

> [!tip] 对象和机制不是一一对应
> 同一个对象能用不同机制压（观察既能截断也能表示级压），同一个机制也能压不同对象。两条轴是正交的，组合起来才定位一个具体方法。

### 4.3 Who / When — 控制策略（4 类）

决定"何时出手"的是控制策略，不是机制本身。同一个算子，可以被预算阈值反应式触发、被外部模块周期触发、或被 agent 自己主动触发。四类策略，"懂不懂语义"递增、"成本和不可靠性"也跟着递增：

| 策略 | 形式 | 靠什么触发 | 强在哪 / 弱在哪 | 代表 |
|---|---|---|---|---|
| **System-Controlled**（系统控制） | $\pi_{\text{sys}}: \mathcal{C} \mapsto (i,\theta)$ | 只看可观测信号：长度、位置、步数 | 可预测、便宜、好测；**但语义盲**——因为预算到了才压、不因为信息没用了才压 | AgentDiet、阈值式 compaction |
| **External Controller**（外部控制器） | $\pi_{\text{ext}}: \mathcal{C} \to (i,\theta)$ | 一个独立模块（小模型 / 规划器 / 检索管理器）看着上下文做决定 | 模块化、控制更稳（压缩能独立于任务执行去调）；代价是多一层延迟、token 开销、还多一个会丢信息的接口 | PAL-UI、AOI |
| **Agent-Controlled**（agent 自控） | $\pi_{\text{agent}}(C_t, s_t) \to (i,\theta)$ | agent 把压缩当成自己的一个动作，$s_t$ 是它的内部状态 | **最懂语义**（同一个在做任务的脑子来决定压什么），适合主动记忆管理和自我反思；弱在 agent 自评一错，就直接成了 F1 | CAT、Focus、ContextBudget |
| **Learned**（学习式） | $\pi_{\text{learn}} = \arg\max_\pi \mathbb{E}_{\tau\sim\pi}[R_{\text{task}}(\tau) - \lambda\,\text{Cost}(\tau)]$ | 从数据里学怎么压（SFT 或 RL） | 表达力最强、原则上最接近 §3 的理想目标；但最费资源、最容易被奖励设计带偏 | ACON、MEM1 |

## 5. 三类失败模式：按"最早在哪一步出错"分类

压缩引发的下游故障，综述**按它在管线上最早出现的位置**归类，对齐 §2 的 Select → Compress → Store / Recover：

```text
上下文到达 → ① 选 → 想/做 → ② 压 → 存 → ③ 取 → 拿去用
              │              │            │
              ▼              ▼            ▼
        F1 压缩前决策错    F2 压缩中丢信息   F3 压缩后取不对
       （选错时机/对象/粒度）（变换把表示压坏了）（存了却取不回 / 取错）
```

混合故障，归给**最早那个引发连锁的点**（因为 agent 工作流天然会错误传播）。

### 5.1 F1 — Pre-compression Decision Error（压缩前决策错误）

错在压缩**之前**：选错了压缩的时机、对象或粒度。问题不在压缩算子，而在"压之前的取舍"已经偏离任务需求。典型：压得太早、看错了某条关键信息的价值、把本该精确保留的约束给压了。

> [!example] 案例 F1：把授权状态当噪声丢了（附录 D.1）
> 任务：删掉 `~/downloads` 下所有 `.pdf`。原始轨迹里，agent 登录、拿到 `access_token`、试着访问目标目录、撞上 `401 Unauthorized`。这个 401 不是偶发错误，它揭示了一条**规则**：后面每个文件系统 API 调用都得显式带上 token。
>
> 压之前该留三条联动的信息：token 值、"调用必须带 token"这条规则、上次 401 的原因。但控制器判断失误——把 token、失败调用的细节、传 token 的规则全当成底层噪声丢了，只留下粗目标 + 一句模糊的"授权失败过"。
>
> 结果：压完之后 agent 还知道"要删 PDF"，却不知道"怎么发起带授权的调用"，于是反复发未授权调用、白白浪费步数。**最早的错发生在压缩前的取舍**，反复的 401 只是它的下游症状。

### 5.2 F2 — In-compression Information Loss（压缩中信息丢失）

错在压缩**操作本身**：变换把语义、结构、关系、约束或细节给压坏了。核心问题是——压完还忠不忠实于原信息。典型：丢了关系结构、把约束过度简化、把"不确定"压成了"确定"。摘要是这里的重灾区。

> [!example] 案例 F2：把"证据不足"压成了"很可能"（附录 D.2）
> 任务：判断材料 A 是否表现出稳定的室温超导。原始轨迹里证据**互相打架**：一个来源说 295K 附近电阻骤降，一个说没测到迈斯纳效应，第三个说复现失败，数据库还标着"未核实、报告冲突"。所以 agent 的中间结论很审慎：**证据不足，下不了定论**。
>
> 和 F1 不同，这些证据都收集到了、也送进了压缩模块。错出在压缩**过程中**：它把这套互相牵制的证据，坍缩成一句"材料 A 显示 295K 相变，暗示可能存在室温超导"，同时把负面和不确定的证据（没有迈斯纳效应、复现失败、未核实、整体存疑）削弱或丢掉了。
>
> 结果：压缩**改了这段轨迹的"把握程度"**——本来支持"不确定"的证据，被压成了"看起来挺有戏"。下游 agent 于是高估证据，给出一个过度自信、其实误导人的结论。**最早的错就藏在压缩这一步里。**

### 5.3 F3 — Post-compression Access Failure（压缩后访问失败）

错在压缩**之后取的时候**：信息以某种形式留下来了，可要用时取不回、展不开、重建不出来。问题是可恢复性，既不是压前的取舍，也不是压时的损坏。典型：检索失败、重建错误、或者状态虽然存着却没法用。

> [!example] 案例 F3：取回了一条"话题对得上、时间却错了"的记忆（附录 D.3）
> 任务：找出 2024 年微软 CEO。原始轨迹里 agent 搜"Microsoft CEO 2024"、打开官方来源、读到 Satya Nadella 于 2014-02-04 出任 CEO。这条正确证据被摘要、外置成记忆条目 `M123`。
>
> 和 F2 不同，压缩**成功**把正确证据外置了，没压坏。但压完后手边的上下文里只剩任务、一个指向外部记忆的指针、和一套"要用时去取"的机制——正确记忆在那儿，得通过一次"压后访问"重新调回来。
>
> 错就出在这一步：agent 没去展开正确的 `M123`，而是发了查询"Microsoft CEO 2024"，检索返回了另一条 `M087`——它话题对得上，**时间却错了**（来自旧文章，说 2013 年 CEO 是 Steve Ballmer）。下游把这条错记忆拼进上下文，答了 Steve Ballmer。**正确证据一直在，错在取的时候没取对。**

> [!note] 三个案例正好是同一条管线的三刀切面
> F1 砍在 Select（该留的没留）、F2 砍在 Compress（留了但压坏了）、F3 砍在 Recover（压对存对了但取错了）。记住这条对应，比记三个名字管用——线上排查压缩故障时，第一步就是定位"最早是哪个阶段失守"。

## 6. 领域差异：压缩没有银弹

压缩是**分领域的**：编码 agent 要结构保真 + 状态连续，Web / GUI agent 要保住异构的多模态观察，DeepResearch agent 靠的是跨长程把延迟证据取回来。

### 6.1 三类 agent 各自的侧重

- **Coding Agents（编码）**——对结构保真、精确证据、可靠恢复的压力最大。标识符、文件路径、句法、局部依赖往往要**精确保留**，所以偏向 structure-aware pruning + 显式留状态。代表：SWE-Pruner、LongCodeZip、CAT。
- **Web & GUI Agents（网页 / 图形界面）**——在异构、部分冗余的观察上干活，可以利用冗余来压（LCoW、PAL-UI），但表示级压缩仍得保住模态和界面线索。
- **DeepResearch Agents（深度研究）**——更多由"延迟证据"定义，而非结构。主要风险是抽象把"只在后期才有用"的证据盖掉了。ReSum、COMPASS 偏摘要，Step-DeepResearch、WebWeaver 偏外置 / 取回以保住长程依赖。

### 6.2 三大生产编码 agent 的对比（Table 2）

综述用统一管线（选 / 压 / 存 / 取）对照了三个生产级编码 agent，只用公开证据和高置信度的产品信号。**它们的共同点不是激进地有损缩短，而是在紧预算下做协同的管线控制**——但重心各不相同：

| 系统 | Select（选） | Compress（压） | Store（存） | Recover（取） |
|---|---|---|---|---|
| **Claude Code** | 反应式、阈值触发 | 对历史**自动 compaction** | 压缩态留在手边的上下文里 | 靠继续往下跑**隐式恢复** |
| **Cursor** | 检索优先：挑文件、代码块、规则 | 相关性过滤 + 现场拼装 | 仓库索引 + 项目规则 + 工作区 | 把检索到的文件 / 规则 / 证据重新注入 |
| **OpenAI Codex** | 任务锚定：盯文件、指令、线程 | 会话延续 + 工作区接地 | 任务线程 + 指令文件 + 仓库状态 | 靠继续线程 + 重新读文件恢复 |

三种重心一目了然：Claude Code 重 **Compress**（反应式 compaction），Cursor 重 **Store / Recover**（仓库索引与检索），Codex 最落在 **Select + 工作区延续**。

> [!info] Claude Code 的 auto-compaction，就是本综述框架的活样本
> 它对应"System-Controlled 策略 + Trajectory 对象 + Summarization 机制 + 隐式 Recover"。它的生产细节（软硬阈值、异步触发、结构化锚点保护、5 级管线）见 [[上下文压缩方案研究]]；Pi 框架的对应实现见 [[07-Compaction-上下文压缩]] 和 [[24-AgentEvent-订阅模型与-Compaction-子系统]]。

## 7. 重新思考评估：别只盯任务成功率

### 7.1 现状的问题

现有基准主要拿**下游任务成功率**判断压缩好坏（辅以 token 数或压缩比）。方便，但不够：

- 成功率把压缩和规划、执行**搅在一起**，分不清到底是压缩好还是别的环节好；
- prompt 更短，几乎说明不了"任务关键证据还在不在"；
- 换个 backbone、换个任务集、换个预算，跨论文一比就失真。

### 7.2 真正该评的，是压缩状态本身

综述指出：该评的不是任务结果，而是**压缩状态本身**。对 agent 来说有四个决定性维度：

$$Q = (D, R, P, O), \qquad J = \alpha D + \beta R - \gamma P - \delta O$$

- **$D$ 任务相关密度**（task-relevant density）：压完留下的内容里，有多少是任务真用得上的。
- **$R$ 可恢复性**（recoverability）：被压 / 被外置的信息，要用时取不取得回。
- **$P$ 传播风险**（propagation risk）：压缩引入的失真在长程被放大的风险（直接对应特点四）。
- **$O$ 运营开销**（operational overhead）：压缩本身（含控制器、检索）的成本。

综合指标 $J$ 把前两个（越高越好）加上、后两个（越低越好）减掉。主张很简单也很要紧：**压缩该按"状态质量"评，而不是只按任务结果**——而且要在各领域自己的约束 $\text{Constraint}_i$ 下评。这里的 $D / R / P$ 三个正向维度，正好回扣 §3 的"紧凑 / 够用 / 可取回"。

> 这一层的思路和 [[06-V-验证与评估]] 一致：终任务成功率是必要、但远不够的信号，得往中间状态质量、可恢复性、错误传播这些更细的维度下沉。

## 8. 代表性方法的实现细节（附录 C，进阶）

综述挑了三个描述相对清楚的方法，剥掉训练细节，只看压缩算子长什么样。

### 8.1 ReSum vs AgentFold：摘要的两种触发方式

两者都把轨迹压成"能重启的可执行摘要"，差别在**摘要是外部工具、还是 agent 自己的动作**：

| 方法 | 谁来触发 | 怎么压 | 压完是什么 | 主要风险 |
|---|---|---|---|---|
| **ReSum** | 周期 / 预算驱动，在长程搜索里调用 | agent 一路攒 ReAct 轨迹，直到摘要被调用；摘要器把先前历史重写成紧凑态，之后 agent 从"原始问题 + 这份摘要"继续，而不是全量历史 | 一份紧凑、能重启的推理态，留住先前发现、有用线索、未决方向 | 摘要可能漏证据、把不确定性压没、或丢掉后期搜索要用的细节 |
| **AgentFold** | agent 每一步自己决定折不折 | 每步把最近交互留作高保真工作记忆，并发一个折叠指令：要么把单步压成细摘要，要么把多步合并成更粗的摘要 | 一份多尺度记忆态：细的局部摘要 + 粗的战略摘要 | agent 可能折得太狠、把异质的中间步硬合、或抽掉后期才需要的细节 |

一句话区分：**ReSum 像"周期性的、工具来做的摘要"，AgentFold 像"agent 自己边走边维护状态"。** 正好对应 §4.3 里 System-Controlled 和 Agent-Controlled 两类策略的落地。

### 8.2 SWE-Pruner：按目标剪枝的行级剪枝

剪枝和摘要的根本区别：**留下的源内容一字不改**。这对编码 agent 尤其要紧——标识符、文件路径、句法、局部依赖常需精确保留。SWE-Pruner 当中间件，卡在编码 agent 和环境之间，拦下冗长的代码观察，返回剪短后的版本。核心算法（只看算子，不看实现）：

```text
输入：代码上下文 C、剪枝目标提示 q、打分模型 F_θ、阈值 τ
1. 把 C 切成行 L = {l_1, …, l_m}
2. 把 C 分词成 tokens X = {x_1, …, x_n}
3. 每个 token x_i：按"和目标 q 多相关"打分 s_i = F_θ(x_i, C, q)   ← 相对 q 打分，所以"按目标"
4. 每一行 l_j：把这行的 token 分数取平均，得行分 s̄_j = (1/|T_j|) Σ s_i
5. 对行分做阈值 / 解码，得保留-丢弃标签 y_j ∈ {0,1}
6. 只留 y_j = 1 的行，拼成剪枝后上下文 C̃
输出：C̃（留下的行一字未改）
```

要点：打分是相对"目标 q"做的，所以**按目标剪**而非一刀切；留下的行原样不动，这正是剪枝区别于摘要、能守住句法保真的关键。

## 9. 开放问题（附录 E，进阶）

综述末尾收敛到几条未来方向：

- **压缩-检索-记忆的边界**：三者常被混用，但功能和可恢复性不同。需要更有原则的框架，判定信息何时该压、何时该外置、何时该留在手边。
- **学会"可取回地"压**：现有学习式策略优化任务成功 + token 效率，却没把"压掉的信息能否在需要时重建"写进目标。该把可恢复性和依赖保留写进训练目标和评估。
- **多 agent 系统里的压缩**：上下文跨 agent 共享时，压缩从"本地记忆优化"变成"通信和协调问题"——什么该摘要、什么该逐字共享、压缩错误如何在 agent 间传播。
- **预算约束下的端到端训练**：压缩通常被当成独立于规划和工具使用的模块，但三者在长程 agent 里紧耦合。在显式预算下联合优化，可能让压缩行为更贴合下游任务。
- **标准化基准与可复现性**：现有工作在 backbone、任务集、预算、压缩对象上差异太大，没法直接比。未来基准除了任务成功和 token 节省，还该在受控设置下报告信息密度、可恢复性、错误传播、控制器开销。

| ④级重要性分级摘要 + CoT 草稿 | Summarization & Abstraction | 这一类是 F2（压缩中丢信息）的重灾区，保真全看模型——你的 CoT 和分级，都是在给这个风险兜底 |
| 软阈值 70% / 硬限 100% 截断兜底 | `System-Controlled` 策略 $\pi_{\text{sys}}$（§4.3） | 它有个通病叫 semantic blindness：只看预算到没到、不看信息还有没有用——这恰好说清了你为什么还得靠 anchor 来补这个窟窿 |
| anchor 物理保护 task id / 状态 / 工具结果 | 因果耦合极高的对象（Plan&Reasoning / Memory State，§4.1） | 这类信息一环扣一环，交给 LLM 摘要必然踩 F1/F2——综述等于给了 anchor 一个"非存在不可"的理由 |

### 第三步：看清你的做法只是"多选一"

- **控制策略**：你用的 `System-Controlled`（阈值触发）只是四类里的一类，另外还有 External Controller、Agent-Controlled、Learned。你没选它们不是漏了，而是被两条约束逼的——不能卡住用户、而且 Go 侧根本拿不到 Worker 的上下文。于是这个选择就从"本该如此"，变成了"四个里、因约束而定的这一个"。
- **摘要漂移**：你方案里靠 fold → append-only 解决的那个问题，综述告诉你它不是个例，而是 `Summarization` 这一整类机制都会有的毛病 F2，再叠加特点四「错误传播」。漂移 = 单次失真 × 重写次数，append-only 正是冲着"次数"这个主因去的。

### 第四步：补缺口——综述里有、你没碰的

这是查缺补漏的重头。分两层：**方法缺口**（别人造好的轮子）和**概念缺口**（你没有的思维工具）。

**方法缺口①：同一格里，别家的另一种做法（直接对比补强你已有的）**

- 你的**④级 LLM 摘要** → 综述给了 **ReSum**（周期触发、把摘要做成一次工具调用）和 **AgentFold**（agent 每步自己决定折不折）。同是摘要，但"谁按下摘要按钮"完全不同，正好补你在**控制策略**轴上的视野（详见 §8.1）。
- 你的**①②规则清 tool 痕迹** → **SWE-Pruner**：不是手写规则，而是**按目标给代码逐行打分再剪**的学习式剪枝（详见 §8.2）。
- 你的 **anchor 规则锚定** → **MEM1 / ACON**：把"该留什么"交给训练，而不是手写规则。

**方法缺口②：你整片没碰的格子（真正的盲区）**

- 整条**表示级压缩**机制（AgentOCR、Q-KVComm、SAC、CodeOCR）——你全程在文本层动手，这一类在 KV cache / token / 隐空间里压，你一个没碰。
- 整类 **External Controller / Learned** 控制策略（PAL-UI、AOI、COMPASS、ContextEvolve）——你用的是 System-Controlled 阈值，另外两类一个没用。
- 另两个生产编码 agent：**Cursor**（检索优先、重 Store / Recover）和 **OpenAI Codex**（任务锚定 + 工作区延续）——和你"重 Compress"的路线，正好是另外两种重心（见 §6.2）。

**概念缺口：你没有的思维工具**

- **完整失败地图 F1/F2/F3**：你的 anchor 防 F1、归档取回防 F3、append-only 防 F2 的累积——但这些是按单点需求逐个加固出来的，手里没有一张全局的失败地图。综述把失败摊成一张完整的图，让你能**提前看见没踩的坑**。比如 F3 不只是"取不回"，还有"取错"（那条话题对得上、时间却错配的记忆）——你的归档闭环挡住了"取不回"，那"取错"挡住了吗？
- **评估四维 $Q=(D,R,P,O)$**：你测的是最终任务成不成。回头看，"anchor 完整性 100%"其实就是在测 $R$（可恢复性）的一块——你早就在做对的事；但 $P$（传播风险）你从没单独测过，而漂移恰恰是 $P$ 的问题。

**补缺优先级（先读哪几个）**

1. **ReSum / AgentFold**（§8.1）——离你最近，直接扩你的④级摘要，还让你看清"摘要触发权"还能怎么分。
2. **Cursor 的检索优先路线**（§6.2）——和你的"阈值压缩"是一面镜子，最能拉开你对"以 Store / Recover 为重"那条路的认知。
3. **表示级压缩**（§4.2）——你的纯盲区，先知道"有这么一层"即可，真要用再深挖。

> 一句话收尾：**综述告诉你设计空间长什么样、有哪些坑（F1/F2/F3）、该怎么评；你的方案告诉你在两条约束（压缩慢、任务不能丢）的夹缝里，这些选择到底怎么排才能上生产。** 本篇之于你，就是一份「体检报告 + 扩展说明书」。
