# 跨层综合与开放问题（Cross-Cutting / Synthesis / Open Problems）

> 综述最后四章把前面 7 个 [[00-Survey总览-ETCLOVG七层框架|ETCLOVG]] 层从"组件覆盖"切换到"系统行为"视角。本笔记把 §10–§13 合在一起：交叉关切、系统级综合、五大开放问题、结论。

---

## 1. Cross-Cutting Concerns（§10）

### 1.1 七层不是独立的

| 关系 | 表现 |
|---|---|
| [[01-E-执行环境与沙箱\|E]] → [[04-L-生命周期与编排\|L]] | execution environment **约束** lifecycle / orchestration 哪种 strategy 可行 |
| [[03-C-上下文与记忆管理\|C]] → [[06-V-验证与评估\|V]] | context management **影响** evaluation 可重复性 |
| [[07-G-治理与安全\|G]] → 全部 | 身份 / permission / audit **横切** 其它六层 |

→ harness design 应当读作**依赖结构**，不是可分组件清单。

### 1.2 Cost-Quality-Speed 三难（trilemma）

更强的 V、更严的 G、更丰富的 O、更保真的 E **都增成本与延迟**。优化速度常牺牲诊断深度或 safety margin；优化质量可能让 iteration 贵到不能日常用。

> 真正的系统必须决定：**哪些 check 同步、哪些 offline、哪些 failure 值得昂贵的 recovery 路径**。

### 1.3 标准化与生态动态

MCP / ACP / A2A 等 protocol 反映对**共享接口**的压力：tool、agent、orchestration state。压力偏向 agent-agnostic 基础设施而非 single-agent integration，但也**把 governance / observability 的责任后推**：标准化 tool call 只在周围 harness 能跨系统保 provenance、permission、cost、failure evidence 时才有用。

### 1.4 持续生态缺口（五个 layer boundary）

1. cross-tool interoperability
2. cost attribution
3. failure recovery
4. multi-repository orchestration
5. human-agent handoff

→ 推动后续综合：核心问题不再是"每层是否有工具可用"，而是**组合后的 harness 是否表现为可靠控制系统**。

## 2. Cross-Layer Synthesis（§11）

> 把 §10 的 cross-cutting concern 合并为五个**系统级**效应，是 Claim 1（harness 是独立 system layer）的中心支撑。

### 2.1 Cost-Quality-Speed Trilemma（系统级）

| 控制项 | 影响 |
|---|---|
| 更强 sandbox + 更保真环境 | 提升 safety / reproducibility，**增 startup latency 和基础设施成本** |
| 更丰富 context / memory policy | 提升 task 连续性，**消耗 token、引入 retrieval overhead、引入 staleness** |
| 更深 evaluation / observability | 提升诊断，**降迭代速度、增存储与 trace 处理成本** |

生产系统不能把 quality 当 scalar——**必须决定哪些 risk 值贵 control、哪些 check 异步或在回归套件中跑、每个 lifecycle stage 哪些 telemetry 值得抓**。

### 2.2 Capability-Control Tradeoff（§11.2）

更强 harness 给 agent 更多权力，但**每多一份权力都扩大 control 问题**：

- 更大 tool 菜单 → task 覆盖广，但 selection error 与 prompt injection surface 增
- 持久 memory → long-running task 可行，但**provenance / staleness / privacy** 风险出现
- 宽松 sandbox → autonomous 执行有用，但**误判 / 失陷 action 的爆炸半径增大**

→ 不是"在功能正常系统上加的 security add-on"，而是**联系 tool schema、context policy、runtime permission、identity、auditability、human approval 的设计轴**。

### 2.3 Harness Coupling Problem（§11.3）—— 局部优化为何脆

各层耦合方式使**局部最优**脆：

- execution environment 通过影响 package 可用性 / reset semantics / latency / failure mode 改 evaluation 结果
- tool description **消耗** context budget 并塑造模型行为
- observability trace **只在 identity / permission state 在同一 granularity 被捕获时**才成 governance evidence
- evaluation design 通过 reward 某些 recovery loop 反馈回 orchestration

→ **harness 改动应当作系统改动测**。某 prompt / tool / memory / sandbox / verifier / monitor 单看有益，组合后可能整体 rollout 退化。

**耦合也解释一个关键观察**：agent score 无法干净归因到模型——必须指明周围 controller。Closed-loop 框下，context policy / tool schema / verifier / recovery loop 任何改动都改了 controller C_H，从而改了同一模型的测量行为（Bölük 2026b）。

### 2.4 从 Agent Framework 到 Agent Platform（§11.4）

| Agent Framework | Agent Platform |
|---|---|
| 提供 agent / tool / memory store / 执行循环等局部 abstraction | 加 durable workspace、managed sandbox、identity、billing、observability、evaluation、governance、跨多 run / user 的 human handoff |

驱动：**long-running agent 不再只是调模型的程序，而是 operational system**——需要 tenancy、合规、fault recovery、trace retention、组织 ownership。

→ 设计问题从 "how do I build an agent?" 变成 "**how do I operate a fleet of agents whose actions remain inspectable and reversible over time?**"

### 2.5 Open Research Agenda（§11.5）

综合指向以 harness 为中心的研究 agenda：

- **harness intervention 而非 model weight** 的 benchmark
- **trace-native attribution** 方法跨层定位失败
- 跨 agent / tool / sandbox / evaluator / human 转移 state 与责任的 **protocol**
- **优化方法** 把 harness 简化跟 model 升级
- §12 把这些转成五个具体开放问题

## 3. 五大开放问题（§12）

### 3.1 Hardening & Scaling Execution Environments（§12.1）

| 子问题 | 实证起点 |
|---|---|
| **frontier model 已能利用 sandbox 弱点** | SandboxEscapeBench |
| defense 仍**分散** | Wu et al. 2025 / Yan 2025 |
| **one-container-per-task** 模式张紧 large-scale 训练与 eval（数万并行 trajectory 需要便宜 reset + replay） | SWE-World 走 Docker-free surrogate environment 方向，learned transition 相对真实执行的保真度未解 |
| **部署 portability** | Docker-based sandbox 继承 Linux 假设；macOS / Windows / 浏览器 / 桌面 / hybrid-cloud 暴露不同 isolation / reproducibility 约束 |

**关键 future work**：让 runtime substrate 既**可测**又**可组合**——共同 security eval（覆盖 prompt injection / goal misalignment / compositional amplification）+ cost model（决定何时用 container / microVM / OS-level / 完整桌面 VM / 浏览器 / learned surrogate）+ portability layer。**MCP 等标准可降组装成本，但只有当 T / G / O 暴露足够 state 保 runtime choice 可审计、可恢复、安全**时。

### 3.2 Maintaining Reliable State in Long-Running Agents（§12.2）

最深 context 问题不是"塞更多 token"，而是**怎样让 agent 工作状态与真实 task state 长时间对齐**。每个 summarize / retrieve / compact / externalize 都可能删约束、扭曲优先级、保留 stale assumption。

**研究 reframe**：把 context management 当 **state estimation**——量化每次 compression / retrieval / forgetting step 损失多少 task-relevant info，bound agent 内部 state 与真实 state 的 divergence。

最近综述把 agent memory 形式化为 write-manage-read loop，识别 policy-learned management 为新兴机制族。未来系统需要：

- uncertainty-aware summary
- remembered fact 的 provenance
- contradiction handling
- explicit staleness marker
- 让 agent 从 durable artifact 重建 missing state（而非信自己压缩历史）的 recovery 流程

也意味 memory 与 evaluation 紧耦：memory policy 应**不仅按 recall accuracy 判**，还按 multi-session task 中是否阻止下游 action error 判。

### 3.3 Diagnosing Failures from Agent Traces（§12.3）

agent eval 太 final-score-centric——run 通过或失败，最终数被当 model quality 证据。对 harness engineering 不够：failed rollout 可能源自模型 reasoning、误导 tool schema、sandbox misconfig、stale context、flaky test、benchmark 歧义、judge instability、orchestration loop。

- Anthropic agentic coding eval 显示 infrastructure setting 可测改 benchmark 分
- Bjarnason 2026 表明 single-run pass rate 隐藏巨大 variance

→ evaluation layer **必须作为测量仪器研究**，不仅 leaderboard generator。

**下一步：trace-native evaluation**——trace 成为系统计算 outcome score / trajectory quality / failure attribution / regression test 的主要对象。observability 已捕 span、tool call、cost、retry、exception、中间消息，**但常与 evaluation pipeline 脱节**——LangChain 2026 survey：89% 团队用 observability，仅 52.4% 跑 offline eval。

future system 应闭环：anomalous production trace → regression case；trajectory metric 直接 over span 计算；diagnostic signal 反哺 prompt / context / tool / orchestration 改动。**Reflexion 在 short-horizon 证 agent 能从自己 trace 学；扩到 long-running multi-session 仍开放**。

### 3.4 Standard Handoffs Across Agents, Tools, Humans（§12.4）

跨 planner / subagent / tool / sandbox / evaluator / human 分布工作的接口仍**特别 ad hoc**。新兴局部标准：MCP（tool access）、A2A（inter-agent comm）、OpenTelemetry（trace 通用底座）。

> **缺的是 cross-layer handoff contract**。planner 给 executor 委派、agent 调 tool、subagent 交还 control、system 升给 human——handoff 应转移**不只 text summary**，还有：intent、constraint、permission、artifact、provenance、budget state、risk level、trace history、unresolved decision。

问题部分技术部分制度：OpenAI 的 Symphony 把 issue tracker + repository 当 agent work 的 control plane；Anthropic 的 long-running agent harness 强调 durable progress artifact + clean handoff state。Governance work 从另一向得同结论：跨系统代用户 action 需要 agent identity、delegation、permission manifest、auditability。**开放问题**：定义足够丰富以保 safety / recovery、又足够简单以广泛采用的 handoff protocol——明确**谁授权 action、转移了什么 state、什么 evidence 支持当前 plan、receiver 允许做什么、何时 control 必须归还**。

### 3.5 Keeping Harnesses Useful as Models Improve（§12.5）

Harness 设计**不应假定单调向更多 scaffolding**。每个 wrapper、reset、verifier、planner、memory rule、permission gate 都编码一条"**模型独自做不到**"的假设。模型能力变 → harness intervention 应被**重估**而非默认有益。

Bölük 2026b 主张 factorial model-by-harness eval 揭示 intervention 改善所有模型、只助特定模型族、还是反转 model ranking。

- Anthropic 报告具体: 之前对一个模型有用的 context reset，对更强模型可舍弃，移除还**降成本而不降质量**
- OpenAI 把 harness engineering 框成"**维持 human attention、repo state、agent execution 对齐**"，而**不只是加 scaffolding**

**Meta-engineering agenda**：harness 需要优化和简化自身的机制：

- Meta-Harness 把 prompt / tool / control loop 当 optimization target 搜索
- NLAH 让 harness module 显式可 ablate
- 生产 observability + cost system（TensorZero / Axon / AgentOps）指向 budget-aware harness 操作

但研究问题更广：**未来系统应识别哪些 intervention causally 对 quality / safety / reliability 负责；跨 harness variant 跑 shadow-mode 或 A/B；在联合 quality / latency / cost / risk 约束下优化**。

> 中心 risk：**benchmark overfit**——只对窄套件优化自己的 harness 可能变脆。更耐用目标是 *adaptive simplification*：harness 持续问，task / tool / model 能力变化时**哪些 control 仍必要**。

## 4. Conclusion（§13）

把 agent harness 当**独立工程 surface**论证：**基础设施质量，不仅模型能力，是真实世界 agent 可靠性的天花板**。围绕这个 binding-constraint thesis 提三 Claim：

| Claim | 内容 | 体现 |
|---|---|---|
| **Claim 1** | harness 是 binding constraint | 三组 harness-only gain 已超同期模型升级幅度 |
| **Claim 2** | 7-layer ETCLOVG 把 O / G 与 Lifecycle Hook 分开，反映生产团队的 tooling / ownership 组织 | [[05-O-可观测性与运维]]、[[07-G-治理与安全]] 各自独立工具栈与团队 |
| **Claim 3** | 148+ 开源项目映射到 ETCLOVG 给最广 ecosystem snapshot，浮出采用 pattern、coverage 缺口、emerging 设计原则 | §2.9 / §2.4 / 各层 figure |

三段工程演化（prompt → context → harness engineering） + cross-layer synthesis（cost-quality-speed / capability-control / harness coupling）+ open-problem agenda 把 harness 放在更大工程轨迹里。

**局限性**：

- 语料偏 English-language / GitHub-visible / 开源
- 偏 coding-agent 生态
- 扩到闭源生产系统与非 coding ecosystem 会**锐化经验图景**

**自我评价**：分类法 *descriptive*。把 ETCLOVG 从**仅分类 harness 设计**升级为**指导设计决策的 normative framework**——是这本综述希望鼓励的**下一步**。
