## 1. 这一层的核心问题

> **简单陈述，难做对**：让模型每一步看到的信息**正好足够**——不要更少（缺状态无法做对），不要更多（性能以可测量、跨模型一致、尚未被完全理解的方式退化）。

按时间尺度分三档：

1. **短期**——单次 inference 步骤或会话内的几步（active context window）
2. **中期**——同 session 跨多 turn、或同 task 跨多 run 的 session state
3. **长期**——跨 session / task / agent 的持久 memory

这三档构成的三层 memory 架构，与传统操作系统的 memory hierarchy 一一对应——既是直觉来源也是术语对照。

---

## 2. 为什么"context 必须主动工程化"

> 更大的 context window 并**不**自动解决 memory 问题。理由要看架构本身。

### 2.1 平方级注意力成本

Transformer 的 self-attention 计算对 context 中**每一对 token** 都要算 pairwise relationship。n 个 token → n² 对权重；计算与显存都是平方级。

工程优化（FlashAttention、position-encoding interpolation）只降常数因子，不动平方结构。**context 翻倍 = 成本四倍**。所以 context window 是一种稀缺资源。

### 2.2 U 形注意力曲线

架构成本不足以解释"在算力够时模型仍然在长 context 上 fail"。Liu et al. (2024) 给出关键实证：

- 20 个文档的多文档 QA，相关文档在 context **中间**位置时，准确率比放在**首尾**低 30 % 以上
- U 形性能曲线在不同模型、任务、context 长度上都成立——**包括专门为长 context 训练的模型**

工程含义：**信息放在哪儿和有没有放一样重要**。检索拿对内容但放错位置，相当于白拿。

### 2.3 Context Rot（大规模下的上下文腐烂）

Hong et al. (2025) 在 18 个 frontier 模型（GPT-4.1、Claude Opus 4、Gemini 2.5、Qwen3）上做控制实验，把 input length 与 task difficulty 隔离测试：

- **每个模型都随输入增长退化**
- 退化非均匀、任务相关——*semantically ambiguous query*（相关段落与问题不字面匹配）下降比 *exact-match query* 陡，指向复合失败：模型既不能定位相关信息，找到后也无法 reason
- 退化在窗口远未填满时就开始——**标称 200K token 的模型可能在 50K 处就显著性能下降**
- 不是边角案例，是任何**累积工具输出、中间推理、跨多步文件内容**的 agent 的常态

**综合结论**：context management 不能事后补——每个"放什么、放哪、什么时候移除"的决定都直接影响 agent 可靠性。

## 3. 从 Prompt Engineering 到 Context Engineering

| 维度 | Prompt Engineering | Context Engineering |
|---|---|---|
| 优化对象 | 单次模型调用的静态文本输入 | 每一步推理可用的完整信息状态 |
| 时间范围 | 单次调用 | 多步任务 |
| 信息流 | 1 路 input | 多路信息流灌入 |

Anthropic Applied AI Team (2025) 的定义："在 LLM inference 中策划和维持最优 token 集合的全部策略"——指导原则是**找到最小的高信号 token 集，最大化期望结果的概率**。

**Context 在部署 agent 的 inference time 里包含什么**：

- system prompt + behavioral instruction
- tool 定义和 schema
- 前几轮历史
- 当前轨迹的 tool call 结果
- 检索文档或 memory record
- 动态注入的输出格式

这些都在**同一份有限注意力预算**里竞争。context engineering = 每步都对每个组件做**显式选择**，不让它们自由累积。

### 三层 memory 架构作为组织框架

这一架构已成主流。映射到 OS：

| 时间尺度 | 类比 | 对应工具 / 技术 |
|---|---|---|
| Active context window | RAM | system prompt 校准、token-efficient tool、JIT retrieval、KV-cache aware design |
| Session-level state | swap / 文件 | 结构化 note-taking、planning-with-files、cross-run injection |
| Cross-session storage | 持久化磁盘 | MemGPT 类 tiered memory、Mem0、A-MEM、Hindsight、Honcho、cq |

## 4. 短期：管理 Active Context Window

> 直接影响每次调用的成本和模型行为。

### 4.1 System Prompt 校准

设计挑战 = 找到**对的 altitude**：

- 太具体 → 引入脆弱、维护重的逻辑
- 太模糊 → 没有具体指导
- 推荐流程：在最好的模型上从最小 prompt 起跑，**实测找出 failure mode 后**针对性补；事先枚举所有 edge case 只会撑爆 prompt 而不提升可靠性

实操上有效的 system prompt 用 XML tag 或 Markdown header 分清楚 background / instruction / tool guidance / output format。

### 4.2 Token-Efficient 工具设计

Tool 定义是主要 token 消耗者——每个 schema / name / description / parameter type 每次调用都注入。大 tool 集可能在 agent 读到用户请求前就吃掉几万 token。

原则：**少而表达力强**胜过**多而窄**。如果人类工程师都说不清在某情境下该用哪个工具，模型也办不到。Tool 要 self-contained、对错误鲁棒、用途明确、参数名利用模型强项。

### 4.3 Just-In-Time Retrieval 与 Progressive Disclosure

不在前面 load 所有"可能相关"的内容，而是维持轻量标识符（文件路径、存储查询、web link），任务展开时用它们 load 数据。Anthropic Applied AI Team (2025) 称为 *progressive disclosure*。

**Claude Code 的混合策略实例**：

- CLAUDE.md 文件在 session start 一次性 load，提供项目上下文
- `glob`、`grep` 让 agent 在需要时 navigate 并 load 具体文件

环境元数据本身也带隐式信号——文件大小提示复杂度、命名规范暗示用途、时间戳是相关性代理。

### 4.4 KV-Cache Aware Context Design

> Prompt caching 是生产 agent 单一最具成本效益的优化，**收益完全取决于 context 如何组织**。

Manus team 经五次架构迭代后把 KV-cache hit rate 定为"生产阶段 AI agent 的最重要指标"——Claude Sonnet 上 cached token 0.30 美元/MTok vs uncached 3.00 美元/MTok。

三条规则：

1. **保持 prompt 前缀稳定**——system prompt 开头一个 token 差异就让其后全部 cache 失效
2. **context 当 append-only 处理**——修改 / 移除过去 action 或 observation 会创建不同的 prefix sequence，破坏 cache 复用
3. **确定性序列化**——JSON 的 key 顺序不稳定会跨"等价请求"静默失效 cache

因为 tool 定义通常出现在序列化 context 的**前部**，**加 / 减工具会让后续 turn 的整段 cached 内容失效**。Manus 的做法：用 context-aware state machine，**在 decoding 时 mask token logits 阻止选择不可用 action**，而不是在 runtime 修改 tool 定义列表。

Anthropic 通过 explicit `cache_control` breakpoint 在产品层暴露这套机制。

## 5. 中期：Session State 与跨 Run 持久化

> 填补"active context window"与"完整长期 memory 系统"之间的空隙。**几百 token 的结构化工作状态**就能跨过 context reset，避免 agent 丢失累积进度。

### 5.1 结构化 note-taking

最简版本：让 agent 维护持久化 note 文件（典型 `NOTES.md` / `todo.md`），run 开始时读、context clear 之前写。

**Anthropic 让 Claude 玩 Pokémon 数千 game step 实测**：没有显式 memory 指令，agent 自发开发出探索区域地图、战斗策略胜负统计、跨 context reset 追踪的目标。每次 compaction step 清主对话历史后，agent 读自己的 note 继续多小时的 training sequence 而不丢失 coherence。

关键洞见：**note-taking 把 working memory 外置**——agent 写重要内容到外部 store，按需读回，不依赖对话历史承载 task state。

### 5.2 File-Based Planning 与任务外置化

把整个 planning representation externalize 到磁盘：

- `planning-with-files`——持久化、基于文件的 planning skill 包
- **Trellis**——管理 project memory 和 spec injection，按 step 需要**选择性注入**

每个 milestone 把 task state / spec / 中间结果 / dependency graph 写到 filesystem，下一次 run 开始时**选择性 load**——绕过 context window 装载"目前不立即相关"的内容。

### 5.3 Cross-Run Injection

补充模式：捕获前一 run 的**显著输出**，注入到下一 run 开头：

- `claude-mem`——plugin 风格 memory layer：捕获 session 历史，提取对未来 run 有用的信息，prepend 到下个 session 的 context
- 不要求向量库、不要图 store，提供大量跨 run 连续性
- `everything-claude-code`（GitHub 150K+ star）是这种模式的最大公开集合，证明 mid-tier memory 已被广泛生产采用

### 5.4 中期权衡

| 优势 | 限制 |
|---|---|
| 比单纯 in-window 管理给出**显著更高的连续性** | 信息只能**前向流**（run-to-run）不可索引检索 |
| 成本远低于完整 long-term memory 系统 | 不容易 scale 到大量历史 |
| 简单、对现有 coding-agent 工作流贴近 | 大跨 run 历史或精确检索需求要补上 long-term tier |

## 6. 长期：Persistent Memory Systems

> 提供**索引化、可检索**的存储，跨 session / task / agent 持久。区别于中期：**任意 recall**——给一个 query，返回最相关的存储 memory，不管它何时被创建。

### 6.1 基础架构

| 工作 | 关键贡献 |
|---|---|
| **MemGPT**（Packer et al., 2023） | OS 启发的分层 memory——LLM context window 当 RAM、外部 storage 当 disk，模型显式分页 |
| **Generative Agents**（Park et al., 2023） | Memory Stream 架构：每个 observation 带 timestamp + importance score；retrieval 综合 recency / importance / relevance；周期性 reflection 把观测合成更高层 insight |
| **MemoryBank**（Zhong et al., 2024） | Ebbinghaus 遗忘曲线驱动的 dynamic forgetting + 层级化 user-personality summary |

**observation–reflection–retrieval 三件套**仍是 agent memory 的标准设计。

### 6.2 生产 memory 系统

| 系统 | 设计要点 | 工业证据 |
|---|---|---|
| **Mem0** | 向量库（语义） + 图库（关系） + KV 库（事实），LLM-based extraction 把 interaction 路由到对应后端 | 1400 万次 Python package 下载、41K GitHub star，原生集成 CrewAI / Flowise / Langflow；AWS Agent SDK 2025 独家选用；LOCOME benchmark 上比 OpenAI native memory 准确率高 26%，token 用量少 90% |
| **A-MEM** | Zettelkasten 启发的 dynamic knowledge network——存的不是扁平 record，而是带 keyword / tag / 上下文描述 / 动态 link 的结构化 note，**新增 memory 时回填更新相关旧 memory** | 解决 retrieval 系统的根本限制：write-time 看不出 relevance，要在与后来 memory 的关系中评估 |
| **Hindsight** | API 三操作：`retain` / `recall` / `reflect`——把 memory 从"记住"重新表述为"学习"；内部 reasoning pipeline 提取 temporal entity、去重 overlapping fact、构造 evidence-grounded knowledge record | LongMemEval 上 state-of-the-art |
| **Honcho**（Plastic Labs） | 构建用户 *model* 而非 fact 集合；异步 reasoning pipeline 持续"做梦"，从过去交互中提取**推断性结论**（偏好、沟通风格、目标） | entity-centric data model 支持 multi-agent 环境——每个 agent 自己的 observation 视角，但共享 user model |
| **cq**（Mozilla AI） | shared memory across agent instances——大部分 memory 系统是 per-agent / per-user，多 agent 各自重新发现别人已学到的事。**MCP-native**，三层（本地开发机 / org 共享 / cross-team） | post-error hook 模式：agent 遇错时 cq 自动查共享 KB，防止跨部署独立重复的失败 |

### 6.3 学术分类

- **Zhang et al. (2025) memory mechanism survey**——区分 short-term / long-term，long-term 再细分 semantic / procedural / episodic；**write-read-manage loop** 成为标准词汇
- **Du (2026)** survey——形式化为 POMDP 风格 agent cycle 中的循环，提三维分类（scope / format / compositional structure），描述三种工程 pattern：A monolithic context、B context window + retrieval store、C tiered memory + learned control policy（与本节短/中/长期对应）
- **Gao et al. (2023) RAG survey**——retrieval-augmented generation 的背景

## 7. 长程技术（100+ turn 的 coherence 维持）

> 前面各节针对单一时间尺度。Long-horizon 任务（大代码库迁移、multi-session research、扩展自治 workflow）需要**同时协调三层**并实时决定每个点用哪种技术。

### 7.1 Context Compaction（上下文压缩）

逼近窗口上限时**总结**当前 context，用压缩表示重启执行。

**校准挑战**（Anthropic Applied AI Team, 2025）：summary 必须保留架构决策、未解 bug、实现细节，**同时丢弃**冗余 tool 输出和已被吸收的中间推理。

推荐调优流程：

1. 起步 **最大化 recall**——captures every potentially relevant piece from the trace
2. 迭代 **删冗余**——improve precision
3. **绝对不从反方向开始**——early 删太多会让 agent 失去后来才发现需要的 context，且该 loss 不可恢复

**Tool result clearing** 是最轻量的 compaction 形式：一旦 agent 已据 tool 输出动作，把原始 output 替换为简洁的 path reference。可连续应用，现在是 Anthropic 开发者平台的产品级 feature。

### 7.2 Sub-Agent Context Isolation

子任务需要深探时，探索本身产生大量中间 context，对 sub-task 内部有用但对 orchestrator 整体视图是污染。

Sub-agent 架构 = 把 sub-task 委派给独立 agent，每个**自己的 fresh context window**，只返回 1,000–2,000 token 的浓缩 summary。

- 简单 sub-task：context 完全不共享
- 复杂 sub-task 需要共享 state：orchestrator 完整 context 传给 sub-agent

但 sharing context 在 agent 间**昂贵**：更大 prefill、不同 system prompt 间无法复用 KV-cache。每种 task 类型必须**显式做隔离成本 vs 协调收益的权衡**。

### 7.3 Hybrid Decision Frameworks

生产部署不会"一种技术统一应用"，而是在执行过程的不同点按任务结构选不同技术：

- 预加载始终需要的内容
- 只在条件需要时 just-in-time 检索
- 窗口接近饱和时 compact history
- 当 sub-task 探索会污染 orchestrator 时 spawn sub-agent

**Harness 层视角**：context management **应当是基础设施的工作**，不是 agent 的工作——当 harness 自动处理 compaction 和 consolidation 时，模型才能专注 task reasoning。

## 8. Context Drift（上下文漂移）—— 当前最难的开放问题

### 8.1 Context Drift vs Context Rot 的区分

| 性质 | Context Rot | Context Drift |
|---|---|---|
| 属于 | 单 inference step 的属性 | 扩展 trajectory 的属性 |
| 触发 | 给定固定 context，token 加多就退化检索 / 推理质量 | 跨 turn 累积，行为渐渐偏离原意，compaction 和 retrieval 减缓但**无法阻止** |
| 表现 | 一次调用答错 | 100+ turn 后**重复已完成的工作、矛盾早前决策、忘掉根本动机** |

**根因不只是窗口饱和**：即使激进 compaction，每次压缩 step 留下的 summary 都带**细微 inaccuracy**，会随时间复合。累积 assumption 偏离实际 task environment，**当前架构里没有任何东西在检测这种 divergence**。

### 8.2 评估缺口

标准 benchmark 评估**几十 step 内完成的任务**——100+ turn 才出现的 failure mode 没被捕获。最近工作开始补：

- **MemBench**（Tan et al., 2025）——评估跨 multi-session 场景的 memory 质量：temporal reasoning、knowledge update、cross-session aggregation
- **MemoryArena**（He et al., 2026）——专门针对 interdependent multi-session task——context drift 最具破坏性的条件
- **Hu et al. (2025b)** ——incremental multi-turn 评估方法学，把 memory 质量从 generation 质量隔离开

benchmark 必要不充分——它们**证明 drift 发生，但不给出防止它所需的机理理解**。

### 8.3 为什么现有技术不够

- **Compaction** 减少 token count，但不保证压缩表示准确捕获所有相关 state——每次 compaction 丢的信息真就丢了
- **Retrieval** 浮出相关历史 memory，但 query 必须**形成良好**——drifting agent 可能不知道该检索什么来纠正航向
- **Sub-agent isolation** 阻止 sub-task context 污染 orchestrator，但 orchestrator 自己的 context 仍会累积 drift

**Bowne-Anderson & Huber (2026)** 论断：这些限制定义了一个边界——**context engineering 单独无法解决 long-horizon 可靠性**。

需要的是**完整 harness 层**：verification loop、strategic interval 的 human-in-the-loop checkpoint、能识别 behavioral divergence 的 anomaly detection——这驱动 [[05-O-可观测性与运维|O 层]] 和 [[07-G-治理与安全|G 层]] 作为 context engineering 的**必要补充**，不是分离关注。

## 9. 本层小结

### 9.1 三层架构对应表

| 时间尺度 | 解决的核心问题 | 代表技术 |
|---|---|---|
| **短期（active window）** | 单步效率与可靠 | system prompt altitude、token-efficient tool、JIT retrieval、KV-cache 友好序列化 |
| **中期（session state）** | 跨 turn / 跨 run 连续性 | NOTES.md / planning-with-files / Trellis / claude-mem / cross-run injection |
| **长期（cross-session）** | 真正的记忆与学习 | MemGPT / Mem0 / A-MEM / Hindsight / Honcho / cq |

### 9.2 三个反复出现的工程约束

1. **窗口大不解决 memory 问题**——平方注意力 + U 形曲线 + context rot 在 50K token 处就开始退化
2. **KV-cache hit rate 是单一最重要的成本指标**——驱动 prompt 前缀稳定、append-only、确定性序列化的纪律
3. **Long-horizon 可靠性需要跨层补救**——context engineering 是基础，不是终点；剩下的差距由 O / V / G 层补

C 层的限制把综述推到下一组层——**控制面**，它们把 reliability 视为可被独立监控、评估、约束的属性。
